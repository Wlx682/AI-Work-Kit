# 代码合并助手

执行 `merge-code` 的预检、意图分析和合并阶段。合并的完成标准不是“文本冲突已消除”，而是两边业务意图被理解、冲突有明确决策、决策落实到代码并有对应验证。默认完成本地合并并验证，不自动 push、远程合并 PR、强推或删除分支。

## 前置边界

1. 明确代码仓路径、源分支和目标分支；缺少任一项且无法从当前仓库可靠确定时，停止并向用户确认。
2. 缺当前阶段 plan 时运行：

```bash
python3 scripts/workflow-plan-init.py --workflow merge-code --title <合并任务标题>
```

已有 plan 时直接续做，不使用 `--all` 预建后续阶段。
3. 读取工程仓的构建、测试、Git 和分支保护约束；工作流原则只取自 AI-Work-Kit。
4. 工作树不干净时不得自动 stash、丢弃或覆盖用户改动。先说明冲突范围，等待用户处理，或使用明确隔离的 worktree。
5. 默认不改写共享历史。需要 rebase、squash、force push、远程 PR merge 或删除分支时，必须有仓库规则或用户明确授权。
6. 不把“能编译”“无文本冲突”当作业务兼容证据。没有读到调用方、测试、契约或需求依据时，降低置信度并进入开发者决策，不猜业务答案。

## `preflight` 阶段

1. 记录仓库、当前分支、源分支、目标分支及各自 commit SHA。
2. 检查工作树、分支存在性、merge-base、领先/落后提交和已合并状态。
3. 按仓库约束确定合并策略；没有约束时使用普通 merge，不擅自改为 rebase 或 squash。
4. 列出两边变更文件、共同触达模块、公共依赖和高风险交叉点，确定意图分析需要读取的证据。
5. 识别必须运行的测试和回滚方式。
6. 在 plan 末尾追加 `skill_run`，运行门禁进入 `intent-analysis`。

## `intent-analysis` 阶段

这一阶段只分析和形成决策，不执行合并。

### 1. 分别还原两边的意图

对源分支和目标分支分别读取：

- 相对 merge-base 的提交列表与 diff，不只看最终冲突文件。
- 关联的 Plan、PR/提交说明、需求与验收标准；缺失时明确标记证据不足。
- 被改函数的调用方、上下游数据流、API/事件契约、数据库迁移、Feature Flag 与回滚路径。
- 原有测试、新增测试和被删除测试，判断行为变化而非只记录代码变化。

在 `双边代码意图` 表中用独立意图 ID 记录“代码改了什么、想解决什么业务问题、用户可见或规则行为如何变化、证据在哪里”。必须同时覆盖源分支与目标分支，并给出置信度。

### 2. 建立业务冲突矩阵

逐项比较两边意图以及它们共同依赖的模块，至少检查：

- 业务规则、默认值和优先级是否互相覆盖。
- 状态机、生命周期和非法状态是否出现新组合。
- 数据不变量、Schema、迁移顺序、读写兼容与历史数据处理。
- API、事件、错误码和序列化契约的向前/向后兼容。
- 权限、安全边界、审计与隐私行为。
- 副作用、消息投递、幂等、并发、事务和重试语义。
- 删除与修改、重命名与新增、公共依赖升级造成的隐式冲突。
- Feature Flag、灰度、降级和回滚路径是否仍有效。
- 两边单独通过但组合后可能失败的跨模块场景。

每项写入 `业务冲突矩阵`。即使未发现冲突，也要用 `MC-000` 记录已检查范围和证据，不能留空。

### 3. 划分 AI 与开发者决策权

AI 只有在证据充分时可以直接给出“无需开发者决策”：

- 纯机械冲突，例如格式、无语义 import 排序或可证明等价的重命名。
- 向后兼容的并集，且调用方、契约和测试能证明两边行为同时保留。
- 一边已完整包含另一边，且提交关系与最终行为有证据。

下列情况必须在 `开发者决策清单` 中暂停并交给开发者：

- 两边业务规则、状态转换、默认行为或优先级不同。
- 需要选择保留哪一侧、组合成第三种行为，或决定上线/迁移顺序。
- 代码事实无法说明产品期望，测试也不能证明唯一答案。
- 权限、财务、数据丢失、兼容性、并发或不可逆迁移存在不确定性。
- 低置信度意图会影响最终用户、外部调用方或公共模块。

决策项必须列出问题、可选方案及各自影响。只有开发者给出结论、决策人和可追溯确认记录后，才能标记 `已决策`；AI 的建议不能冒充开发者结论。所有冲突都必须在 `合并策略与验证映射` 中对应到处理策略、影响范围和组合验证场景。

### 4. 通过分析门禁

将 plan frontmatter 更新为：

```yaml
status: 已采纳
p0_open: 0
```

在 plan 末尾追加 `skill_run` 后运行门禁。`validate-merge-analysis.py` 会阻止以下情况进入合并：

- 缺源分支或目标分支意图。
- 冲突没有关联意图、业务影响或验证策略。
- 需开发者决策的项目未确认、由 AI 代签或缺确认记录。
- 分析仍有占位内容或 `p0_open` 不为 0。

## `merge` 阶段

1. 切到并确认目标分支，再合入源分支；禁止把方向写反。
2. 严格按已采纳的冲突策略和开发者决策处理；发现新语义冲突时退回 `intent-analysis`，不得在合并现场自行补决策。
3. 发生文本冲突时逐文件理解两侧意图与相邻测试，不使用整边覆盖代替判断。
4. 在 `决策落实记录` 中把每个冲突 ID 和决策 ID 映射到影响文件、落实方式和验证用例。
5. 合并完成后检查 `git status`、提交图和最终 diff，确认没有调试残留、意外文件或未解释的行为变化。
6. 运行单侧既有测试、合并后回归测试以及冲突矩阵中的跨模块组合场景，记录命令与结果。
7. 在 plan 末尾追加合法 `skill_run`，再运行：

```bash
bash scripts/workflow-gate.sh --workflow merge-code --json
```

门禁进入 `review` 后交给 `code-review` 做最终复核。

## 完成证据

- 源/目标分支及合并前后的 commit SHA。
- 两边代码意图、业务规则变化、证据和置信度。
- 业务冲突矩阵、开发者决策及可追溯确认记录。
- 冲突/决策到影响文件和验证用例的落实映射。
- 单侧回归、跨模块组合场景、静态检查或构建命令与结果。
- 本地合并、push、PR 状态分别说明；未获授权的远程动作标记为未执行。
- `Plans/代码重构/` 当前阶段 plan 的 `skill_run`。

## 工作流自身测试优先级

修改 `merge-code` 蓝图、Skill、模板、门禁或校验器时，必须先运行专属 P0 回归；失败时停止后续发布或同步，不得用通用 smoke 通过代替：

```bash
python3 scripts/test-merge-code-workflow.py
```

P0 套件使用临时真实 Git 仓库覆盖：快进、重复合并、跨文件自动合并、同文件不同区块、权限位与内容并行修改、同一行文本冲突、删除/修改、重命名/修改、重命名/重命名、二进制冲突、同路径新增、文件/目录冲突、脏工作树保护、Git 无文本冲突但业务语义冲突、开发者决策落实追踪。P0 通过后，再运行蓝图校验、通用 workflow smoke 和 Skill 多端一致性检查。
