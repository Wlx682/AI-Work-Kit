Chat 链路 · 事件隔离

多设备场景下的
子龙虾事件流隔离

同一用户在移动端 + Web 端同时操作同一个子龙虾的不同会话时，如何防止事件流串流、消息错位、UI 状态污染。这是单栏纵向叙事骨架——无侧栏、居中阅读列，适合没有明显结构特征的通用长文。

模块 ClawChat 状态 已实现 更新 2026-07-08
01 — 问题域

为什么需要隔离

OpenClaw 协议有一条硬约束：一个 sessionKey 在服务端同一时刻只能有一个 active 会话。当设备 A 激活会话 X，设备 B 的会话 X 会被标记为 archived。这条约束一旦遇上多设备并发，就会产生事件串流。

典型场景：移动端进入某会话的历史（active=false），Web 端在同一会话发起新对话，服务端把新 runId 的流式事件推送到所有订阅该会话的设备。移动端并没有这轮对话的用户问题，不应该渲染这些事件。

!
修复前的 bug：移动端看到 currentRunId=nil 就认领了远程 runId，结果 Web 端的回答被拼接到移动端历史消息的最后一轮。
02 — 核心概念

四个关键标识

概念说明生命周期
sessionKey会话标识符，如 agent:main:main持久
sessionId会话 UUID，服务端分配持久
runId对话轮次标识符，每轮一问一答生成一次临时
active会话是否活跃，服务端维护且唯一动态

隔离的本质，是在事件到达时用这四个标识回答一个问题：这条事件属不属于「当前设备正在看的这一轮对话」。

03 — 解决方案

三层防护体系

隔离不是单点判断，而是三层依次收窄的守卫：从「是不是这个 Agent」，到「是不是这一轮」，再到「本机是不是活跃」。

Layer 2 的双守卫

远程 runId 认领是最容易出错的一环。它要求两个守卫同时满足：会话必须活跃，且历史加载状态必须是「有未完成 turn」。

guard handler.active else {
  // 非活跃：用户在查看历史，拒绝认领
  return
}
guard handler.initialHistoryLoadState
      == .pendingUnfinishedTurn else {
  // 无未完成 turn，不认领远程事件
  return
}
handler.currentRunId = runId  // 通过双守卫，认领
04 — 状态机

历史加载的四态流转

Layer 2 是否放行，取决于 NMChatInitialHistoryStateCoordinator 的状态。关键是 pendingUnfinishedTurn——它告诉守卫「当前有未完成对话，允许放行远程事件等待认领」。

i
30 秒安全超时：若 pendingUnfinishedTurn 内一直没收到事件，自动转 resolved，防止永久卡在 pending 状态。
这套设计的核心判断：不靠「有没有 runId」单点决定，而是靠「本机是否活跃 × 历史是否有未完成轮次」两个维度交叉，才决定要不要认领一条来路不明的远程事件。
