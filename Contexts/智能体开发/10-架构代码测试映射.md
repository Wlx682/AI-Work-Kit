# 架构—代码—测试映射

## 一、问题：图画得越细，越容易和代码一起过期

学习文档最危险的不是写少，而是把历史实现写成当前事实。这个仓库已经经历`system1/system2 → capabilities`、手写Team/MessageBus → Team Graph等重构，因此必须让每个结论同时指向代码和验证证据。

## 二、证据口径

```text
设计结论
  → 当前代码路径
  → 对应接口/状态
  → 成功测试
  → 失败测试
  → 最近实际运行结果
```

| 状态 | 可以说 | 不可以说 |
|---|---|---|
| 只有文档 | 已设计 | 已实现 |
| 有代码 | 已实现 | 已验证 |
| 有测试文件 | 有测试覆盖 | 本次测试通过 |
| 当前命令成功 | 本次通过 | 未来永远正确 |

## 十、文档防腐协议

代码变更时按以下顺序更新：

1. 先改代码与测试。
2. 更新本页映射和验证结果。
3. 更新对应专题的流程、Schema和缺口。
4. 最后更新`00-知识图谱`状态与`last_verified`。
5. 路径删除/重命名必须搜索旧引用；历史Plan可保留，但要标注superseded。

学习完成不以“文档读完”为准，而以能从一个新失败反推模块、接口和测试为准。
