# 测试先行原则

> 母原则：[[Contexts/决策/Kit核心原则]] 的“测试先行原则”。  
> 核心口径：**先定义如何证明它对，再实现它。**

---

## 一、适用范围

所有建设动作都继承本原则：

- 工作流 / 蓝图
- 阶段任务 / Plan
- Skill
- 脚本
- Prompt
- 智能体能力
- 对外系统接入

测试先行不等于所有场景都必须先写自动化测试代码；它要求先定义可验证证据。

---

## 二、最小测试包

每次实现或接入前，至少先定义三类样例：

| 类型 | 说明 | 例子 |
|------|------|------|
| 正例 | 什么应该通过 | “全流程开发支付收银台”应命中 `client-dev` |
| 反例 | 什么必须拒绝 | “实现这个函数”不应被强行路由到 `client-dev` |
| 边界例 | 什么需要阻塞确认 | `workflow=unknown` 应返回 unknown 或要求确认 |

还要明确验收证据：

- 自动化脚本 / fixture
- 命令与预期 stdout / exit code
- JSON、表格或文本样例输出
- 人工检查表
- 真实或模拟调用记录

---

## 三、对象级要求

| 对象 | 测试先行产物 | 不满足时 |
|------|--------------|----------|
| 工作流 / 蓝图 | 正例、反例、边界例、阶段退出条件、门禁命令 | 不新增或启用蓝图 |
| 阶段任务 / Plan | 验收标准、失败样例、可检查交付物 | 不标记完成 |
| Skill | 触发样例、不触发样例、输出格式、越界禁止项 | 不同步到多端 Skill |
| 脚本 | 最小 fixture、成功/失败命令、预期 stdout 或退出码 | 不作为门禁依赖 |
| Prompt | 输入样例、期望 JSON/表格/文本、反例拒绝规则 | 不固化为 Skill 或工具 |
| 智能体能力 | 任务目标、工具调用期望、禁止动作、观察结果验收 | 不接入真实工作流 |

---

## 四、硬规则

- 正例 / 反例 / 边界例先于实现。
- 验收标准必须可检查；优先脚本化，暂不能脚本化时用人工检查表兜底。
- 没有测试样例，不算开始实现。
- 没有试跑记录，不算接入完成。
- 智能体不得自证通过；高风险动作必须有独立验证或人类确认点。

高风险动作包括：

- UI 还原结论
- workflow 门禁推进
- 写入 `Contexts`
- 改 Epic 状态或 WBS 投影
- 自动执行部署、删除、提交、推送

---

## 五、推荐写法

在 plan、Skill 或脚本说明里优先写成：

````markdown
## 测试先行

| Case | 输入 | 期望 | 类型 |
|------|------|------|------|
| T1 | 【】 | 【】 | 正例 |
| T2 | 【】 | 【】 | 反例 |
| T3 | 【】 | 【】 | 边界例 |

验收命令：

```bash
【命令】
```

通过标准：
- 【】
````

---

## 六、与现有工作流的关系

- `client-dev` 在每个 Scope Story 内执行 Red→Green→Refactor，全部 Story 完成后再做全量集成测试；没有独立的“验收测试先行”阶段。
- `plan-gate-check.sh`、`workflow-gate.sh`、`test-workflow-refactor.py` 是可执行验证的优先承载。
- 无法立即脚本化的 Prompt / Skill / 智能体能力，至少先用样例表和人工验收标准固定行为。
