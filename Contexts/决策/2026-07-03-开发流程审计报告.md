## 三、历史主要发现（已由 §七/§八 复核）

> 以下为本日第一次审计时的历史问题清单，保留作演进轨迹；当前有效结论以 §八 为准。

### P1. Codex 工作流路径口径不一致

`AGENTS.md` 写的是 `.Codex/workflows/`，但实际可用蓝图在 `.claude/workflows/`；仓库里存在 `.codex/skills/` 与 `.Codex/skills/` 两套大小写目录，且只有 hooks，没有 workflows。  

影响：Codex 入口会让 Agent 误以为存在 `.Codex/workflows/<name>.json`，新建蓝图或排查时容易落错位置。  

建议：统一命名策略。若工作流真相源仍是 `.claude/workflows/`，则把 `AGENTS.md` 和相关文档全部改成 `.claude/workflows/`；若要 Codex 独立工作流，则补 `.codex/workflows/` 并同步脚本读取路径。

### P1. 技术方案目录与蓝图不一致

`client-dev.json` 的 architecture 阶段写 `Plans/客户端技术方案` / `Plans/服务端技术方案`，但当前标准目录是 `Plans/技术方案/`，文件清单里也没有客户端/服务端技术方案目录。`plan-gate-check.sh` 同样仍从 `Plans/客户端技术方案/`、`Plans/服务端技术方案/` 链接里找技术方案。

影响：新 Epic 进入架构/开发门禁时，可能提示写入或链接到非标准目录，导致模板、索引、清理规则和门禁事实源分叉。  

建议：二选一统一：要么恢复并正式纳入 `Plans/客户端技术方案/` 与 `Plans/服务端技术方案/`，要么把蓝图、门禁、测试 fixture、模板示例统一迁到 `Plans/技术方案/`。

### P1. 反馈协议声明“全 Skill 强制”，实际门禁仍是试点强制

`Kit核心原则` 与 `Skill反馈协议` 写“每个 Skill 完成任务必须输出 `skill_run`”，但 `plan-gate-check.sh` 注释和逻辑仍是：仅 `Plans/需求分析/` 强制，其他路径有块才校验。`workflow-gate.sh` 对蓝图阶段的 `skillRun: true` 会强制校验，但普通单阶段 plan 不一定会被同样强制。

影响：制度层说全量闭环，机械门禁仍是局部闭环；反馈聚合样本会继续偏稀疏，冷却候选也容易假阳性。  

建议：明确当前状态。如果仍是试点，就把长期文档改成“试点中”；如果已决定全量推广，就把 `plan-gate-check.sh` 对所有 `Plans/` 分类强制 `--require`，并补对应回归测试。

### P2. 关系图谱有 5 条双向关系缺失

`relations-check.py` 报告以下反向 dependents 缺失：

- `Contexts/需求分析/需求分析规范.md` → `Templates/模板约定.md`
- `Templates/Epic母版.md` → `Templates/Epic母版-client-dev.md`
- `Templates/Epic母版.md` → `Contexts/决策/AI-Work-Kit工作流总览.md`
- `Templates/电脑管理清单模板.md` → `Templates/模板约定.md`
- `Templates/Epic母版-client-dev.md` → `Templates/模板约定.md`

影响：关系图谱不能完整保护模板与协议的改动影响面。  

建议：运行 `python3 scripts/relations-check.py --write-dependents` 或手动补 dependents，然后把它加入常规审计命令。

### P2. 反馈聚合解析 `contexts_missing` 有异常

`Contexts/决策/反馈聚合-2026-07.md` 的补全候选出现 `[` 与 `]` 各 6 次，明显不是有效主题。  

影响：进化闭环的“缺失 Contexts 候选”信号失真，后续月度复盘会被噪声污染。  

建议：修 `feedback-aggregate.py` 对空数组、行内数组或字符串数组的解析，并增加 fixture，避免把 YAML 标点聚合成主题。

## 八、三次复审（2026-07-03）

### 当前判定

**主链健康，结论从“部分修复”更新为“复审通过-保留治理缺口”。**

- 入口口径：`AGENTS.md` / `CLAUDE.md` / `Skills/README.md` 均指向 `workflow-router` + `.workflows/blueprints/*.json` + `workflow-gate.sh`。
- 蓝图事实：`client-dev`、`computer-mgmt`、`full-cycle` 三个蓝图通过 schema 校验；`full-cycle` 是 engine-index，不作为可运行业务蓝图。
- 路由事实：全流程开发命中 `client-dev`，电脑清理命中 `computer-mgmt`；“实现函数”“需求评审”“workflow=unknown”均未误劫持。
- 门禁事实：当前无 `Plans/Epic/*.md`，`client-dev` 阻塞在 `bootstrap-epic` 且推荐 `template-generator`；`computer-mgmt` 阻塞在盘点 plan 未创建，均符合文件系统事实。
- 多端事实：`.cursor/skills`、`.claude/skills`、`.codex/skills` 与全局同步口径一致，共 23 个 Skill。

### 仍保留的缺口

1. **`skill_run` 全量强制仍是制度强、脚本弱。**  
   `Kit核心原则` 与 `Skill反馈协议` 写“每个 Skill 完成任务必须输出”，但 `plan-gate-check.sh` 仍只对 `Plans/需求分析/` 强制；`workflow-gate.sh` 会按蓝图 `skillRun: true` 强制阶段 plan，但普通单阶段 plan 仍可能漏反馈。

2. **真实 Epic 样本缺失。**  
   当前 `Plans/Epic/` 为空，端到端只能验证“无 Epic 时正确阻塞”，还不能验证真实 Epic 的 `plans.*`、子 plan WBS、`skill_run` 与派生阶段是否一致。

### 下一步建议

1. 决定 `skill_run` 是否全量强制：若是，升级 `plan-gate-check.sh`；若不是，回调 `Kit核心原则` 与 `Skill反馈协议` 文字为“蓝图阶段强制 + 普通单阶段试点”。
2. 下一次创建真实 `client-dev` Epic 后，跑一次端到端审计：`workflow-gate`、`derive-epic-status`、`validate-epic-projection`、`plan-gate-check` 四件套一起验证。

## 十、四次复审（2026-07-03）

已完成 `workflow-run.py` 生命周期命令：

- `advance --run <run> [--stage <stage>] [--reason <reason>]`：默认按蓝图推进到下一阶段，也可指定阶段。
