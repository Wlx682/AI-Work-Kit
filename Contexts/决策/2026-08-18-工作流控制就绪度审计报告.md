# 工作流控制就绪度审计报告

## 一、审计结论

当前 AI-Work-Kit 工作流系统的**机械完整性为 PASS**：7 套蓝图均通过 Schema 校验、专项回归与通用 smoke；两个现有 Epic 的文件事实与门禁派生阶段没有发现会导致错误推进的严重矛盾。

当前系统的**控制就绪度为 PARTIAL**：`client-dev`、`merge-code`、`ui-change` 的部分关键阶段已经具备结构化结果证据，但全库 35 个阶段中仍有 24 个只依赖 Plan 存在、章节、状态或 `skill_run` 等过程事实。它们可以证明“流程动作已经留下文件”，不能证明“现实结果已经成立”。

因此，对“是否可以依据当前门禁和看板扩大自动推进或操作权限”的结论是 **ABSTAIN**：证据模型尚不足以支持这项决策。该结论不是否定现有工作流价值；当前看板可以用于理解进度、发现卡点和回放历史，但不能把所有绿色阶段统一解释为外部结果已经通过。

## 二、控制系统解释模型

本次审计采用以下职责边界：

1. **蓝图是控制策略**：定义阶段、允许的控制决策、退出条件和所需证据。
2. **Plan/Story/TDD/测试报告是被观察事实**：它们不是判定本身。
3. **Validator/Oracle 是测量系统**：负责判断证据能否支持当前控制主张。
4. **Gate 是控制器**：消费合格证据，给出明确判定，但不创造业务事实。
5. **事件是不可变控制证据**：记录一次真实判定的配置、输入、结论和证据引用。
6. **看板是观测与解释面**：展示事实、判定、不确定性和历史，不能发明控制规则。
7. **反馈与进化是外环控制**：使用重复卡点、失效证据和人工裁决改进蓝图，而不是追求一个脱离语境的健康分。

该模型参考：`Pattern-Insights/agent-system-control/cycles/2026-08-17-control-readiness-evaluation/06-article.md`。

## 四、控制就绪度发现（按严重性排序）

### CR-01 · 高：24/35 阶段只能证明过程完成，不能证明结果成立

**证据**

- `bugfix` 的 reproduce、diagnose、fix、regression 只要求子 Plan 与 `skill_run`；回归阶段没有可执行测试结果、目标 commit 或外部结果引用硬门禁。
- `computer-mgmt` 的 inventory、cleanup、backup、harden、review 全部只要求子 Plan 与 `skill_run`。这是可能涉及删除、备份和系统配置的高风险工作流，却没有目标状态、不变量、恢复证据或人工确认契约。
- `learning-loop` 的 8 个阶段只要求章节与 `skill_run`；verify 能证明形成了一篇验证记录，不能证明学习目标或实现结果通过了可复核参考。
- `client-dev` 的 requirement、architecture 等早期阶段存在内容与状态检查，但仍主要证明文档完整性；真正较强的结果证据集中在 Story TDD、测试审核与集成报告阶段。

**影响**

绿色门禁在不同工作流中含义不一致：有的表示外部可执行证据通过，有的只表示文档和反馈齐全。看板若统一显示“门禁通过”，用户容易过度解释为相同强度的结果保证。

**结论**

现阶段不能让仅有过程门禁的阶段独立授权高风险、不可逆操作，也不能用其通过率衡量工作流有效性。

### CR-02 · 高：事件账本尚未形成统一、可资格审查的证据协议

**证据**

- `.workflows/schemas/` 没有门禁事件 Schema。
- 146 条门禁事件中 117 条缺少 `event_id`；现存事件共有 3 种字段形态。
- v2 新事件具备 UUID、Scope 与 Plan 快照，但不记录蓝图版本、Validator/Oracle 身份或完整配置指纹。
- `workflow-gate.sh` 的事件写入被设计为旁路，写失败会被 `|| true` 静默吞掉；门禁调用者无法区分“判定完成且证据落账”和“判定完成但审计证据丢失”。

**影响**

事件可以回放历史，但目前不能稳定回答：这次结论由哪一版蓝图、哪一个评估器、哪套证据规则产生；配置变化后旧结论是否仍然有效；事件缺失是“没有执行”还是“写入失败”。

### CR-03 · 高：双事件生产路径语义不一致

**证据**

- `workflow-gate.sh` 会直接写 Epic/项目聚合事件，v2 事件带 UUID。
- `workflow-run.py gate` 调用未带 `--probe` 的 `workflow-gate.sh`，随后又向 Run 自己的事件文件追加一条不带 UUID 的 `gate_pass/gate_fail`。
- `.workflows/runs` 当前没有真实 Run，说明版本化 Run 身份并未成为现行工作流主路径。

**影响**

一旦启用 Run 主路径，一次门禁调用可能产生两份不同 Schema、不同聚合键的事件。看板、审计和后续进化统计无法自然确定哪一份是权威控制证据。

### CR-04 · 高：不确定性和评估器失效没有成为一等判定

**证据**

- 当前显式展示主要使用 pass、fail、pending。
- `pending` 的兼容投影仍会根据 Plan 状态与 reason 文本标记推导。
- 系统没有统一的 ABSTAIN（证据不足/无法下结论）和 INVALID（环境、参照或评估器失效）协议。
- Validator 命令异常、证据确实违反要求、环境路径失效可能都被压入 blocker/fail 文本。

**影响**

系统无法区分“Agent 没做对”“还没做完”“证据不足”和“测量系统坏了”。这会污染失败率、连续失败告警和工作流进化输入。

### CR-05 · 中高：蓝图声明与实际评估器之间存在隐藏耦合

**证据**

- Blueprint Schema 和 Gate 已支持阶段级 `validator` 字段，但 35 个阶段均未声明。
- 实际专项校验由 `workflow-gate.sh` 根据 `storyTddComplete`、`mergeAnalysis` 等魔法条件名硬编码分派。
- 蓝图版本存在，但 Gate 事件没有携带该版本；只在尚未采用的 Workflow Run 文件中记录 `workflow_version`。

**影响**

单看蓝图不能完整还原“由哪个校验器、按什么版本、检查哪些证据”产生判定。修改 Gate 内部映射可能改变所有蓝图语义，却不会自动使旧事件失效。

### CR-06 · 中：看板已经接近正确职责，但仍承担部分判定解释

**正向证据**

- 当前状态从蓝图与文件事实派生，不依赖 Epic 手写 `lifecycle_state` 路由。
- 旧门禁通过 Plan snapshot 与当前 Plan 匹配，避免旧结论污染当前状态。
- Story 卡片不再发明逐 Story 门禁或把事件缺失显示成异常。
- 卡片和事件支持打开实际证据文件，保留 UUID、commit 与 snapshot 技术详情。

**剩余风险**

- 旧事件的 pending/fail 兼容仍依赖 reason 文本标记。
- 不同强度的阶段通过仍使用相似视觉表达；用户不容易区分“过程完整”“外部结果已验证”和“人工裁决通过”。
- 当前 KPI 统计门禁通过率，但没有同时展示证据资格、ABSTAIN/INVALID 比例和蓝图版本新鲜度。

### CR-07 · 中：现有回归证明机械敏感性，不等于评估资格

**证据**

- 全部专项回归和 smoke 均通过，说明路由、文件门禁和已有 Validator 没有明显实现回归。
- 通用 smoke 主要使用合成 Plan、章节、回执和 JSON fixture 推进阶段。
- 尚未为所有重要门禁固定四类资格样本：正确参考必须 PASS、已知错误必须 FAIL、证据不足必须 ABSTAIN、评估环境失效必须 INVALID。

**影响**

现有测试能够发现“代码不再按当前规则运行”，但不一定发现“当前规则测错了现实对象”。

### CR-08 · 中：现有生命周期审计器与当前权威状态存在概念漂移

**证据**

- `workflow-gate.sh` 已把 Epic `lifecycle_state` 标为 deprecated hint，路由只认文件事实与 Gate。
- `dev-lifecycle-audit-assistant` 的维度 A/D 仍把 `lifecycle_state` 与 Story/Scope 一致性作为主要审计项。
- 已归档“图谱质量审计”Epic 的 `lifecycle_state=story-development`，但只读 Gate 已派生为 done，Epic status 为已归档。

**影响**

旧审计器可能把废弃提示字段的漂移当作控制异常，或让用户误以为该字段仍是权威状态。

## 五、按工作流评估的当前适用边界

| 工作流 | 当前控制就绪度 | 可以支持的结论 | 当前不能支持的结论 |
|---|---|---|---|
| client-dev | 部分就绪，成熟度最高 | Story TDD 文件事实、测试计划审核、集成报告与阶段推进 | 所有早期文档门禁都等价于业务结果有效 |
| merge-code | 部分就绪 | 意图分析、冲突决策和实现追踪链存在 | 最终 review 仅凭回执即可证明合并后业务完全正确 |

| learning-loop | 未达到结果控制就绪 | 学习过程与材料已形成 | 学习目标达成、实现结论可靠或知识已经迁移 |

## 七、进化 Backlog

### P0 · 在控制协议补齐前限制结论和权限

1. 仅有 Plan/章节/`skill_run` 的阶段不得单独授权高风险或不可逆动作。
2. 看板和文档把此类绿色结论表达为“过程条件已满足”，不要统一解释为“结果已验证”。
3. `computer-mgmt` 的 destructive 操作在引入目标状态、备份验证、恢复验证和人工确认前，保持人工执行与逐项确认。

### P1 · 建立可资格审查的统一控制证据协议

1. 为 Blueprint Stage 增加并强制：`decisionClaim`、`evidenceContract`、`validator/oracle`、`verdictModel`、`reEvaluationTriggers`。
2. 新建门禁事件 Schema：UUID、event/evaluation 版本、workflow/blueprint 版本、配置指纹、判定主体、证据引用、显式 verdict、reason、快照和时间。
3. 收敛为单一权威事件生产者；若保留旁路审计，写入失败必须产生可观测告警，不能静默消失。
4. 统一 PASS/FAIL/ABSTAIN/INVALID；`pending` 只表达工作尚未提交判定，不与证据不足或评估器失效混用。
5. 看板只消费显式 verdict；reason 文本推断仅用于带“旧事件/未资格”标记的兼容历史。


### P1 · 为高价值阶段补 Outcome Oracle

1. `bugfix` regression：固定目标 commit、复现用例、FAIL→PASS 转换、相关回归命令和外部目标环境观察。
2. `computer-mgmt`：固定目标清单、dry-run 结果、备份可读性、恢复演练、删除差异和人工批准。
3. `learning-loop` verify：固定学习主张、参考任务、错误解、可迁移输出和人工/程序评分边界。
4. `merge-code` / `ui-change`：把最终 review 从执行回执提升为可追踪裁决和证据引用。

### P1 · 为评估器本身建立资格测试

每个高价值门禁至少固定：

- 正确参考方案必须 PASS；
- 已知错误或历史事故种子必须 FAIL；
- 缺关键证据必须 ABSTAIN；
- 参照、路径、环境或评分器失效必须 INVALID。

### P1 · 把人工裁决变成正式证据

1. 建立 `Human Adjudication Log`，记录争议样本、裁决理由和参与者。
2. 为开放式任务保留 Gold Set 与边界样本，不把“自动能跑”当成“自动可信”。
3. 当评分器分歧、参照失效或环境异常时，允许系统明确输出 ABSTAIN / INVALID，并触发重评。
4. 只要配置、Harness、工具或蓝图版本变化，就重跑受影响的资格样本。

### P2 · 收敛运行态与进化观测

1. 决定正式采用 `workflow-run` 还是移除未使用的第二运行态，避免双权威。
2. 从审计器和模板中移除 `lifecycle_state` 的权威语义，统一只读 Gate 派生状态。
3. 看板增加蓝图版本/配置身份、证据强度、ABSTAIN/INVALID、重复卡点和重评触发器视图。
4. 进化指标同时展示 Agent/工作流表现与评估可信度，禁止只用通过率扩大自主权。

## 八、落地优先级

当前最小可执行顺序是：

1. 先补统一事件字段和显式 verdict。
2. 再补失败种子与四态资格样本。
3. 再把人工裁决、Gold Set 和重评触发器写进长期证据。
4. 最后才讨论看板扩权或自动推进。

## 九、验收标准

本报告对应的进化完成条件不是“所有阶段都有更多门禁”，而是：

1. 每个门禁都能说明自己支持什么控制决策；
2. 每个结论都能追到配置身份、合格证据与显式评估器；
3. 没有资格下结论时系统能够输出 ABSTAIN/INVALID；
4. 看板不从缺失事件、reason 文本或文件状态发明新的控制结论；
