## Findings

### 已完成基线：CloudFiles 与文件预览主体并非从零开始

在本 Epic 创建前，CloudFiles 与文件预览已经有一轮完整的功能和架构建设，不能表述为“都没有改”：

- `e96f3f9b`、`142a924c`、`22fca349`：接通个人云预览生产链，并完成 iOS Quick Look 与 Android 系统预览 Gate。
- `4c1ee55d`：重构统一文件预览与 Files 模块，拆出 Preview Planner、Coordinator、Launcher、Source、App composition provider 与多格式预览页面，并建立边界/运行时/协调器测试。
- `9c156421`：统一 Files 三类文件预览与 CloudFiles 模块，重命名并迁移 CloudFiles Runtime、Provider、下载与预览适配链。
- `1c2be2f8`：接通 CloudFiles 上传及三类文件分享。
- `6073ae16`：补齐 PPTX、HTML、图片多图缓存、统一分享与 Android 媒体兼容。

因此，8 月 19 日创建的目标 Epic 是建立在上述成果上的**第二轮依赖边界收口**：专门消除 Feature → App、composition module → root 的遗留反向依赖，并拆分 App 私有 Runtime 与 Feature 可见投影；它不代表 CloudFiles/文件预览主体功能尚未开发。

### P0：Epic 专属实现阶段尚未开始

- `validate-client-dev.py implementation-design` 返回 `BLOCKED`，原因是缺少 `implementation_design` 路径。
- US-CFR-001 至 US-CFR-007 共 7 个 Scope Story，状态全部为“待落点设计”；对应 `*.impl.json` 尚未产出。
- 进度同步后，功能开发主 Plan 与 US-CFR-001 已统一标记为 `status: 进行中`、`lifecycle_state: implementation-design`；逐故事 TDD、集成测试计划审核和全量集成测试仍未开始。

这不等于 8 月 19 日没有文件相关代码提交。提交复核确认：

- `f1224fb6`（`[需求] 完成 InputBar 附件上传与预览闭环`）实现了 InputBar 实例级附件选择/上传状态机、失败恢复、发送围栏，并扩展 `AppFilePreviewLauncher` / `AppFilePreviewSource` 支持输入附件预览。
- `beeff8dd`（`[修复] 恢复 InputBar 生产附件链`）修正了 ProductChat 附件生产组合的 owner 校验。

- 同日 `81806ede` 虽修改了 Files、`file_download_providers.dart` 与 `composition_root.dart`，实际目标是 QQ/QZone 分享接入，并未删除本 Epic 要治理的反向依赖。

### P0：目标依赖违规仍存在于生产代码

- `lib/features/files/presentation/files_page.dart` 仍直接 import `lib/app/composition_root.dart`、App composition provider 与 `cloud_files_runtime.dart`。
- `cloud_browser_controller.dart` 与 `cloud_drive_sdk.dart` 仍反向 import `app/composition_root.dart` 并读取 `clawApiProvider`。
