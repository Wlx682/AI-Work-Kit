# Flutter 组件化 InputBar 开发流程审计报告

## 结论

**严重矛盾 / PARTIAL。** Slate 已开始开发，但当前实现只是“Slate 最小协议 + Flutter `TextField` 编辑投影 + @agent 原子节点”的 MVP，不是 iOS `NMSlateEditor` 的完整组件迁移。`US-IB-001` 标记为“已完成”与实际代码、测试覆盖和 Epic 阶段均不一致，应撤回完成口径并重新进入 Slate Story 的范围确认与开发。

## 当前实际完成的 Slate 能力

- `NamiSlateDocument` 支持 paragraph、text、agent mention 的 JSON、display text 与 prompt text。
- `NamiSlateEditingController` 把结构化文档投影到 Flutter `TextEditingValue`，提供 mention 原子删除和基础 selection/composing 保护。
- `NamiTextInputComponent` 仍以普通 Flutter `TextField` 为编辑器，通过 `buildTextSpan` 高亮 mention。
- @候选由实例外部注入，使用简单 BottomSheet 选择后插入 agent mention。
- 已补外部状态应用时的重入保护，避免组件回写导致分发死循环。

## 相对 iOS Slate 尚未迁移或缺少证据的能力

- 没有独立 Slate Editor / renderer 组件；当前只是 `TextField + TextSpan` 投影。
- 没有 iOS `NMDocumentManager` / `NMDocumentSynchronizer` 等文档编辑与同步层。
- 没有通用 `NMReferenceProvider` 体系；只有预构造的 agent 候选列表。
- 没有 file reference / file payload 节点，也没有 Slate 内文件引用的编辑与序列化闭环。
- 没有已存在 mention 的重选/替换、光标跨原子节点导航、复制粘贴、撤销重做等完整编辑语义证据。
- 没有中文等 IME 组合输入矩阵、复杂多段文档、未知节点保真、10 万字性能与内存验证。
- 没有 iPhone/iPad、Android Phone/Pad/Fold 的真机编辑回归。

## 根因

US-IB-001 把“iOS Slate 迁移”收窄成了“协议兼容 + @mention MVP”，验收标准只覆盖 JSON 往返、@选择和原子删除。完成该最小纵切后，计划直接把 Story 标成已完成并把当前实现 Scope 转到附件 US-IB-002，因此 Slate 没有继续按 iOS 的编辑组件能力展开。

## 必须纠正

1. 撤回 US-IB-001 的“已完成”结论，状态改为 `PARTIAL`，重新纳入 Sprint Scope。
2. 先按当前产品确实使用的 iOS Slate 生产链补全能力清单和 AC；不使用的多 renderer/旧实现无需机械迁移。
3. 将编辑内核、reference provider、agent/file reference、剪贴板/选区/IME/恢复语义和大文本性能分别落实到实现与测试。
4. Slate 验收通过前，不应以附件 Story 的推进替代 Slate 完成度。

## 最严重待办

**重新打开 Slate Story，并把“完整编辑器能力”写成可验收范围；当前最严重的问题不是代码量少，而是计划把 MVP 错报成完成，导致后续开发绕过了尚未闭合的编辑核心。**
