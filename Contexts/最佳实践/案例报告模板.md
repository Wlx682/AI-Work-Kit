# 案例报告模板

> 用途：`best-practice-digest` 产出每周提效案例。度量口径见 [[Contexts/最佳实践/提效度量口径]]；进化闭环见 [[Contexts/最佳实践/进化闭环]]。
> 一套骨架通用，技术/QA 与 产品/设计/运营 只是「所属环节」不同、证据链取材不同。

---

## 一、开工前先补齐输入（信息不全必须逐项追问，禁止瞎编）

采集这些，缺哪项就追问用户，直到能写出完整报告：

1. 本周主要完成哪项任务（需求调研/原型设计/官网设计/代码提交/数据分析…）
2. 以前你/团队通常怎么做、大约花多久（**基线**）
3. 这次用了什么 AI 工具 / 什么 Prompt / 什么新组合方式
4. 这次实际花了多久（**精确到分钟**）
5. 过程中是否有试错/迭代（Prompt 改了几版）
6. 是否有过程记录（对话链接 / 设计稿历史 / 截图 / commit）

> **红线**：任一项缺失且影响「可测量可验证」→ 追问，不得编造。见 [[提效度量口径]] 反作弊红线。

---

## 二、人类卷写作规范（硬约束，产出必须过这几条）

> 目标：一篇**技术博客水准**的分享——客观、准确、有信息密度，让同行快速看懂并复用。既不是填字段的交付物，也不是娱乐化的段子。基准参照优秀工程博客（如官方 engineering blog）。

1. **叙事骨架，不是字段清单**：按下面「叙事顺序」写成连贯文章，小标题用**说明性短语**（如「问题：三端手工同步」「方案」「踩到的坑」），不许出现「基本信息 / 对应哪个 Kit 能力 / 证据链（可验证佐证）」这类表单标签。
2. **符号当标点用**：正文只用标题、`>` 引用、`-` 列表、**加粗**、代码块。禁止 📌🔴🟢✅⏸ 这类装饰性图标堆砌。
3. **专业中性的语气**：术语直接用、必要时一句话解释，不回避技术细节。**禁止娱乐化比喻、段子、卖关子**（不要「像体检完直接出院」这类打比方）。踩坑部分当作**根因分析**写：现象 → 根因 → 修复，给出可复查的技术细节。
4. **标题说明主题**：用「做了什么 + 效果/机制」的说明式标题（如「用一个校验脚本保证 Skill 三端一致」），不要交付物腔的「提效案例：XXX」，也不要标题党/段子标题。
5. **能画就画**：涉及结构/流程（多端、管道、状态机）时给一个 ASCII 小图或代码块，把「需要想象」变成「一眼看清」。
6. **人类卷不含机器噪音**：不写 `skill_run`、不写「AI 专用/人类可略过」这种自相矛盾的段落。`.meta.yaml` 只在文末一行小字注释里提一句即可。

**叙事顺序（推荐段落流）**：
```
一句话摘要（转发用，前置，客观陈述成果与数据）
→ 问题（旧办法的具体低效点，可量化）
→ 方案（做了什么，具体到可复现）
→ 踩到的坑 / 根因分析（现象→根因→修复，保留技术细节，不打比方）
→ 效果数据（表格，保留可验证性）
→ 复用说明（前提 + 下一步建议 + 溯源实锤）
→ 小结（一句话点明机制本质）
→ 文末：⏸ 报告链接 + .meta.yaml 注释 + 提交确认语
```

## 三、信息完整性自查清单（Agent 内部用，确保没漏，但不作为文章结构）

写完文章后自查，以下信息点是否都已**自然融进叙事**（不是列成字段）：

- [ ] 提交人 / 环节 / 目标频道（可放 frontmatter 或标题行）
- [ ] 旧办法 + 基线数据（含估算需标注「估算」）
- [ ] 新方法（具体到可复现）+ 对应哪个 Kit 能力（融进正文，不单列）
- [ ] 迭代/翻车过程（证明非偶然）
- [ ] 可测量数据表（耗时/可复用性等，选 1–3 维）
- [ ] 证据链（commit/plan/脚本行数等实锤）+ 复现前置条件
- [ ] 进化建议（缺陷→Kit 该补什么 / 完美→固化命名建议）
- [ ] ⏸ 报告链接交接项 + 提交确认语

> 度量口径见 [[提效度量口径]] 反作弊红线：无基线/断证据链一律打回。

## 五、AI 卷：独立元数据文件（`{{案例名}}.meta.yaml`）

> **双卷分离**：人类卷（上面 .md）讲故事、给结论，**不含** YAML 噪音；AI 卷（本 .meta.yaml）只放结构化数据，喂 `feedback-aggregate → vault-evolve`。
> 与 .md 同目录、同名、后缀 `.meta.yaml`。**纯 YAML，不套 Markdown 代码块**（脚本已支持直接解析整文件）。

写一个 `Plans/最佳实践/{{案例名}}.meta.yaml`，内容即原 skill_run（遵 [[Contexts/决策/Skill反馈协议]]）：

```yaml
skill_run:
  skill: best-practice-digest
  plan: Plans/最佳实践/YYYY-MM-DD-案例名.md    # 指向人类卷 .md
  date: YYYY-MM-DD
  contexts_used:
    - path: Contexts/最佳实践/提效度量口径.md
      utility: high
      reason: "按口径取基线与证据链"
  contexts_missing:            # 本次暴露的「该有却缺」的能力 → 下月新 Skill/Contexts 候选
    - "{{如：反爬场景的半自动采集流程}}"
  contexts_stale: []
```

> 兼容旧案例：未拆分的旧报告若仍把 skill_run 写在 .md 里，`feedback-aggregate` 仍能回退读取；同一 plan 两处都有时以 .meta.yaml 为准去重。
