# 提效度量口径

> 作业要求：提效数据必须**可测量、可验证**，创作过程要能转成报告链接。本文定义「什么算证据」，杜绝拍脑袋的「效率翻倍」。

## 一、度量三原则

1. **有基线**：必须有「改进前」的对照值（老办法耗时/返工次数/缺陷数），否则「提升」无意义。
2. **可取证**：每个数字背后有一条可复查的证据链（commit / plan / 看板 / 日志 / 录屏 / skill_run），不是记忆。
3. **可复算**：口径写清「怎么算的」，换个人按同口径能算出相近结果。

## 二、认可的度量维度（选 1–3 个，够用即可）

| 维度 | 老办法基线取证 | 新办法取证 | 计算 |
|------|----------------|-----------|------|
| **耗时** | 历史同类任务耗时（日报/工时/记忆估） | 本次实际耗时（会话时长/commit 间隔/看板阶段时间戳） | 节省 = (旧−新)/旧 |
| **返工次数** | 旧流程平均返工轮次 | 本次返工轮次 | 减少量 |
| **缺陷/遗漏** | 旧流程漏掉的需求点/bug 数 | 本次被 Skill 提前发现的数 | requirement-analyst 报告可直接取 |
| **产出量** | 单位时间原产出（页/用例/组件数） | 用 AI 后同口径产出 | 倍数 |
| **覆盖率** | 手工测试覆盖 | test-generator 生成覆盖 | 百分点提升 |
| **可复用性** | 旧做法是否可复用（低/中/高） | 本次是否已固化（Prompt/Skill/模板） | 低→已固化 |

> **时间戳硬要求**：耗时维度尽量给「开始~结束，精确到分钟」的时间戳，比模糊估值更可验证。

## 三、证据链要求（每个案例必附）

- **技术/QA 案例**（→「2.技术提交分享」）：commit hash / PR / 看板阶段截图 / test-generator 或 review-assistant 产出 / skill_run 块。
- **产品/设计/运营案例**（→「3.产品提效最佳实践」）：需求调研 plan / 原型链接 / 官网设计稿 / requirement-analyst 输出的问题清单 / material-prep 产物。

## 四、创作过程 → 报告链接

作业要求「把创作过程转化成报告链接上传」。落地方式：
- 案例报告草稿存 `Plans/最佳实践/YYYY-MM-DD-案例名.md`，含完整证据链。
- 定稿后由**人工**转成可分享报告链接（纳米Work / 内部文档 / 飞书云文档），Agent 输出「⏸ 待人工：把本报告转成分享链接」交接项。

## 五、反作弊红线

- 无基线的「提升 X%」→ 打回，标注「缺基线」。
- 证据链断裂（只有结论没有可查来源）→ 不进台账。
- 度量口径必须写进报告，审阅者能复算。
- **信息不全必须逐项追问，禁止瞎编**：6 项输入（任务/基线做法/AI方法/本次耗时/迭代过程/过程记录）缺哪项就问用户，补齐再动笔。
