# 进化闭环：作业案例 ↔ 工作流进化

> **核心主张**：这个作业本身就是 AI-Work-Kit 要解决的问题——用工作流放大 AI 生产力。所以每个提效案例有**两个出口**，一次萃取、两处使用：
> - **对外**：交作业（发「2.技术/3.产品」频道）。
> - **对内**：作为工作流进化的**可验证证据**，反哺 Kit。
>
> 不接进化链的案例，只是一次性作业；接上了，才形成闭环。原则见 [[Contexts/决策/Kit核心原则]]。

## 一、AI 工作流创新如何体现（关键）

每个案例必须能回答：**这次提效，是哪个工作流能力带来的？**

| 案例里的新方法 | 对应 Kit 能力 | 创新落点 |
|----------------|--------------|----------|
| Loop Engineering 反复迭代 | `/loop`、resume-assistant、Plans/Contexts 三层 | 上下文可复用、断点续 |
| 并行/多步自动化 | Workflow、subagents | 一次 fan-out 覆盖多任务 |
| 需求漏洞提前发现 | requirement-analyst | 缺陷左移，返工前拦截 |
| 自动出测试用例 | test-generator | 覆盖率提升可测量 |
| 高频操作封装触发词 | Skill 三端同步 | 路径一致、不临场发挥 |

**创新不是「我用了 AI」，而是「我用工作流的哪个机制，把某类任务从点状变成可复用/可度量」。** 案例报告的「本周用了什么新方法」必须点到这一层。

## 二、闭环两条腿（缺一不闭）

### 腿1：案例 → skill_run 反馈（喂给已有进化链）

每个提效案例定稿时，除了案例报告，**必须同时输出一个 `skill_run` 块**（遵 [[Contexts/决策/Skill反馈协议]]），写进案例 plan 末尾：
- `contexts_used`：这次提效实际靠哪些 Contexts/Skill。
- `contexts_missing`：这次暴露出「本该有但缺」的能力 → **这就是 Kit 下一步该长出的 Skill/Contexts**。
- `contexts_stale`：发现哪些文档与现网脱钩。

这样案例数据自动进 `scripts/feedback-aggregate.py` → `scripts/vault-evolve.py` 月度报告，无需另造管道。

### 腿2：案例「可否沉淀」结论 → 工作流进化项

案例报告的「可否沉淀进工作流」字段有三种归宿：
| 结论 | 动作 |
|------|------|
| 值得成为通用能力 | 提一个新 Skill / Contexts 候选（走 `template-generator` 或用户确认） |
| 是现有 Skill 的改进 | 记进该 Skill 的迭代建议 |
| 一次性技巧 | 只留案例台账，不进 Kit |

## 三、月度进化如何消费

`vault-evolve` 月度报告 §1 已聚合所有 `skill_run`。**新增视角**：把当月最佳实践案例的 `contexts_missing` 汇总，作为「Kit 下月进化优先级」的证据来源——从「哪些能力被高频需要却缺失」倒推该建什么。

这样：**员工交的作业 → 变成 Kit 进化的需求信号 → Kit 长出新能力 → 员工下次提效更强**，形成正反馈螺旋。

## 四、一次萃取两处使用（操作口诀）

```
写案例报告（对外作业）
      │
      ├─→ ⏸ 转报告链接 → 发频道（交作业）
      │
      └─→ 附 skill_run 块 + 「可否沉淀」结论
                │
                ├─→ feedback-aggregate → vault-evolve 月报（进化证据）
                └─→ contexts_missing → 下月新 Skill/Contexts 候选（进化需求）
```
