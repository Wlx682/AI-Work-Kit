01 — 问题域

为什么需要隔离

OpenClaw 协议有一条硬约束：一个 sessionKey 在服务端同一时刻只能有一个 active 会话。当设备 A 激活会话 X，设备 B 的会话 X 会被标记为 archived。这条约束一旦遇上多设备并发，就会产生事件串流。

!
修复前的 bug：移动端看到 currentRunId=nil 就认领了远程 runId，Web 端的回答被拼接到移动端历史消息末尾。
02 — 核心概念

四个关键标识

概念说明生命周期
sessionKey会话标识符，如 agent:main:main持久
sessionId会话 UUID，服务端分配持久
runId对话轮次标识符，每轮一问一答生成一次临时
active会话是否活跃，服务端维护且唯一动态

隔离的本质，是在事件到达时用这四个标识回答一个问题：这条事件属不属于「当前设备正在看的这一轮对话」。

03 — 解决方案

三层依次收窄的守卫

隔离不是单点判断，而是三层守卫：从「是不是这个 Agent」，到「是不是这一轮」，再到「本机是不是活跃」。

Layer 2 的双守卫

远程 runId 认领要求两个守卫同时满足：会话必须活跃，且历史加载状态是「有未完成 turn」。

guard handler.active else { // 非活跃：查看历史，拒绝认领
  return
}
guard handler.state == .pendingUnfinishedTurn else {
  return
}
handler.currentRunId = runId  // 双守卫通过，认领
04 — 状态机

历史加载的四态流转

Layer 2 是否放行，取决于历史状态协调器。关键是 pendingUnfinishedTurn——它告诉守卫「当前有未完成对话，允许放行远程事件等待认领」。

核心判断：不靠「有没有 runId」单点决定，而是靠「本机是否活跃 × 历史是否有未完成轮次」两个维度交叉，才决定要不要认领一条来路不明的远程事件。
