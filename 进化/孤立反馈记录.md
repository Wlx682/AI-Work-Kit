### 进化候选：stage 级智能流程规划（需求特征 → 该走哪些阶段/环节）

- **触发**：用户问"能否在整体任务规划时智能决策是否需要某环节，如是否需要接口调试、是否需要接入 API、是否需要 UI 调整"。这是**流程启动时**决定该需求走哪些 stage，不是开发阶段内切片取舍（后者见上一条 WBS 候选的"生产端"）。
- **现状（证据）**：stage 基本是**写死的**。`client-dev.json` 5 个 stage 里只有 `architecture` 有 `onlyIf: {含业务逻辑: 是}`，其余 4 个无条件永远执行；全部 6 个蓝图 `onlyIf` 仅此 1 处。且 `含业务逻辑` 是**人在 Epic 里手填**的字段，非 AI 判断。即"智能规划"目前几乎不存在。
- **诉求本质**：把 `onlyIf` 从"1 处、人工填字段"扩展成"覆盖各环节、AI 读需求特征自动判定该跳哪些 stage/环节"。例：需要接入 API 吗→否→跳联调 stage；需要 UI 调整吗→否→跳 UI/figma；需要接口调试吗→否→跳真机联调。
- **核心张力（须先解决）**：CLAUDE.md 规则3「Epic 是数据上下文，不驱动流程；阶段由文件系统事实判定」+ 门禁「无状态、只读文件事实、不撒谎」。而"AI 智能判断该跳哪些 stage"是**让判断介入路由**，动的是引擎最核心哲学。落地须想清：AI 规划结论如何落成"文件事实"（如写入 Epic 的 skip 声明字段），让门禁仍只读事实、AI 判断只发生在启动规划期而非路由期——保住不撒谎。
- **与相邻候选的层次**：本条是 **stage 级**（整段环节走不走）；WBS 候选是**切片级**（开发阶段内子任务取舍）。两者可共用"可选/条件"机制但作用粒度不同。
- **归位方向**：属工作流引擎路由级进化，风险高于切片级；落地前须用户确认"AI 判断如何不破坏无状态门禁"这一设计边界。关联 [[project_workflow_three_layer_arch]]。

### 进化候选：门禁内自愈循环（gate 内 retry loop）

- **触发**：本次给 `workflow-gate.sh` 挂了审计旁路（auditd 哲学）后，用户提出下一步——门禁 `gate_fail` 时不直接退出，而是自动触发 AI 修复脚本改文件、再判定，循环至 pass 或达最大重试。
- **地基已就位**：每条门禁事件现已带 `git_commit` + `plan_snapshot`（sha256），即回溯所需的「恢复密钥」，可支撑自愈/回滚。
- **落地要点（未做）**：
  1. `MAX_RETRIES=3` 硬上限 + 时间熔断（1h 内 >5 次回溯即 Circuit Breaker），防无限自爆。
  2. 自愈脚本只改「当前 Epic 的子 Plan 文件」，`git checkout` 必带 `-- <epic_path>` 限定，绝不跨 Epic 联动。
  3. 铁律不变：retry loop 里每次判定仍走无状态门禁；事件只 append，不参与路由。
  4. 需用户先定「AI 介入模式」：全自动无人值守 vs 每次改文件前询问。
- **归位方向**：候选升级为通用 workflow 执行器能力或独立 `ai-healer.sh` 骨架；实现前须用户确认介入模式。
