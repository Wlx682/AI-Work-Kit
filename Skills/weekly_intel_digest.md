## 抓取工具：DocShark MCP（可用时优先）

DocShark 是可选增强能力，不是本 Skill 的硬依赖。当前会话能看到 `manage_library`、`search_docs`、`list_libraries`、`get_doc_page` 这类工具时，官方文档站按「先建库、再搜索」使用；看不到这些工具时，直接降级为可用的 Web 搜索/浏览能力，或请用户贴原文链接/正文，不阻塞整条周报流程。

DocShark 工具（若可用）：

| 工具 | 用途 |
|------|------|
| `manage_library` | 给文档站根 URL → 爬取并建 FTS5 索引（首次较慢，之后可复用） |
| `search_docs` | 在已建库里全文搜索（BM25 排序），拿候选 |
| `list_libraries` | 看已索引哪些站，避免重复建库 |
| `get_doc_page` | 取某页完整 Markdown 正文（喂评分/写导语用） |

**适配**：DocShark 强于**结构化文档站**（官方 engineering / docs），弱于 X 推文与零散个人博客单帖。故官方源有 DocShark 就优先用；无 DocShark 或单帖抓不到时，降级 Web 搜索/浏览，仍抓不到则 ⏸ 人工贴链接。**它不产出中文/纳米Work链接**——传播链接仍是人工节点，硬规则不变。

## 执行协议（每期 11 步 · 双卷分离）

```
1. 开场读资产 → follow名单（种子源/源健康参考）+ 评分标准 + 去重清单
2. 候选发现 → 不局限 follow；围绕智能体/AI 编程方向主动搜索，优先找 agent 开发、app 开发新范式、AI 原生 IDE/框架/工具链、端到端产品构建方式、多人/多 agent 协作模式等主题；优先选有机制、有方法、有可复用启发的英文一手内容
3. 抓取     → 官方文档源有 DocShark 时用 list_libraries/manage_library/search_docs/get_doc_page；无 DocShark 时降级 Web 搜索/浏览；X/零散博客抓不到 → ⏸ 交你贴链接/正文
4. 原文解构 → **先抽 `source_map → evidence_map → principle_map → transfer_map` 再写正文**：先还原原文结构，再抽证据/数据/失败模式，再抽通用设计原则，最后判断迁移到 Kit 的边界；无标题时按语义切成 5-8 个块
5. 硬门槛过滤 → 非英文一手 / 纯视频 / 近8周已发 → 淘汰
6. 筛选打分 → 按评分标准算分，输出候选表（分数+理由）交你终审，**每期只选 1 篇最高分**深挖
7. 去重确认 → 与已发去重清单比对，避免重复选题
8. 组装人类卷 → 按「人类卷写作规范」写**纯净正文** `.md`（从标题开始，无提示词/注释/元说明），必须先过「原文完备度门禁」+「原则迁移门禁」，再过「信息完整性自查清单」（正文不含 YAML）
9. 生成炫酷网页 → **走 `@Skills/html_generate.md`**：把纯净正文交给「内容→骨架」选择器（周报深挖长文默认 **B 侧栏文档式**，含前后对比时可选 D）；若正文含公式、数据图、UML/架构图、复杂依赖、研究谱系、伪代码或 API/Schema 表格，按 `@Skills/visual_markdown_toolbox.md` 的平铺选择表确定表达方式 → 产自渲染 `.html`（遵 [[Contexts/规范/炫酷建站规范]]：渐进增强 + 炫酷标准），并**用本地浏览器过自检清单**（各表达引擎渲染成功 / console 无报错 / 正文全可见 / 移动端不溢出）
10. 生成 AI 卷 → 同名 .meta.yaml：skill_run 块，主要从「工作流提炼」段的 transfer_map 萃取 contexts_missing + 源健康自检；附 `source_coverage` 记录覆盖情况；不得反向污染「文章介绍/知识总结」
11. 收尾     → 三个文件存 Plans/情报周报/：`.md`（正文）+ `.html`（Agent 产的炫酷网页，已过自检）+ `.meta.yaml`（AI卷）；**交你把 `.html` 给纳米Work → 它只做「上传 CDN + 返回短链」，不再生成网页**；发布后追加去重清单一行、删 plan
```

**双卷分离**（与 `best-practice-digest` 同源机制）：人类卷(.md)是**技术博客水准的署名文章**给同事读，无 YAML 噪音；AI 卷(.meta.yaml)给脚本读——`feedback-aggregate.py` 优先扫 `Plans/**/*.meta.yaml`。两卷同源，一次萃取。**网页由 Agent 直接产 `.html`**（遵 [[Contexts/规范/炫酷建站规范]]），纳米Work 降级为纯托管。

## 选题侧重（筛选加分项）

候选文章不只看“是不是新”，更看是否揭示开发范式变化。以下主题优先加分，但不作为硬排除：

- **Agent 开发**：agent runtime、tool use、memory、planning/evaluation、multi-agent 协作、human-in-the-loop、agent observability、权限与安全边界。
- **App 开发新范式**：AI 原生 IDE、自然语言到应用、设计到代码、规格驱动开发、agentic coding workflow、应用生成后的维护/测试/部署方式。
- **产品构建方式变化**：从“写代码”转向“定义目标、约束、验收与反馈回路”的实践；团队角色、交付节奏、质量门禁如何变化。
- **可迁移工程方法**：能落到本 Kit 的 Skill、workflow、模板、评审清单或自动化脚本，而不是只展示某个产品发布。

## 人类卷写作规范（技术博客水准 · 每期深挖 1 篇）

发出去的是**署名技术文章**，不是资讯罗列帖。**每期只写 1 篇**——把这一篇讲透，而不是三篇都浅尝。

**深度标准（"透彻"的可操作定义）**：
- **先忠实介绍原文**：作者/来源、背景、核心问题、文章自身结构、为什么值得读——先让读者知道原文在说什么，不急着映射 AI-Work-Kit。
- **再按原文类型总结知识**：研究综述讲谱系、分支、代表工作、指标与争议；工程复盘讲事故链路和边界；产品发布讲能力、治理和适用场景；论文讲问题、方法、实验、局限；文档/规范讲能力面、配置、约束、迁移路径。知识总结必须服务原文自身，不强行套同一种框架。
- **讲机制，不止讲结论**：原文的方法/架构怎么运作、为什么这么设计、解决了什么旧方案的痛点——拆到"读完能自己复述给别人"的程度。
- **覆盖原文而不是抽取灵感**：长文/综述默认目标是“替代粗读原文”，不是写一页导语；不能只抓主线，必须覆盖原文主要章节、代表案例、证据、局限与附录里有用的 benchmark。
- **最后才提炼 AI 工作流启发**：只在收尾段讨论对 Skill / workflow / 模板 / 门禁 / 评审清单的复用价值；先抽象通用原则，再判断 Kit 是否已有承载、是否需要补强、是否必须保留人工决策边界。没有明确落点时允许写“暂不落地”，不要硬凑。

### 原文完备度门禁（写前先抽分析地图，写后逐项核）

**先生成四层分析地图（临时分析，不写进人类卷开头）**：

```yaml
source_map:
  headings: []              # h1/h2/h3 或语义分块
  concepts: []              # 主要概念/系统/论文/工具
  figures_tables_numbers: []# 图、表、公式、benchmark、关键数字
  limitations: []           # 作者明确的 concern / limitation / negative result
evidence_map:
  claims:                   # 作者关键主张，不要只摘结论
    - claim:
      support:              # 案例、实验、数据、benchmark、失败模式、引用来源
      caveat:
  methods:
    - name:
      problem:
      mechanism:
      evidence:
      limitation:
      relation_to_others:   # 与前后方法的差异、递进或冲突
principle_map:
  principles:
    - principle:            # 不绑定原文术语的通用系统设计原则
      source_basis:
      category:             # governance_boundary / persistent_state / failure_taxonomy / regression_evaluation / human_decision_layer / evidence_traceability / long_term_quality / other
transfer_map:
  items:
    - source_basis:         # 原文依据
      principle:            # 通用原则
      kit_current_state:    # Kit 已有承载，避免重复造轮子
      gap_judgment:         # 缺规范/模板/脚本/门禁/评审/仅意识提醒
      migration_boundary:   # 什么不该自动化，哪里需要人工判断
      landing_shape:        # Context / Skill / workflow / checklist / script / 暂不落地
```

**source_map 必抽信息**：

| 必抽信息 | 怎么用 |
|----------|--------|
| 原文 h1/h2/h3 或语义分块 | 决定正文小标题和覆盖表；无标题时人工切 5-8 个主题块 |
| 主要概念/系统/论文/工具名 | 在「知识总结」中至少出现一次，必要时做对照表 |
| 图、表、公式、benchmark、关键数字 | 保留、解释或重画；不能删成一句“有实验支撑” |
| 作者明确的 limitation / concern / negative result | 单独讲边界，避免乐观化转述 |
| 附录/benchmark/参考资料中对读者有用的部分 | 综述类文章要用表格压缩承接，不能直接丢弃 |

**evidence_map 硬门槛**：

- 每个核心 claim 必须绑定证据类型：案例、实验、benchmark、失败模式、作者经验判断或引用研究；证据弱时要明说，不把观点包装成事实。
- 研究综述/benchmark 密集长文至少展开 5 个代表方法到 `problem → mechanism → evidence → limitation → relation_to_others`，不能只列名词。
- 关键数字必须解释口径和意义：数字是什么、比较基线是什么、为什么能支撑原文主张。
- benchmark 不得只罗列“有哪些”，必须说明它测的是哪一层能力，以及它没测到什么。

**按原文类型设深度预算**：

| 原文类型 | 默认目标 | 正文密度下限 |
|----------|----------|--------------|
| 短观点/产品发布（<4k 英文词或 <6 个小节） | 讲清主张、机制、边界 | 约 2500-4500 中文字，随信息量调整 |
| 长工程文/长文档（4k-8k 英文词或 6-12 个小节） | 让读者不读原文也能掌握结构 | 约 5000-8500 中文字，必须有结构表/流程图 |
| 研究综述/论文综述/benchmark 密集长文（>8k 英文词或 >12 个小节） | 替代粗读原文，保留谱系和代表工作 | 约 8000-14000 中文字；若平台限制，先产完整稿，再另做短版 |

**覆盖率硬门槛**：

- 原文所有 h1/h2 必须在「文章介绍」的原文结构或「知识总结」中覆盖；若主动略过，必须在正文或 meta 的 `source_coverage.omitted` 写清理由。
- 重要 h3、代表案例、公式、图表、benchmark 至少覆盖 70%；研究综述类文章里主要论文/系统/方法名要做表格，不允许只挑 3-5 个熟悉的讲。
- 研究综述类正文必须有方法谱系/概念对照/证据与边界三类表达；章节覆盖不等于完成，代表方法未讲到机制层视为未覆盖。
- 「知识总结」默认占全文 60%-75%；「工作流提炼」默认占 15%-25%。如果工作流提炼过早占主篇幅，说明原文还没讲完。
- 生成 `.md` 后反查 source_map：任何未覆盖的主章节都要补写，不能用“篇幅所限”跳过，除非用户明确要求短版。

### 原则迁移门禁（防止功能照搬和空洞建议）

工作流提炼的目标不是把原文中的功能、框架或术语迁移到 Kit，而是抽取可复用的系统设计原则，并判断这些原则在 Kit 中是否已有承载、是否需要补强、是否应保留人工决策边界。

**原则优先级**：

1. 原则内化：能指导多个 workflow 的系统设计原则。
2. 门禁补强：能减少错误、回归、权限越界或长期质量退化的检查点。
3. 证据链增强：能让决策更可审计、更可复盘。
4. 模板/字段补充：只在确有重复场景时落地。
5. 功能迁移：最低优先级，禁止因为原文提到某功能就建议 Kit 增加同名功能。

**transfer_map 每条建议必须回答**：

| 字段 | 说明 |
|---|---|
| 原文依据 | 原文中的主张、案例、数据、失败模式或作者 caveat |
| 通用原则 | 不依赖具体文章主题的系统设计原则 |
| Kit 现状 | Kit 已有机制，避免重复造轮子 |
| 缺口判断 | 缺的是规范、模板、脚本、门禁、评审，还是只是意识提醒 |
| 迁移边界 | 什么情况下不该自动化，哪里需要人工判断 |
| 落地形态 | Context / Skill / workflow / checklist / script / 暂不落地 |

可复用原则分类可包括但不限于：可变/不可变边界、持久化状态与审计轨迹、失败模式建模、回归评估、证据可追溯、人类判断上移、长期质量优先。分类只帮助抽象，不要求每篇都硬凑。

**行文结构**（三段递进，每段用 `####` 子标题分隔，不要用加粗代替标题）：
1. **#### 文章介绍** —— 这篇文章是什么：作者/来源、写作背景、核心问题、原文结构、为什么值得读。**本段禁止强行映射 AI-Work-Kit / Skill / Contexts / workflow / gate。**
2. **#### 知识总结** —— 按原文自己的形态展开知识，而不是套固定模板。可以根据文章类型自由组织小标题、图示和表格；研究综述允许讲多条谱系，工程文允许讲链路，产品文允许讲能力边界。**本段仍以原文为主，除非原文直接讨论相关概念，不要主动映射 AI-Work-Kit。长综述必须保留“原文地图/方法谱系/代表工作/benchmark 或局限表”这类结构化表达，并体现证据与数据、概念与方法间的对比分析。**
3. **#### 工作流提炼** —— 最后再提炼对 AI 工作流 / AI-Work-Kit 的启发：从“功能迁移”转向“原则内化”，先讲通用设计原则，再讲 Kit 现状、缺口、边界和落地形态；哪些只是观察，不必落地。`contexts_missing` 主要从本段萃取，避免污染前两段。

**铁律**：
- **正文纯净，网页是 Agent 另产的 `.html`**：人类卷 `.md` 是**纯净正文**（从文章标题开始，不含任何提示词/注释/元说明）；网页由 Agent 依 [[Contexts/规范/炫酷建站规范]] 直接产同名 `.html` 成品（不再写 `.prompt.md` 生成指令）。正文里**不写对文章本身的要求/元说明**（如「面向技术同学…」「本文图示用大白话」）——那是给写作者的规范，不是给读者的内容。
- **前两段不被 Kit 约束**：`文章介绍` 与 `知识总结` 只服务原文理解，不为了反哺 Kit 而改写原文主线；只有 `工作流提炼` 段允许主动讨论 AI-Work-Kit / Skill / Contexts / workflow / gate。
- **工作流提炼不照搬功能**：禁止因为原文出现某个机制，就直接建议 Kit 增加同名功能；必须先抽象原则，再判断已有承载、真实缺口和迁移边界。
- 说明性小标题（如「为什么 harness 会过期」），不用装饰性标题。
- 专业、中性笔调；**禁装饰图标/emoji**，**禁娱乐化比喻、段子、网络梗**。
- 正文保持技术博客的专业表达；网页视觉由 Agent 在 `.html` 里实现（遵炫酷建站规范），做成有科技感和产品感的专题页，而不是普通 Markdown 皮肤。
- **复杂表达走图文工具箱**：不要把公式、论文图、系统框架、benchmark 曲线、taxonomy 强行压成简单流程图。人类卷 `.md` 与网页 `.html` 的图文表达按 `@Skills/visual_markdown_toolbox.md` 的平铺选择表处理。
- 双视角（技术看点/通用看点）**融入行文本身**，不贴标签、不在正文里声明"这是给谁看的"。
- 不含任何 YAML/机器块。

#### 每期产两个文件：纯净正文 + 炫酷网页成品

| 文件 | 内容 |
|------|------|
| `YYYY-MM-DD-第N期.md` | **纯净正文**，从文章标题开始，无提示词/注释/元说明 |
| `YYYY-MM-DD-第N期.html` | **Agent 直接产的炫酷自渲染网页成品**，遵 [[Contexts/规范/炫酷建站规范]]，过浏览器自检 |

**网页由 Agent 产 `.html`，纳米Work 只托管**：完整建站标准、技术基线、浏览器自检清单、交接话术，全部见 [[Contexts/规范/炫酷建站规范]]；布局骨架见 `@Skills/html_generate.md`，复杂图文表达见 `@Skills/visual_markdown_toolbox.md`。要点复述：

- 第一屏就不能像「白底 Markdown」——大标题 + 摘要 + 来源/日期/标签 + 与主题相关的代码生成视觉主画面；深色 AI 开发者工具风。
- **表达引擎页面内自渲染**：具体工具选择交给 `@Skills/visual_markdown_toolbox.md`，所有引擎都要渐进增强，JS 失败时正文仍可读。
- 滚动渐显等动效**渐进增强**：默认可见、JS 正常才隐藏渐显 + setTimeout 兜底，正文可读性不赌 JS。
- **关键数字主角化**：量化结论（如 `p50↓~60%`）用特大字（`clamp(34px..)`）独占卡、成组、count-up 入场，别挤角落；核心论点也数字化/公式化成锚点卡。
- **动态适配硬指标**：卡片容器用 `auto-fit minmax` 流式栅格随视口 3→2→1 列自动重排，排版全程 `clamp()`，不靠单一断点硬切。
- 产完**用本地浏览器过自检**：本期用到的 Mermaid/MathJax/KaTeX/Vega/Graphviz/markmap/SVG 等表达块均渲染成功、无 raw text leak；console 0 error、section 全可见、**375/768/1440 三宽度无横溢出**；清理自检残留。
- 交接纳米Work 的话术只要一句：「把这个 `.html` 传 CDN、返回短链，不改内容」。

#### 图文表达路由

若原文有公式、数据图、UML/架构图、复杂依赖、研究谱系、伪代码或 API/Schema 表格，调用 `@Skills/visual_markdown_toolbox.md`。该 Skill 是平铺路由：按内容块选择对应表达方式，避免 weekly 自身承载工具细节。

**进化萃取 = 复用已有 `skill_run`，不新造 schema**：读某篇文章暴露的「Kit 本该有却缺的能力」→ 直接写进 `contexts_missing`（语义即外部方案的 `capability_gap`）。这样自动流入 `feedback-aggregate.py → vault-evolve.py` 月度报告的「补全候选」池（同字符串累计 ≥2 触发），作为下月新 Contexts/Skill 的**外部需求证据**。是否真的沉淀由你月度 review 拍板，Skill 不自作主张写 Contexts。

AI 卷 `.meta.yaml` 样例：

```yaml
skill_run:
  skill: weekly-intel-digest
  date: 2026-07-01          # 第 N 期
  contexts_used:
    - path: Contexts/情报源/筛选评分标准.md
      utility: high
      reason: 按加权分选出 Top3
  contexts_missing:          # ← capability_gap：读入选文章暴露的 Kit 能力缺口，通常至少一项；确实无缺口则填 [] 并在 notes 说明
    - "subagents 配置与并行任务拆分"
  contexts_stale: []
  source_coverage:
    covered_headings:
      - "原文 h1/h2 或语义块标题"
    omitted: []              # 若省略原文主章节，必须写 reason
    coverage_notes: "主要方法、公式、benchmark、局限均已覆盖"
  notes: |                   # 源健康自检写这里
    source_stale_warning: Cat Wu 连续 3 期无入选，建议人工复核 follow 名单
```

## 产物位置

- **人类卷正文（临时）**：`Plans/情报周报/YYYY-MM-DD-第N期.md`，纯净正文，发完即删。
- **炫酷网页（临时）**：同目录同名 `.html`，Agent 直接产、过浏览器自检，交纳米Work 托管，发完即删。
- **AI 卷（临时）**：同目录同名 `.meta.yaml`，喂 `feedback-aggregate`。
- **长期沉淀**：去重清单追加、follow 名单增补淘汰、建站规范/模板迭代 → `Contexts/情报源/`、`Contexts/规范/`。

## 硬规则

1. 进入人类卷的原文**必须英文一手**；对外传播的网页由 **Agent 产 `.html` 成品 → 纳米Work 上传 CDN 出短链**（遵 [[Contexts/规范/炫酷建站规范]]），正文与网页缺一不发。
2. 不接受小红书/抖音/纯视频独立传播。
3. 面向技术为主、产品设计运营也参与 → 每篇必含「技术看点 + 通用看点」双视角（融入行文，非贴标签）。
4. **人类卷是技术博客水准的署名文章，不含机器块**：正文按写作规范三段结构（文章介绍/知识总结/工作流提炼），`skill_run`/YAML 不得出现在 .md 里。
5. **进化萃取强制**：每期 `.meta.yaml` 必须包含 `contexts_missing` 字段；通常至少填一项（读入选文章暴露的 Kit 能力缺口），确实无缺口则写 `contexts_missing: []` 并在 `notes` 写明理由，不得省略此字段。
6. **源健康自检**：follow 名单只做种子与巡检，不限制候选来源；某 follow 源连续 3 期无入选文章，`.meta.yaml` 的 `notes` 必须输出 `source_stale_warning`，提醒人工复核名单。判据来自 [[Contexts/情报源/已发去重清单]] 的历史入选记录。
7. 写 Contexts/情报源/ 下资产前，若非「增补去重清单/follow名单」这类既定动作，须用户确认（遵 CLAUDE.md 规则 2）。

## 反馈回路（遵 CLAUDE.md 规则 5）

任务结束把 `skill_run` 写入**独立 `.meta.yaml`**（人类卷 .md 不含 YAML）——一次输出双处使用：对外交作业，对内喂 `feedback-aggregate → vault-evolve` 进化链。`contexts_missing` 即外部需求证据（学到的先进理念→Kit 缺口）。若无独立 plan，不再把完整过程小票追加到孤立反馈；未归位缺口写 `## 待整理`，已归位结论只写 `## 已归位` 摘要。
