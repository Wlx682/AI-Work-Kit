# 变更影响分析 Skill

## 触发条件（口语前置）

当用户说以下任一时执行 —— 口语化说法优先匹配，PM 日常对话中的「改东西」类发问直接走本 Skill：

- **口语优先**：「**需求变了**」「**改个东西**」「**Scope 调整**」「**临时改一下**」「**这个不做了 / 加一个**」「**PRD 又改了**」
- **正式词**：「需求变更」「改 scope」「变更影响」「变更影响分析」
- `/change-impact-analysis` 命令

**不响应（让位给其他 Skill）**：

- 「开发流程审计 / 检查 Epic 进度」→ `dev-lifecycle-audit-assistant`
- 「重新做需求分析（全新需求）」→ `requirement-analyst`
- 「重新设计架构（方案级重写）」→ `architecture-design-assistant`

> 需求变了、开发做到一半：通过 Obsidian 双向链接反向查找受影响 plan，输出变更影响报告。

## 知识库

- 真理源：`Plans/需求分析/xxx.md`
- 扫描：`Plans/技术方案/`、`Plans/功能开发/`、`Plans/自动化测试/`、`Plans/部署/`

## 执行步骤

1. 确认变更点：用户描述 + 读需求 plan 当前内容。
2. **反向链接查找**（grep + 双链）：
   - 依赖该需求的 **技术方案** plan
   - 进行中的 **功能开发** plan / 子任务
   - **自动化测试**、**部署** plan
3. 输出 **变更影响报告**（Markdown，可写入需求 plan 末尾或 `Contexts/决策/`）：

| 受影响 plan | 阶段 | 影响类型 | 建议动作 |
|-------------|------|----------|----------|
| 【】 | 架构/开发/测试 | 重写/微调/仅文档 | 【】 |

4. 将受影响 plan 的 `status` 更新为 **`pending-change`**（须用户确认后写入）。
5. 若影响代码：列出**可能重写的模块路径**（在当前代码库搜索）。
6. 若影响测试：列出需重写的 UT/IT ID。

## 后续

- P0 变更 → 先更新需求 plan → `/architecture-design-assistant` 复审方案
- 小改 → 直接 `/resume` 对应子任务

## 上下文汇报

```
📌 当前阶段：[变更影响分析] | 受影响 plan：N 个 | 建议：【回退到架构/继续开发】 | 中断：/resume plan=...
```

## 触发示例

```
/change-impact-analysis 需求=Plans/需求分析/2026-06-20-支付.md，变更=取消灰度，直接全量
```
