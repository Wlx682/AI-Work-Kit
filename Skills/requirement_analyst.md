# 需求分析助手 Skill

> 在开发前，系统性地发现 PRD 中的逻辑矛盾、交互冲突、需求遗漏和边界不清，将模糊需求转化为可执行、可验收的明确产物。

## 触发时机

当用户提出以下意图时自动激活：

- 「分析需求」「看一下这个 PRD」「做需求评审」
- 「这个需求有什么问题」「帮我 push 产品」「感觉需求有遗漏」
- 或其他明确希望审视、补全、质疑 PRD 质量的场景

> ⚠️ **即便需求质量很差**，也必须先完成本 Skill 的分析，再进入后续的开发 / 架构设计阶段。

## 知识库与模板

- **方法论唯一源**：`Contexts/需求分析/需求分析规范.md`（整体思想/事件驱动 / 三层面 / 事件建模+四图 / 逐类检查项 / 分卷输出 / 避坑——改方法看此文）
- 示例模式：`Contexts/需求分析/示例-创建自动化任务-PRD问题模式.md`
- 门禁字段：`Contexts/需求分析/需求分析产出标准.md`
- 输出模板：`Templates/需求分析模板.md`（推荐 `需求分析-带验收标准模板.md`）
- 分析记录：所有分析结果存档于 `Plans/需求分析/`，命名 `YYYY-MM-DD-模块名.md`

## 核心理念：先按"三层面"组织，再挑问题

拿到任何需求，**不要一上来就画界面或挑错**，先按 Why → What → How 的顺序对齐：

| 层面 | 回答 | 产出 |
|------|------|------|
| **战略层（Why）** | 解决什么痛点？不做会怎样？ | 一句话目标 + 量化指标 |
| **范围层（What）** | 做哪些、明确不做哪些？ | 功能清单 + 排除项 |
| **细节层（How）** | 逻辑、流程、字段、边界、AC | 流程图、数据字典、AC 表、异常矩阵 |

> 先对齐目标，再看细节。跳过 Why 直接讲 How，评审会变成"我觉得这个没必要做"的争论。

## 五种表达手段（不能只用文字）

分析过程中组合使用，并落到产出文档：

1. **用户故事 + 场景代入**：`作为……我想要……以便……` + 用户旅程地图。
2. **原型/交互稿**：低保真线框，标注热区与跳转流向。
3. **事件建模 + 四图**：先抓业务事件 → 画 `命令→聚合→事件` 触发链 → 四步法产出 ER/状态机/时序/决策流程图；方法与 Mermaid 模板见 `需求分析规范.md` §三。**能用图讲清就别堆表格。**
4. **数据字典**：字段 / 类型 / 必填 / 范围 / 默认值 / 来源 / 说明。
5. **AC + 实例化**：Given-When-Then，每条可测、且写**反例**。

## 分析流程（八步）

1. **获取输入**：索要 PRD 全文或飞书链接（链接仅当次使用，不存档）；口头需求先整理成文字草稿。
2. **加载规范、清单与模板**：先读 `需求分析规范.md`，再读检查清单与输出模板，确保覆盖全面。
3. **三层面分析**：按 Why / What / How 拆解，先对齐战略与范围，再展开细节。
4. **事件驱动建模（完成凭证·阻断关卡）**：先抓**业务事件**（过去式）→ 画 `命令 → 聚合/不变条件 → 事件` 触发链 → 再用四步法产出 ER/状态机/时序/决策流程四图，方法与模板见 `需求分析规范.md` §三。
   - **事件是脊柱**：状态机每条迁移必须挂一个事件；遗漏检查 = 事件链闭环（哪个事件无命令触发？哪个命令无结果事件？）。
   - 🚧 **阻断规则**：事件链 + 四图（或经判断明确不适用的图须注明理由）未完成前，**禁止进入第 5、6 步**。画图是分析的"完成凭证"，图不全分析不往下走——防止为省 token 跳过画图直接填表。
5. **五块核心问题输出**（详见下一节）+ 按需用五种手段产出可视化材料。这五块连同数据字典/边界/AC 属 **AI 工作底稿**，存档时置于 `<!-- AI工作底稿 ↓ -->` 分隔符之后。
6. **用户旅程闭环图**：文字或 mermaid，明确标记「PRD 已覆盖 / PRD 缺失」环节。
7. **验收标准**：产出可测试的 AC 表（Given-When-Then），作为后续测试真理源。
8. **待产品确认清单**：分「逻辑交互」与「**需求遗漏**」两类；P0 级遗漏与 P0 级逻辑矛盾**同等阻塞开发**。
9. **人类卷四件套**（置于正文最前，软约束 ≤3 页）：A 用户使用地图（角色→目标）、B 关键业务时刻（事件时间线）、C 业务规则（Do/Don't）、**D 需求问题清单**（把底稿 §六/七/八的不理解/矛盾/遗漏浓缩成产品视角一句话表，标 P0/P1 与三类标签 🤔不理解/⚔️矛盾/🕳️遗漏；明细仍留底稿）。**人类校验门禁**：删掉底稿后没读过 PRD 的产品须 3 分钟答清「先点哪→解决什么场景→能做/不能做→**有哪些要我拍板**」，D 块缺失或答不清则重写人类卷。分卷规范见 `Templates/模板约定.md`。

完成后 **存档** → `Plans/需求分析/YYYY-MM-DD-模块名.md`（人类卷在前 + AI 工作底稿在后），该文件即本次需求分析的全流程**真理源**。

## 必须输出的五块内容

无论 PRD 篇幅多短，以下五张表都必须完整产出：

### ① 逻辑问题表
PRD 中明确写出但存在矛盾、未定义分支、条件缺失的内容。  
例：A 流程要求跳转新页面，后文又变成弹窗，未说明区分条件。

### ② 交互冲突表
涉及交互行为的矛盾或缺口，包括入口、空态、创建/编辑状态、Tab 切换、加载态等。可与设计稿对照，快速发现 UI 状态缺失。

### ③ 整体遗漏表
逐类扫描 PRD 全文，找出功能上线必需但 PRD 完全未提及的内容。每条必须写明：

- **缺失内容**
- **若产品不补时开发会怎么猜**（风险）
- **严重程度**

检查类别：

- 用户旅程的完整闭环（正常 + 异常）
- 接口定义与字段说明
- 删除 / 启用停用 / 数据回收等生命周期
- 数据为空、弱网、权限、并发等边界
- 埋点与数据统计需求
- 验收标准（AC）本身是否被遗漏

某类 PRD 已覆盖时，**明确标注「本类 PRD 已覆盖」**。

### ④ 边界情况清单
列出所有需要处理的极限、异常和特殊场景：空数据、极长文本、弱网、无权限、多端并发、重复提交等。详见 `Templates/需求分析-带验收标准模板.md` §四。

### ⑤ 异常流程矩阵
表格列出：**异常触发条件 → 用户看到什么反馈 → 系统做什么行为**。  
确保每个异常都有明确的产品决策，而不是靠开发自行猜测。详见同模板 §五。

## 遗漏分析专项要求（核心能力）

不只挑错别字，而是回答关键问题：**"要完整把这个功能做上线，PRD 还缺哪几段？"**

- 对照检查清单 §3.1–3.6 逐类扫描
- 每条遗漏给出明确的补全建议或至少 **2–3 个可选方案**

## 与后续阶段衔接

| 分析结论 | 后续动作 |
|---------|---------|
| P0 问题（含关键遗漏）未闭环 | 继续 `/requirement-analyst`，或用户明确「接受风险」并记录在案 |
| 所有问题已闭环 | 进入 `/architecture-design-assistant` 或 `/feature-dev-assistant`（纯 UI 改动可跳过架构） |

## 评审确认 · 角色沟通 · 避坑

以上三项的完整规则见 `Contexts/需求分析/需求分析规范.md`（§2.4 评审确认 / §六 角色沟通 / §七 避坑）。要点速记：**讲完让开发复述+测试列 3~5 测试点才算通过**；**问题聚焦最致命 3~5 个，>10 条多为过度解读**。

## 输出原则

- **挑剔但建设性**：每条问题都附补全建议或方案选项
- **清晰分离**：遗漏项必须标明「PRD 全文未提及」，不与逻辑矛盾混为一谈
- **结构化呈现**：与产品沟通时，按「**逻辑 · 交互 · 遗漏**」三大块归类，提高沟通效率

## 续做机制

产品补充信息或 PRD 更新后，基于已有 Plan 继续：

1. 读取之前的分析 Plan
2. 对照产品回复或新版本 PRD
3. 更新三类问题状态（已解决 / 待确认 / 新增）
4. 重新评估是否可以进入开发

## 触发示例

```
/requirement-analyst 新分析，PRD=【飞书链接】，模块=创建自动化任务

/requirement-analyst 续做，plan=需求分析/2026-06-24-创建自动化任务.md，进度=产品已补充删除流程，请更新遗漏表
```

## 输出反馈（全量强制 · 硬门槛）

> 完成存档后，**必须**在 plan 文件**末尾**追加一节 `## 反馈（skill_run）`，节内嵌 fenced yaml 代码块；缺则 `plan-gate-check.sh` 视为任务未完成。
> 协议全文：[[Contexts/决策/Skill反馈协议]]。

### 完整写入示例（直接追加到 plan 末尾）

````markdown
## 反馈（skill_run）

```yaml
skill_run:
  skill: requirement-analyst
  plan: Plans/需求分析/2026-06-24-创建自动化任务.md
  date: 2026-06-24
  contexts_used:
    - path: Contexts/需求分析/需求分析规范.md
      utility: high
      reason: "对照 §五逐类检查项扫遗漏类别"
    - path: Contexts/需求分析/示例-创建自动化任务-PRD问题模式.md
      utility: high
      reason: "对照已知问题模式定位本次 PRD 漏洞"
  contexts_missing:
    - "【若本次发现 PRD 涉及但 Contexts 没覆盖的主题，列 1 句话；无则删本字段】"
  contexts_stale:
    - path: 【若发现 Contexts 与代码/现网脱钩的文件路径；无则删本字段】
      reason: 【脱钩证据，1 句话】
```
````

### 字段规则速查

- `utility` 二选一：`high`（必给一句话 `reason`）/ `not-needed`（说明"看了但没用上"或"默认列表里但本次没读"）
- 禁止 `medium` / `low` / `unknown` 等其他取值
- `contexts_used[].path` 必须是仓库内真实路径
- `contexts_missing` 与 `contexts_stale` 可省略，但**积极填写**会让月度聚合产出更高质量的 Vault 优化建议

### 写入位置与校验

- 有 plan（本 Skill 总是有）：追加 `## 反馈（skill_run）` 节到 `Plans/需求分析/YYYY-MM-DD-xxx.md` **文件末尾**
- 写完跑：`bash scripts/plan-gate-check.sh Plans/需求分析/YYYY-MM-DD-xxx.md`，校验通过才算任务完成
