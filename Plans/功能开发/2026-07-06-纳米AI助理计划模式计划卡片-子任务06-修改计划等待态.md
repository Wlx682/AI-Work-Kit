# 子任务06：修改计划 + 等待输入意见态

**parent**：[[2026-07-06-纳米AI助理计划模式计划卡片]]
**覆盖 AC**：AC3, AC4, AC5
**依赖**：T05（交互链 + PlanCard extension）、T01（answerPlan feedback）

## 输入
- 方案 §5.4「修改意见发送时序（已确认）」：点修改计划 → 切 modifying + **复用现有输入框**聚焦；提交时把输入框 prompt **直接作为 `feedback` 调 `answerPlan(approve:false, feedback:prompt)`**，**不插用户气泡、不走 chat.send**；服务端重出新 ExitPlanMode → T03 识别链渲染新卡片。
- 需求 §C/D2：等待态无超时/无取消入口；多次修改端不限制（P0-2 客户端不关心）；反悔表达（"按原计划来"）由 AI 重出同款卡片（AC5，端无需特判）。
- 输入框能力：`Share/UI/InputBar/`（图片/文件/语音转文字，复用不裁剪）。

## 步骤
1. `+PlanCard` 实现 `handlePlanCardModify(cellVm:)`：
   - `guard cellVm.canApprove`。
   - 切 `updatePlanCardState(.modifying)`（按钮移除、卡下显示「等待输入意见」）。
   - 记录"当前处于修改态、待接管下一条输入"的上下文（如 `pendingModifyToolCallId = cellVm.toolCallId`），聚焦输入框、弹键盘。
2. **接管发送**：在聊天发送入口（用户点发送处）判断：若 `pendingModifyToolCallId != nil` → 走修改分支而非普通 chat.send：
   - 取输入框文本(+附件)作为 feedback；显示「提交修改意见…」（`updatePlanCardState` 文案态或独立标记）。
   - 调 `answerPlan(approve:false, feedback:文本)`；清 `pendingModifyToolCallId`。
   - **不插用户气泡**（区别于普通 send）。
   - 失败：Toast + 允许重试（保持修改态）。
3. 新卡片到达（T03 的 insertPlanCard）自动把旧卡翻 disabled、新卡 pending，天然"回到闸门"（AC4）。
4. AC5：反悔文本同样作为 feedback 透传，AI 重出卡片，端无特判——确认代码路径对任意 feedback 文本一致处理。

## 输出
- `handlePlanCardModify` + 发送入口的修改态接管分支 + Cell onModify 绑定。

## 验收
- [ ] `xcodebuild build` 通过。
- [ ] AC3：点修改计划 → 按钮移除、显示「等待输入意见」、输入框聚焦弹键盘。
- [ ] AC4：提交意见 → 显示「提交修改意见…」→ 发 answerPlan(approve:false,feedback) → 新卡片到达带两按钮、旧卡失效。
- [ ] AC5：输入"不用改了按原计划来"同样透传 feedback，重出卡片可再点开始执行。
- [ ] 修改态发送**不插用户气泡**、不走 chat.send。
- [ ] 多次修改不被端拦截。

## 修订（2026-07-07）：进行态改为「卡片下方独立胶囊」

**背景**：对稿 Figma 37886-7336（开始执行）/ 37886-7602（等待输入意见）/ 37886-7468（提交修改意见）后发现——三个进行态不是「卡内替换文案」，而是**计划卡片下方一张独立状态胶囊**（描边圆角矩形，与卡片间距 16pt）：

| 态 | 胶囊文案 | 四点动画 | Figma |
|----|----------|----------|-------|
| executing | 开始执行 | 有 | 37886-7336 |
| modifying | 等待输入意见 | 无（待用户输入） | 37886-7602 |
| submitting | 提交修改意见 | 有 | 37886-7468 |

**改动**：
- `NMPlanCardApprovalState` 拆 `modifying`（等待输入意见）/ 新增 `submitting`（提交修改意见）；进行态卡内只留正文，状态挂卡下独立胶囊。
- `NMChatPlanCardCell`：新增 `pillContainer`（描边胶囊）+ `pillStatusLabel` + 四点 Lottie（复用 `message_loading_animate`）；pending/disabled 仍卡内按钮。
- `NMChatPlanCardCellVM`：高度拆 `cardBottomAreaHeight`（卡内）+ `detachedPillHeight`（卡下胶囊，含 16 间距 + 53 高）。
- `submitPlanModifyFeedback`：发送时本地切 `.submitting`（等待输入意见 → 提交修改意见 + 四点）。

> ⚠️ **本节方案已被下方「二次修订」推翻**：不再在计划卡片内画独立胶囊，改为复用对话流唯一的 loading 胶囊。度量表仍有效（loading 胶囊尺寸一致）。

## 二次修订（2026-07-07）：复用唯一 loading 胶囊承载进行态（推翻上一节 pillContainer 方案）

**背景（用户反馈）**：
1. 三个进行态胶囊与对话流本来就有的 loading 胶囊「是同一个东西」，不该另造 `pillContainer`。
2. 对话中**任意时刻只应有一张 loading**：之前的 loading 要被替换，不能与状态胶囊同时在页面上。
3. 不要把「计划」业务语义耦合进通用 `NMChatLoadingCellVM`——它本就支持文案配置，只需补「是否展示四点」的通用开关。

**最终改动**：
- **通用化 `NMChatLoadingCellVM`**（无 "plan" 字样）：新增通用属性 `fixedText`（固定文案覆盖分时文案）、`showsDots`（四点开关）、`pinsVisible`（常驻不收起）；配套 `setFixedStatus(text:showsDots:pinned:)` / `clearFixedStatus()`。`finishLoading`/`calculateHeight`/`shouldShowStatusText`/`statusText`/`contentHash` 全部尊重这三个通用属性。
- **`NMChatLoadingCell`**：`fixedText` 非空时渲染固定文案；`showsDots=false` 时隐藏四点并把气泡右缘收紧到文案（新增 `bubbleTrailingToLabel` 约束）。
- **`NMChatViewModel.applyPlanProgressToLoading`**：`.updatePlanCardState` 进行态映射到**本轮唯一 loading 胶囊**——executing=「开始执行」+四点、submitting=「提交修改意见」+四点、modifying=「等待输入意见」无四点且常驻；pending/disabled/consumed 清除固定文案恢复普通 loading。`currentRoundLoadingCell()` 取本轮那一张。
- **`NMChatPlanCardCell` 回退**：删掉 `pillContainer` 那套，进行态卡内仅留正文（按钮隐藏）；`NMChatPlanCardCellVM` 删 `detachedPillHeight`/pill 常量，高度回到「卡内区」单一来源。
- 计划卡片本体在正文出来时被替换的诉求 → 由「唯一 loading 承载 + 正文事件走既有 `insertFinalTextCellEvictingProcessNodes`」自然满足，无需单独驱逐计划卡。

**关键不变量**：全程只有一张 loading cell；状态胶囊 = 这张 loading 换文案，不新增 cell。
