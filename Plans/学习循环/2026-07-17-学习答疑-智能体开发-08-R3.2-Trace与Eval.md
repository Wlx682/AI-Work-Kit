# 学习答疑：R3.2 Trace 与 Eval

## 五、学习过程

| 时间 | 问题 | 用户回答 | 结论 |
|------|------|----------|------|
| 2026-07-17 | checkpoint、trace、eval 分别是什么？ | checkpoint 是 work 的当前存档；trace 是整个执行记录；eval 评测智能体执行是否符合预期。 | ✅ 已掌握三个职责边界；补充：一个 thread 会保留多个 checkpoint 快照。 |
| 2026-07-22 | trace 写入失败时如何处理？ | 默认成功但告警。 | ✅ 业务结果和观测结果分离；仅审计强制场景才将 trace 失败升级为业务失败。 |

## 六、问题与澄清

| 问题 | 澄清 |
|------|------|
| checkpoint 是不是只有一个？ | 不是。一次图运行常在多个 super-step 后各存一个 checkpoint；它们服务于恢复和查看状态历史。 |
| trace 保存什么？ | 保存项目自己的稳定事实：任务、run ID、终态、错误和 `RunEvent` 序列，而不是框架私有对象。 |
| eval 要评估什么？ | 本轮只评估编排行为契约：是否正确完成、是否重规划、失败是否收口和落盘；不评估真实模型文案质量。 |
| trace 写入失败会不会改变任务结果？ | 默认不会。任务已成功就保持成功，在结果中留下可观测性告警；本项目不属于审计必须落盘的强制场景。 |

## 七、下一步设计题

已完成。设计结论已转入下一阶段：`RunResult` 增加默认空的 `warnings`，trace 写入失败只追加 `trace_persist_failed: <reason>`，不改变 `succeeded`。
