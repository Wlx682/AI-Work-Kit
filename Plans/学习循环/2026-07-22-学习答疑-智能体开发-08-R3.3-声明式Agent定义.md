# 学习答疑：R3.3 声明式 Agent 定义

## 五、学习过程

| 时间 | 问题 | 用户回答 | 结论 |
|------|------|----------|------|
| 2026-07-22 | 定义允许 shell、但安全层禁止时谁优先？ | safety 为准，安全第一。 | ✅ 配置不能扩大运行时权限；有效权限为 `definition_allowlist ∩ safety_allowlist`。 |
| 2026-07-22 | 哪些字段属于 `orchestrator.yaml`？ | Orchestrator 不该有角色；角色、工具和验收属于智能体。 | ✅ 纠正命名：runtime/编排与 Agent 定义必须分离。 |

## 六、问题与澄清

| 问题 | 澄清 |
|------|------|
| 声明定义的价值是什么？ | 它是可审阅、可版本化的策略输入，而不是安全机制本身。 |
| 为什么还需要 loader？ | loader 将不可信 YAML 转为受 schema 限制的对象，拒绝未知工具、缺字段和错误格式。 |
| 为什么不叫 `orchestrator.yaml`？ | Orchestrator 是加载定义、运行图和收口错误的机制；它不拥有 Agent 的角色或业务目标。 |

## 七、设计题

已完成。第一份声明应是独立的 Agent 定义，而不是 `orchestrator.yaml`：角色名、目标、工具 allowlist 和输出验收归 Agent；LangGraph 图的重规划回环仍留在 runtime 代码中。
