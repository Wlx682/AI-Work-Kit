# 学习复盘：R3.3 声明式 Agent 定义

## 十二、复盘

| 维度 | 内容 |
|------|------|
| 已掌握 | Agent Definition 是经校验的策略对象；角色定义策略，capability 提供共享本事，tool 是外部行动接口。 |
| 关键纠偏 | Orchestrator 不是 Agent；`orchestrator.yaml` 是错误命名。Team Graph 的控制流应由 LangGraph 代码承担，不塞进 JSON。 |
| 已实现 | 单智能体和四个 Team role 均加载 JSON + Markdown 定义；allowlist 与安全裁决分层；Team 已迁移为 LangGraph Team Graph。 |
| Team 结论 | 图的条件边决定路由与重试；角色方法只做业务能力调用；角色交接作为 `RunEvent` trace 证据保留日志标签，但不再是 `MessageBus` 控制命令。 |
| 验证证据 | 15 项离线测试通过，覆盖安全直达、风险调整、Reviewer 打回重试、重试上限、checkpoint 与 trace 写入失败仅告警。 |

## 十四、Team 改造交接

下一轮实现以 [R3 生产化计划](../2026-07-17-学习-智能体开发-08-R3生产化.md) 的「Team Graph 改造交接契约」为准：角色定义保持 JSON + Markdown，capability 继续是共享 Python 实现，控制流迁入 LangGraph 代码图，安全和 trace/eval 契约不得回退。

原 `Team.run()` 的直接调用和 `MessageBus` 留痕已完成迁移：共享图状态与结构化 trace 驱动协作，而不是把控制流重写成配置 DSL。

## 十三、下一步建议

R3.3 收口后，下一轮聚焦 Team Graph 的生产化取舍：哪些节点可并发、哪些失败应重试、哪些任务需要人工审批或 durable checkpoint；角色声明与 capability 保持现有边界。
