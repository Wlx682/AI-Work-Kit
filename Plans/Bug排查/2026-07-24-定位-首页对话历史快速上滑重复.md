## 一、输入

- 来源：复现阶段确认的“返回刷新 + 快速上拉”相邻请求链。
- 范围：`viewWillAppear` 静默刷新、`NMTaskRecordListVM.loadMore()` 延迟重放与 MJRefresh footer 状态切换。
- 非目标：修改 `sessions.history-page` 数据、排序、游标或追加策略。

## 二、阶段产出

- [x] 必要机制：`pendingLoadMoreAfterCurrentRequest` 用于 SWR 缓存帧已上屏、网络最终帧仍在途时保存一次上拉；它保证分页使用网络最终帧确定的最新 cursor，不能整体删除。
- [x] 根因：首屏结束时 VM 在当前主线程周期同步重放分页，但 `configWithResult` 内 `MJRefresh.endRefreshing()` 要到下一主线程周期才回 idle，形成“分页已开始、footer 随后才 idle”的错拍。
- [x] 污染窗口：footer 回 idle 后继续上滑会在分页请求在途时再次进入 `loadMore()`；旧逻辑只看 `isRequesting`，会再次设置 pending，而分页完成路径不消费它，使旧上拉残留到后续首屏刷新。
- [x] 回归原因：`235fddff` 整体删除 pending，并在刷新在途时主动 `endRefreshing`，会让 footer 更早回 idle、在同一滑动阶段反复触发，因此问题变为稳定复现。
- [x] 排除项：问题不要求服务端返回重复数据，也不是会话 ID 去重缺失；核心是首屏刷新、分页请求与 MJRefresh 状态的时序。
- [x] 引入时间：pending 由 `d708b2fc`（2026-06-23 17:26）用于修复首屏在途上拉丢失；`871a7da9`（2026-07-07 22:14）接入 SWR 双帧后，缓存帧可交互但请求仍在途，使错拍窗口稳定出现。
- [x] 修复边界：保留首屏 pending；仅首屏刷新在途允许置位，分页在途重复触发直接忽略；首屏结束后延后一主线程周期再消费 pending。
