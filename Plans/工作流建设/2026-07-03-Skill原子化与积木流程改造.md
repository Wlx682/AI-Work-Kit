# Skill 原子化与积木流程改造

**目标**：把当前偏重 `client-dev` 的重流程，演进为「原子 Skill + 轻量 Workflow + 便捷测试」的积木系统。

**一期范围**：先解决验证成本高的问题，不一次性重写所有 Skill。

---

## 一、背景判断

当前 `client-dev` 适合完整需求开发，但日常还有三类高频轻场景：

| 场景 | 现状问题 | 一期方向 |
|------|----------|----------|
| 纯 UI 小改 | 已有 `figma-ui` 路由硬规则，但没有独立轻流程和低成本测试入口 | 建 `ui-change` 蓝图草案 + Figma smoke fixture |
| Bugfix | 有 `Plans/Bug排查/` 和排查模板，但未成为可编排流程 | 建 `bugfix` 蓝图草案 + Bug 样例 fixture |
| 单点 Skill 调优 | 要靠完整流程验证，成本高 | 建 `skill-smoke-test` 约定，先覆盖 3 个 Skill |

原则：**先定义积木接口，再搭更多流程**。否则流程越多，漂移越快。

## 三、Skill Contract 草案

每个可编排 Skill 至少声明以下字段：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | dash-form 名称，与路由表一致 |
| `scope` | 是 | 只做什么，不做什么 |
| `inputs` | 是 | 必需输入，如 PRD、Figma 链接、错误日志、技术方案 |
| `outputs` | 是 | 产物类型和路径，如 plan、审查结论、测试计划 |
| `gates` | 是 | 完成门槛，如 checklist、状态、脚本校验 |
| `contexts` | 是 | 默认要读/可能读的 Contexts |
| `feedback` | 是 | 是否必须写 `skill_run`，写到 plan 还是孤立反馈 |
| `smoke_tests` | 是 | fixture 路径、断言项、预期失败样例 |

### 一期示例

| Skill | 输入 | 输出 | 完成门槛 |
|-------|------|------|----------|
| `figma-ui` | Figma 链接 / 截图 / 目标页面路径 | UI 实现 + `Figma还原自检表` | 自评分 >= 9，差异表完整 |
| `task-splitter` | 已采纳技术方案 / Epic | 5-10 个原子任务 plan | 每个任务有输入、输出、验收、依赖 |
| `review-assistant` | diff / PR / 分支 | Findings-first review 结论 | 有严重级排序、文件行号、测试风险 |

## 四、轻流程蓝图草案

### 1. `ui-change`

适用：纯 UI 小改、Figma 还原、无业务逻辑或业务逻辑极少的界面调整。

建议阶段：

| stage | Skill | 产物 | 退出条件 |
|-------|-------|------|----------|
| `ui-scope` | `figma-ui` | UI 范围说明 / 自检 plan | 明确 Figma 节点、页面、状态覆盖 |
| `ui-implement` | `figma-ui` | 代码改动 + 截图 | 自检表 >= 9 |
| `ui-review` | `review-assistant` | UI review 结论 | 无阻塞问题 |

边界：一旦发现接口联调、埋点、状态机或跨模块业务逻辑，升级到 `client-dev` 或 `feature-dev-assistant` 所在流程。

### 2. `bugfix`

适用：已有功能的问题修复、回归缺陷、线上异常定位。

建议阶段：

| stage | Skill | 产物 | 退出条件 |
|-------|-------|------|----------|
| `reproduce` | `bugfix-assistant` 或 `feature-dev-assistant` | 最小复现路径 | 能稳定复现或说明不可复现证据 |
| `diagnose` | `bugfix-assistant` | 根因候选与验证记录 | 根因归类明确 |
| `fix` | `feature-dev-assistant` | 修复代码 | 回归场景通过 |
| `regression` | `test-generator` / `review-assistant` | 回归说明或测试 plan | 覆盖原问题和相邻风险 |

一期不强行新增复杂 Skill，可以先把 `bugfix-assistant` 作为候选，复用 `排查问题模板.md` 跑通夹具。

### 3. `task-split-only`

适用：已有技术方案，只需要拆任务，不进入开发。

建议阶段：

| stage | Skill | 产物 | 退出条件 |
|-------|-------|------|----------|
| `split` | `task-splitter` | 主 plan + 子任务 plan | 5-10 个原子任务，依赖清楚 |
| `check` | `task-splitter` | WBS / 依赖自检 | 无跨任务职责混杂 |

边界：WBS 修订必须走 `task-splitter` 或用户确认，不由执行 agent 自行推荐 A/B/C。

## 五、便捷测试设计

先做「结构型 smoke test」，目标不是替代人工判断，而是快速发现 Skill 产物漂移。

### Fixture 目录

```text
tests/fixtures/skills/
  figma-ui/
    basic-card.input.md
    basic-card.expected.md
  task-splitter/
    checkout-tech-plan.input.md
    checkout-tech-plan.expected.md
  review-assistant/
    risky-diff.input.md
    risky-diff.expected.md
```

### 脚本入口

```bash
python3 scripts/skill-smoke-test.py figma-ui tests/fixtures/skills/figma-ui/basic-card.input.md
python3 scripts/skill-smoke-test.py task-splitter tests/fixtures/skills/task-splitter/checkout-tech-plan.input.md
python3 scripts/skill-smoke-test.py review-assistant tests/fixtures/skills/review-assistant/risky-diff.input.md
```

### 一期断言

| Skill | 断言 |
|-------|------|
| `figma-ui` | 输出包含自检分数、差异表、Figma 节点/截图引用、未达标时不能说完成 |
| `task-splitter` | 输出 5-10 个任务；每个任务有输入、输出、验收、依赖；不得擅自替用户做 WBS 方案选择 |
| `review-assistant` | Findings first；按严重级排序；问题有文件/行号；没有问题时说明测试缺口 |

## 六、反馈规则结论

已拍板采用 **A. 全量强制**。

| 规则 | 结论 |
|------|------|
| 有 plan 的 Skill 任务 | 必须在 plan 末尾追加合法 `skill_run` |
| 无 plan 的 Skill 任务 | 写入 `Contexts/决策/孤立反馈记录.md`，`plan: orphan` |
| 机械门禁 | `plan-gate-check.sh` 默认对所有 plan 执行 `validate-skill-run.py --require` |
| 回归测试 | `test_plan_gate_requires_skill_run_for_all_plan_categories` 覆盖非需求类 plan 缺反馈必须失败 |
| 纯讨论 | 不自动写孤立反馈；形成可复用规则、脚本或 plan 时再记录 |

对应文档已同步：`Contexts/决策/Skill反馈协议.md`、`Contexts/决策/Kit核心原则.md`、`Contexts/决策/Skill原子契约.md`。
