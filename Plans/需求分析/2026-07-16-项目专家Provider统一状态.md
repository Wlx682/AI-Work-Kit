# 需求分析：项目专家 Provider 统一状态

## 一、需求结论

用户已明确状态边界与依赖方向，可直接开发，P0=0。

## 二、业务规则

- 项目专家列表和当前选中专家由同一个项目级 Provider 管理。
- Provider 必须支持添加观察者，供其他使用模块监听变化。
- `NMProjectAddedExpertPopupController` 不直接依赖 Provider；调用方注入列表，弹窗数据变化后由调用方回写 Provider。
- `NMModelComponent` 不直接依赖 Provider；调用方根据 Provider 更新展示，用户选择专家后由调用方回写 Provider。
- `NMProjectTeamViewController` 的增删查结果必须进入同一个 Provider。

## 三、验收标准

| AC | 验收条件 |
|----|----------|
| AC1 | 专家 Tab 添加或移除专家后，弹窗下次打开展示同一份最新列表 |
| AC2 | 当前选中专家变化后，输入框专家胶囊同步更新 |
| AC3 | 当前选中专家被移除后，选中态回退到剩余列表首项；列表为空时展示纳米 AI 助理兜底 |
| AC4 | Provider 更新时，已注册观察者收到通知；观察者释放后不被 Provider 强持有 |
| AC5 | 弹窗和 `NMModelComponent` 的源码不引用 `NMProjectExpertProvider` |
| AC6 | 同一项目同时触发列表刷新时复用同一请求结果，不产生多份状态 |

## 四、非目标

- 不调整专家接口协议。
- 不修改 UI 视觉和交互规格。
- 不改变定时任务场景独立使用专家弹窗的能力。
