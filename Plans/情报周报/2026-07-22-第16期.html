01 — 研究问题

从单个 PR 的成败，转向项目能否持续吸收

Rochester Institute of Technology 的 Maliha Noushin Raida 与 Daqing Hou 分析真实 GitHub 工作流，论文被 KDD 2026 Agentic Software Engineering Workshop 接收。此前研究常问 Agent PR 是否合并、代码质量如何；本文把观察单位提升到仓库和团队。

RQ1 · Adoption

项目中有多少贡献者参与 Agent PR，三个月产生多少 Agent PR。

RQ2 · Activity proxy

每位人类参与者对应多少 Agent PR，项目能管理多大贡献量。

RQ3 · Collaboration

修改、审核与整合责任集中在个人，还是由多人分担。

Agent 的生成能力已经进入现实工程，但广泛采用、稳定吞吐与团队化监督并没有同步发生。

02 — 数据与方法

从五类 GitHub 工件重建人机协作

AIDev-pop 原始数据包含 2,807 个热门仓库的 33,596 个 Agent PR。作者保留 2025 年 5–7 月创建、已合并或关闭且能取得贡献者信息的记录，得到 2,361 个仓库、25,264 个 PR 和 291,866 个 commit。

数据来源提取信息研究用途
pull_requestAgent 标签、状态、时间建立样本与结果窗口
commit detail作者、提交者、提交信息判断人类是否修改 Agent 代码
review / comment审核者与讨论者识别技术监督与互动
timeline event合并、关闭等 actor补足整合阶段参与者
contributors API默认分支非 bot 贡献者代理项目团队规模

包含 codex、claude、copilot、bot 等标识的 commit 被视为自动化，其余 distinct committer 与 reviewer、commenter、timeline actor 合并为人类参与者集合。团队按 1–5、6–15、16+ 名贡献者分组，得到 343 个小型、456 个中型和 1,562 个大型项目。

Participation Ratio = Agent PR 参与者 ÷ 仓库贡献者

“参与有多广”和“活动有多强”必须同时观察。

Activity Proxy = Agent PR ÷ 人类参与者

只代表贡献活动量，不包含质量、复杂度、审核成本或业务价值。

03 — RQ1 · 采用广度

工具进入了仓库，却没有进入大多数人的日常

 participation-thresholds.svg

非参数检验显示项目规模与参与率显著相关，效应量为大；约 61.6% 的参与率差异与规模分组相关。更换团队规模边界后结果仍保持，说明结论不依赖唯一分组方式。

 mean-vs-median.svg

平均数与中位数的巨大差距证明活动高度偏斜。不能用小项目平均 50.2 推断一般小团队都会高频采用；典型仓库仍处在试用或零散使用阶段。

04 — RQ2 · 项目级活动量

只有 25 个项目越过 36 PR 参照线

作者把“每位开发者三个月 36 个 PR”作为上下文参照，而非普适生产力标准。2,361 个项目中只有 25 个、约 1%，超过每位 Agent 工作流参与者 36 个 Agent PR。

1–2
典型仓库三个月中位数

一人或少数人参与的项目离散程度最大，从几个 PR 到数百个不等。参与人数增加后，更多项目聚集在较低的人均活动量。可能原因包括小分母、熟练先行者、任务可并行性和工作流设计，但论文没有识别因果。

指标边界

PR / participant 没有计算 PR 大小、复杂度、缺陷率、审核时间、返工或业务价值。它只能说明每人对应的 Agent PR 活动量，不能直接称为 ROI 或完整生产力。

05 — RQ3 · 协作结构

Agent PR 的默认组织形态仍是个人闭环

 collaboration-distribution.svg
same reviewer+committerone reviewermulti-human

最常见模式是同一个开发者修改 Agent 代码并完成审核，占 78.9%；第二是一个人审核、没有人类 commit，占 9.8%。大型项目的多人协作略多，但仍未改变单人监督的主导地位。

模式人类分工潜在治理特征
1 reviewer，无 committer一人审核 Agent 原始输出审核集中，代码来源清楚
reviewer = committer同一人修改并审核个人闭环，缺少职责分离
reviewer ≠ committer修改与审核由不同人承担接近传统双人制约
1 reviewer + 多 committer多人改码，一人审核修改分布，判断集中
多 reviewer，无 committer多人共审 Agent 原始输出团队监督，无人工改码

88.7% 不是“没有检查”，而是监督责任集中。论文没有比较各种模式的缺陷率或质量，因此不能直接推出单人审核更差；它建立的是组织结构基线。

06 — 讨论与有效性威胁

这是一张早期快照，不是行业全景

热门开源样本

只含 100 Stars 以上仓库，不能外推到长尾、私有与企业环境。

三种 Agent

只覆盖 Copilot、Codex、Claude Code，忽略其他工具和自研系统。

三个月窗口

2025 年 5–7 月是早期切片，不能代表 2026 年当前采用率。

身份识别误差

关键词过滤可能漏掉自动化账号或误排人类账号。

规模代理

历史贡献者数不等于当前活跃团队或真实决策结构。

活动量代理

PR 数不含复杂度、质量、价值与审核成本，不能等同完整生产力。

论文能证明项目规模、参与覆盖和监督模式之间存在显著结构差异，却不能解释为什么少数项目能高频采用，也没有连接协作模式与质量结果。下一步需要纵向数据，把治理方式、审核容量和工作流设计与缺陷、返工和价值结合。

07 — 工作流提炼

AI-Work-Kit 要观测的，不只是“跑了几次”

区分工具出现与工作流采用

Kit 已有 Epic、workflow run、事件日志和 skill_run，能记录一次流程是否完成；还缺少 adoption 聚合：首用、复用、多人扩散、稳定过门禁应是不同状态。unique user、repeat run、success gate 与人工回退能帮助识别卡点，但不能被用作个人绩效指标。

把生成吞吐连接到吸收漏斗

Agent 创建更多输出，只有在审核、测试、返工和发布风险没有失控时才形成净收益。可从 Git、测试与 workflow event 聚合 agent_outputs_created、review_minutes、rework_cycles、gate_reject_rate 与接受价值；业务价值仍由人判断，避免以 PR 数诱导拆小任务。

职责分离按变更风险触发

单人闭环适合低风险、可回滚、测试充分的改动；涉及权限与凭证、数据迁移、公共 API、跨模块影响或不可逆外部写入时，应要求独立 reviewer 或更强验证证据。小团队可以用独立测试、第二模型 review、延迟发布与回滚部分补偿，但另一个 Agent 不能自动等同于人类责任。

推广策略要看参与结构

小项目与大项目的采用阻力不同。应按团队规模、角色、仓库风险与熟练度观察首用到复用的转化，定位卡在权限、上下文准备、测试还是 review 阶段，再由负责人决定培训与默认流程。

为指标建立契约

关键指标应同时记录定义、观察窗口、分母、数据来源、未覆盖内容与禁止解释。例如 agent_pr_per_participant 必须明确“不代表质量、复杂度或 ROI”。指标名称会比脚注传播得更快，边界必须与数字一起进入看板和复盘。

Agent 能力继续提升后，真正稀缺的资源会逐渐从生成 token 转向清晰责任、验证证据和团队吸收能力。
