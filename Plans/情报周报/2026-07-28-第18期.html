01 — The Missing Step

旧评测把最难的一步提前做完了

假设你让 Agent 开发一个文件解析器，只说：“读取配置文件，返回结构化数据。”真正动手时，它马上会遇到一串没有答案的问题：支持哪些格式？空文件怎么处理？错误是返回结果还是抛出异常？调用方需要命令行还是函数接口？

人类开发者会在实现过程中不断确认这些问题。大多数编码评测却先替 Agent 把它们整理好，再要求它写代码。这样的评测能看出 Agent 会不会照着清楚说明施工，却看不出它能不能在说明不完整时把事情推进下去。

ICAE-Bench 因此把起点换成一段很短的需求，平均只有 276 个英文词元。Agent 最多可以向模拟用户提问 16 次，随后必须交付完整仓库。最终测试检查的不是它问了多少，而是它有没有把答案真正做进产品。

发现缺口 → 问到答案 → 写进代码 → 通过验证

这不是一个动作，而是一条随时可能中断的链路。

ICAE-Bench 想回答的不是“Agent 会不会写”，而是“需求尚未完整时，它能不能把产品做出来”。

02 — A Fair Ambiguous Task

要考模糊需求，先保证答案不是评测者临时编的

模糊需求很难公平判分。用户只说“做一个解析器”，Agent 选择 JSON、YAML 或自定义格式都可能合理。如果研究者事后拿自己的偏好当标准答案，测到的只是 Agent 有没有猜中心思。

论文因此反过来出题：先找一个已经能正常运行、原始测试全部通过的真实开源项目。研究团队从它的代码和测试中整理出完整需求，再故意隐藏部分 API、边界行为和架构约束。这样，初始需求虽然模糊，背后仍然有一套事先确定、可以验证的行为。

T = (Df, E, P, U, B)

模糊 PRD · 执行环境 · 可恢复示例 · 用户记录 · 权威行为测试

01 · VERIFY筛选真实仓库受控 Docker 中原始测试全部通过。
02 · GROUND生成完整合同GroundPRD + Native / Enhanced 黑盒用例。
03 · FUZZIFY隐藏关键约束形成 L1/L2/L3 与可查询 User Data。
04 · PACKAGE打包 Ultimate Image保留环境，删除 golden code 与答案痕迹。
05 · REBUILD重建与一致性验证确认失败来自 Agent，而非错误规格。

完整需求称为 GroundPRD，可以理解为“经过验证的产品合同”。删减后的 Fuzzy PRD 是 Agent 的起点。被删掉的信息进入模拟用户的记录，只有问到相关问题才会返回。最终测试则独立保存，Agent 无法靠提问把答案逐条套出来。

材料平均规模用一句话理解
Fuzzy PRD L1276 个词元Agent 第一眼看到的简短需求
GroundPRD6,764 个词元根据真实行为整理出的完整合同
模拟用户记录7,091 个词元问对问题后可以找回的隐藏信息
原始项目35,533 行 · 258 个文件定义正确行为，不要求 Agent 复制内部写法

研究团队还会让模型只根据 GroundPRD 重建项目，再用原始测试校正需求；新增的边界测试也必须先在原项目上通过。这样做的目的，是尽量保证失败来自 Agent，而不是题目写错了。

03 — What The Agent Experiences

Agent 不是在答题，而是在经历一次缩短版项目开发

任务开始时，Agent 只拿到模糊需求和一个准备好的开发环境。模拟用户掌握着隐藏信息，但不能自由发挥：每条需求都有固定记录和可能的问法。问题命中后，一次最多返回三个技术点；没有命中，就只给兜底回答。

这种模拟不如真人自然，却保证同一个任务可以重复比较。研究者能够分清：是 Agent 没有问到关键问题，还是用户每次回答不一样。

交互结束后，Agent 必须交付能构建和运行的完整仓库。评测系统会在一个全新容器里注入测试。开发过程中临时改过环境、手工运行成功，但没有进入最终产物的操作，一律不算。

为什么还需要四组证据

一个项目失败，可能是逻辑写错，也可能根本构建不起来；可能 Agent 没问到需求，也可能问到了却在后续修改中忘掉。因此，论文不只给一个总分。

功能是否正确

公开示例、原项目行为和新增边界测试，最终都要实际运行。

方向是否接近

比较功能语义、公共 API 与设计质量，帮助解释“差在哪里”。

仓库是否健康

观察文件、代码量和结构，发现少做、过度构建或交付污染。

问题是否有效

记录找回多少隐藏约束、多少问题没有命中，以及用了多少预算。

关键区别：模拟用户能回答的内容，不等于最终测试的全部答案。Agent 仍然要从有限示例中归纳一般规则。
04 — The First Surprise

公开示例做对了，不代表产品真的做成了

在完整的 480 个任务上，Claude Opus 4.8 通过了 38.2% 的测试，GPT-5.5 为 37.2%。这里按测试用例计分，并不是说 38.2% 的项目已经完成。事实上，每个模型只有 1 到 13 个仓库通过了全部测试。

公开示例和隐藏边界之间的落差更值得注意。两个最强模型都能通过大约一半的公开示例，但遇到未展示的异常和边界时，只剩三成多。Agent 能模仿已经见过的行为，却没有稳定地推导出背后的完整规则。

其他指标也没有和功能结果保持一致。GPT-5.5 找回的隐藏需求更多，最终通过率却略低；Claude Sonnet 4.6 的语义相似度很高，功能排名却靠后。问得更多、代码看起来更像、仓库做得更大，都不能单独证明它真的正确。

05 — The Executable Difference

最有效的改动不是增加需求，而是让示例可以直接运行

论文最醒目的实验没有给 Agent 任何新信息。研究者只是把原本通过问答返回的公开输入输出示例，提前做成工作区里的测试文件。

结果是，Agent 知道的事实几乎没变，测试通过率却从 37.4% 上升到 61.8%。一段文字只是在描述“应该怎样”；可运行测试则让 Agent 修改代码后立刻看到成功或失败，并能反复回归。

干预结果解释
可运行测试37.4% → 61.8%把输入、预期输出和运行方式合成一条即时反馈。Agent 找回的约束反而略少。
更换 Agent 框架GPT-5.5：53.3% → 31.5%从 Claude Code 换到 OpenHands 后，编辑、命令、状态和终止方式都变了。
增加思考Gemini 26.7% → 36.6%更多推理通常有帮助，但不能代替需求整合和实际验证。
统一改用 Python26.6% → 29.9%总体小幅提升，不同原始语言却有升有降，没有通用捷径。
更稳妥的结论：实验不意味着“任何项目多写测试都会提升 24.4 点”，而是说明可执行、可重复验证的信息，通常比只出现于上下文的信息更容易被 Agent 使用。
06 — Where Information Gets Lost

问到答案以后，还有一半路要走

研究者把所有可通过提问获得的回答一次性附在需求后，Agent 不再需要判断问什么，也不会漏掉信息。这个版本仍然不如一份整理好的完整需求。

差别不在事实数量，而在组织方式。一叠问答记录解决的是局部问题；Agent 还要判断每条回答影响哪个接口、是否与其他约束冲突、应该落到哪些文件，以及后续重构有没有把它破坏。完整需求已经把这些碎片整理成一份连贯合同。

论文因此区分两个缺口：第一个是能否发现缺少什么并问到答案，称为“需求访问缺口”；第二个是答案能否持续进入设计、实现和验证，称为“信息到执行缺口”。

这也解释了为什么 24 次提问反而不如 16 次。提问预算从 8 增到 16 时，通过率从 22.9% 上升到 37.4%；继续增到 24 次，Agent 找回的需求更多，通过率却回落到 34.4%。没有稳定的约束管理时，更多回答也意味着更多需要整合、冲突和遗忘的内容。

更丰富的运行环境同样没有自动带来更好结果。加入更多依赖后，通过率从 37.4% 降到 28.4%，生成代码量膨胀到原项目的 674.1%。选择变多，也会让有限的推理和调试预算分散到更多模块上。

07 — What The Numbers Do Not Mean

38.2% 不是“Agent 完成真实项目的成功率”

这个数字只描述特定模型、Agent 框架、提问预算和测试协议下的用例通过情况。基准规模很大，仍然不能覆盖真实软件开发的全部复杂性。

模拟用户不是真人

固定回答保证可复现，却没有真实用户的含糊、改口和目标变化。

目标来自已有项目

总有一个可验证答案，无法代表没有标准答案的开放式创新。

前端与体验覆盖不足

输入输出测试适合后端行为，不擅长判断视觉、可用性和主观体验。

大量对照实验使用小样本

许多消融基于 50 个较小项目，不能直接当作完整榜单结论。

50 个项目组成的轻量版与完整榜单排名相关系数为 0.71，适合快速比较配置，但第一、第二名会互换。用于评价语义、API 和设计的模型评审，与人工评分也只有有限到中等相关，不能替代实际运行测试。

正确读法

论文最可靠的贡献不是一个永久模型排名，而是多组对照实验反复指向同一件事：让信息出现，与让信息生效，必须分开衡量。

08 — Workflow Lessons

工作流要管理的不是问答记录，而是需求如何变成证据

1. 澄清以后，要能看见它去了哪里

重要需求不能只留在聊天历史里。一次澄清如果改变了产品行为，就应该关联到设计决策、实现位置、可执行验收，或明确的人工评审项。后续修改发生时，团队才能反向找到可能被破坏的旧结论。

2. 用生命周期保存约束

discovered → accepted → implemented → tested → verified

回答已收到不等于需求已完成；任何缺失状态都应成为 review 可见的风险。

只保留最新版 PRD，会丢失约束何时出现、为什么改变，以及旧实现是否仍然存在。状态可以自动记录，但商业确认和冲突取舍仍要由人完成。

3. 让高价值需求尽快拥有可执行反馈

输入输出、错误路径和状态迁移适合转成测试；UI 和体验可以转成截图基线、结构检查或人工评审清单。形式可以不同，但都要让“没有做到”变得可观察。公开示例帮助 Agent 调试，独立验收则防止它只针对样例优化。

4. 记录完整的 Agent 运行条件

模型名称并不足以复现结果。还要记录 Agent 框架、工具与权限、环境、思考配置、提问预算、执行命令和验收版本。框架切换造成最高 21.8 个百分点的差异，说明这些都是系统的一部分。

5. 先判断断点，再决定重做什么

没有发现需求、回答没有保留、实现行为错误、项目无法执行、验收不足，是五种不同问题。只有先分类，团队才知道应该补澄清、修状态传递、改代码、修环境还是补验证，而不是一律归结为“提示词不够好”。

6. 提问要能改变后续行动

好的问题应该改变设计、接口、实现顺序或验收方式。如果连续提问都没有产生新的决策和证据，就应从收集信息转入实现与验证。原则不是少问，而是不要把提问变成没有改变执行状态的忙碌。

未来的 Agent 工作流，不只要把信息送进上下文，还要让每条重要信息留下可执行、可回归、可审计的痕迹。
