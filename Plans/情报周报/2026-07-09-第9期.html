主题

文档不是落后一步，而是被工作流接住

产品仓库的代码已经合并，文档仓库却常常慢半拍。Aspire 团队把这个空档交给 GitHub Agentic Workflows：产品 PR 合并后，工作流判断是否需要文档；如果需要，就在文档仓库起草稿 PR，并请真正懂功能的人审。

这篇的重点不是 Agent 会写文档，而是它把跨仓写入这件事收进了边界。Agent 可以读 diff、读 issue、草拟内容，但仓库、分支、文件保护、标签、草稿状态和失败兜底都由 safe-outputs 合约控制。

模型可以模糊，动作面不能模糊。
机制

Agent 产意图，门禁负责落地

这套系统把“判断”和“落地”拆开。Agent 判断是否需要文档，safe-outputs 只接受被允许的输出形态。这样做的好处是，判断可以有灰度，但写入动作必须硬。

路由

不要让 Agent 猜分支

目标分支不是靠语义想象出来的，而是从已有工程信号里推导：先看 PR milestone，再看 linked issue milestone，再看 PR base ref，最后才 fallback 到 main。好的 Agent 系统会尽量使用确定性信号，减少提示词里的猜测。

审查

人类不是补救者，而是验收门

文档 PR 一律是 draft，永远不自动合并。reviewer 取源 PR 的 SME，也就是产品团队已经信任过的功能审批人。这样文档层不再倒推功能语义，而是把草稿送回最懂功能的人那里确认。

自动化真正难的是边界，不是生成。

第一版的 docs-worthy 判断太宽，CI 调整、日志重构、测试变更也会触发文档 PR，导致约 13% 的关闭率。修复方式不是一句“更谨慎”，而是收紧用户可见变更定义，补负例，并在 pre-agent steps 里先抽取结构化摘要，减少大 diff 对提示词预算的挤压。

这说明 Agent workflow 的稳定性来自外围结构：负例、预处理、受限输出、失败兜底、人工审查、可度量指标。

复用

把 safe outputs 写进 Kit

AI-Work-Kit 也应该把“Agent 想做什么”和“系统允许落地什么”分成两层。Agent 负责产意图、草稿和证据；工作流契约负责路径、动作、保护文件、人工审查和失败出口。

safe_outputs 字段在蓝图 Schema 中表达 allowed_paths、blocked_paths、allowed_actions、human_review_required、fallback。
结构化预处理先抽目标文件、依赖 plan、去重项、review owner，再交给 Agent 判断。
责任绑定谁批准需求，谁参与验收相关产物；Agent 只负责草稿和提醒。
not-needed 出口“无需新增”也应成为可审计输出，不逼每次都产物。
