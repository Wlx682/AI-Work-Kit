01 — Valid Is Not Correct

工具没有报错，不代表它验证了你关心的事

假设 AI 生成了一份交通信号灯规格。文件格式正确，模型检查器也运行成功。它仍可能只描述初始状态，根本没让信号灯变化；或者只检查一个永远为真的条件。工具忠实执行了规则，规则本身却没有排除危险行为。

TLA+ 用状态、状态转换和属性描述并发或分布式系统。模型检查器 TLC 会遍历给定配置下全部可达状态，这比有限测试更强。但它只检查规格中写出的行为和配置点名的属性。

能解析 ≠ 能运行 ≠ 行为正确 ≠ 属性承重

每一层通过，都回答一个更强的问题。

TLA+-Bench 的任务是根据自然语言生成完整 TLA+ 模块。SANY 先检查语法，TLC 再执行参考配置。论文拒绝把两个结果混成一个分数。

精确验证器不会误解它检查的命题，但命题可能根本没有价值。

02 — Dataset Construction

真实数据也要先证明它能区分能力

研究团队从 13 个公开仓库收集 1,614 个候选模块，删除重复、无法解析、工具内部文件、测试脚手架和运行失败项，留下 1,300 份规格。

03 — Correctness Envelope

一个正确率，背后藏着四个不同问题

默认模式只给自然语言需求，模型必须同时恢复接口名称和系统行为。Configuration-aware 模式额外提供常量与属性名。随后，研究者再对默认输出施加两级更严格的通过质量检查。

这些数字不是四个互相竞争的“真实正确率”。18.7% 问接口已知时能否建模；10% 问能否自行恢复接口；4% 问规格是否真的产生行为；1.7% 问被检查属性是否真正排除错误系统。

核心发现：只报告一个通过率，相当于默默替读者选定了“正确”的含义。正确性包络把这项选择变成显式信息。
04 — Failure Fingerprints

模型很会写合法格式，却很难写对行为

Claude Opus 4.5 有 87% 的输出能够解析，默认语义正确率只有 16%；GPT-5 的两项数字分别是 89% 与 4%。语法和行为之间的差距，远大于前沿模型之间的排名差异。

难度一旦离开基础层，三个前沿模型的合并正确率从 25% 跌到 2%，解析率只从 86% 降到 76%。输出仍然看起来专业，语义已经接近地板。

最大的失败来源是配置绑定：GPT-5 和 Opus 失败中分别有 74% 与 73% 是名称没有匹配参考配置。提供接口名后，最强模型从 16% 升到 26%。总分把“猜接口”和“建模行为”混在了一起。

05 — Pass Quality

30 次默认通过，真正承重的只剩 5 次

模型检查器能通过一个什么也没验证的规格。论文先要求规格到达多个状态，且属性不是恒真式或纯类型约束。30 个默认通过结果中，只有 12 个满足这一“实质通过”标准。

研究者再把安全属性替换为 TRUE 并重新运行。如果属性被拿掉后错误仍然会暴露，说明它确实承担约束作用；如果仍然轻松通过，原属性可能只是装饰。在 18 个适合变异的结果中，只有 5 个经受住测试。

证据存在 ≠ 证据承重

验收项必须在实现被故意破坏时真正失败。

9 个静止规格

从未离开初始状态，因此没有检查真实状态变化。

9 个类型属性

只检查按构造必然成立的类型或格式条件。

5 个变异幸存

被检查属性确实能排除某些错误行为。

时序属性无法简单替换为 TRUE，论文将 1.7% 明确称为保守下界，而不是精确的非空洞率。这种边界说明比一个漂亮的总分更重要。

06 — Evidence Boundary

精确检查也有明确范围

属性范围

TLC 只证明给定配置和常量下，规格满足被点名的属性，不证明与参考行为完全等价。

单次采样

每题只生成一次，95% 区间约 ±4–7 个百分点，小模型排名只具提示性。

输入范围

主实验只用 GPT-5 的 Declarative 描述，Intent 和另一提供方尚未评测。

组合不足

多模块组合与 refinement 在 100 个主实验任务中只有 17 个。

403 个 Gold 配置中，291 个明确检查安全或时序属性，112 个只确认模块能运行。描述虽然经过 400 份双人审计，仍由模型生成，不能代替真实工程师从零提出规格。

正确读法

论文没有证明某个模型生成 TLA+ 的永久成功率，也没有把 1.7% 定义成唯一真相。它提供的是一套能显式报告接口、行为和属性强度的测量仪器。

07 — Workflow Extraction

完成不是一个点，而是一组有强弱的证据

为任务建立 acceptance envelope

AI-Work-Kit 已有 workflow gate、验收标准和测试计划，但“完成”常把文件存在、命令成功、行为正确和独立验收混在一起。适合在 plan 中列出从宽到严的证据层，并声明发布决策采用哪一层。不是每个任务都走最严门禁，但不能隐藏选择。

把接口失败与语义失败拆开

已有系统中的名称、路径、Schema、命令和协议属于兼容接口；从零项目才允许 Agent 自行设计。报告应把 interface mismatch 与 semantic mismatch 分开，避免为命名问题重做业务逻辑，也避免把接口对齐误当成功能正确。

检查验收证据是否承重

对支付规则、状态机和安全约束，可以临时移除校验、反转条件或替换期望，确认测试确实变红，再恢复实现。变异必须在隔离测试环境中进行，并由人决定哪些高风险规则值得承担额外成本。

显式标记平凡通过

空数据、永远成功的 mock、没有状态变化的 UI 流程，都会让 Agent 轻易通过。关键验收至少应有真实状态变化、失败路径或能区分正确与错误实现的反例。标记和解释比静默删除更可审计。

让直接证据决定失败类别

优先使用构建日志、测试结果、Schema 校验和浏览器错误分类，再让 Agent 解释。artifact_invalid、interface_binding、behavior_violation、evidence_vacuous 与 resource_limit 应分别触发不同返工动作。

为验证器声明 oracle scope

每个关键 gate 都应说明检查什么、没有检查什么、依赖哪些环境和样本，以及通过后支持什么决策。测试通过不等于所有行为正确，验证器有盲区也不意味着它没有价值。

最重要的不是找到一个绝对正确的总分，而是让证据强度、判分选择和决策边界都能被看见。
