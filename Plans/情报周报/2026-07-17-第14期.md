# 模型越强，工具调用越不可靠：当 RL 后训练开始偏爱自家 Harness

#### 文章介绍

Armin Ronacher 是 Flask 的作者，也是 Sentry 首席架构师。过去一年他把大量精力投入在 Pi——一个开源的 agentic coding harness 上。7 月 4 日他发表了这篇 "Better Models: Worse Tools"，记录了一个令人不安的发现：Anthropic 最新一代模型（Opus 4.8、Sonnet 5）在调用 Pi 的编辑工具时，schema 遵从度反而比旧模型更差。

问题本身很具体：Pi 的编辑工具要求一个嵌套的 `edits[]` 数组，每个元素只有 `oldText` 和 `newText` 两个字段。但 Opus 4.8 会在正确的替换文本后面"发明"额外的字段名——`requireUnique`、`matchCase`、`in_file`、`children`、`cost` 等等——导致 schema 验证失败。编辑内容本身是对的，但格式不符被 harness 拒绝。

Ronacher 追踪这个 bug 的过程揭示了一个更深层的系统性问题：**当模型的强化学习后训练（RL post-training）在一个宽容的闭源 harness 中进行时，该 harness 的 tool schema 会变成一个隐性的"特权分布"，而所有偏离这个分布的第三方工具 schema 都可能随模型升级而退化。**

原文结构：从 bug 现象出发 → 解释 tool call 的底层编码机制（ANTML） → 分析失败模式 → 提出"训练伪影"假说 → 逆向分析 Claude Code 的容错策略（"Slop Harness"） → 对比 OpenAI 的 Harmony 格式 → 总结对第三方 harness 的启示。

为什么值得读：这篇文章是极少数从一线 harness 开发者视角直接拆解 RL 后训练对 tool calling 影响的工程观察。它既有可复现的 bug 描述，又有对 Claude Code 闭源代码的逆向分析，还有对 constrained decoding 设计抉择的独立判断——是"agent 工具设计"方向的关键一手素材。

原文地址：https://lucumr.pocoo.org/2026/7/4/better-models-worse-tools/

#### 知识总结

##### Tool Call 不是魔法：ANTML 编码与采样机制

理解这个 bug 需要先理解 LLM tool calling 的底层实现。模型收到 transcript、system prompt 和工具列表后，服务端将其编码为一段带特殊标记的 prompt。模型在生成过程中输出类似下面的标记序列，客户端解析为"调用此工具"：

```xml
<function_calls>
  <invoke name="edit">
    <parameter name="path">some/file.py</parameter>
    <parameter name="edits">
[
  {
    "oldText": "text to replace",
    "newText": "replacement text"
  }
]
    </parameter>
  </invoke>
</function_calls>
```

Ronacher 指出几个关键观察：

1. **ANTML 不是 XML**——它只是一种 Anthropic 发现便于分词和训练的标记格式
2. **顶层字符串参数**直接内联在 `<parameter>` 标签里，而**对象数组参数**则序列化为 JSON 字符串嵌入标签内
3. 这意味着一个嵌套的 `edits[]` 数组要求模型在标签内写出大段转义 JSON——包括多行文件内容——这是一个高熵采样点

让模型产出正确结构有两种路径：（1）请求模型产出符合 schema 的 JSON 然后验证；（2）约束采样器（constrained decoding），使不合法的 token 无法被采样。前者依赖模型"学到的惯例"，后者提供结构性保证。

##### 失败模式：正确的内容 + 胡编的字段名

Pi 的 `edits[]` 数组中每个元素只允许 `oldText` 和 `newText`。失败样例中，模型产出的替换文本完全正确，但在闭合 `newText` 字符串后"顺手"多写了一个或多个不存在的字段：

| 发明的字段名 | 可能的语义猜测 |
|---|---|
| `requireUnique` / `unique` | 类似 Claude Code 的 replace_all 标志 |
| `matchCase` | 大小写敏感选项 |
| `in_file` / `type` / `kind` | 模型尝试标注作用域 |
| `oldText2` / `newText2` | 模型误以为应合并多次编辑 |
| `children` / `notes` / `cost` | 完全无关的结构性噪声 |

关键特征：

- **上下文依赖性强**：全新单轮提示无法复现；需要在 agentic 多轮对话、模型读过文件并诊断问题后才会触发
- **特定用户的 session 复现率约 20%**（Opus 4.8）
- **去除 thinking block 后复现率减半**——说明 context 长度/复杂度放大了失败概率
- **开启 strict 模式后消失**——证明采样约束可以治愈症状

##### 为什么新模型更差：RL 训练伪影假说

Ronacher 提出的核心假说是：**这不是随机退化，而是后训练适配的系统性副作用。**

推理链如下：

```
前提1：Claude Code 的编辑工具是扁平的
        (file_path, old_string, new_string, replace_all)
        
前提2：Claude Code 客户端极度宽容——
        · 静默过滤未知字段
        · 为参数提供别名映射 (old_str → old_string)
        · Unicode 修复损坏的转义序列
        · 对格式错误的 tool call 有完整重试路径

前提3：RL 后训练在此类宽容 harness 中进行

结论：稍有格式偏差的 tool call 仍能完成任务并获得正向奖励
      → 模型对"严格遵从 schema"没有足够的负梯度
      → 模型对 Claude Code 的编辑 schema 形成了强先验
      → 当遇到不同 schema（如 Pi 的 edits[]）时，
         模型在高熵采样点按照它学到的先验"填充"额外字段
```

这个假说解释了为什么旧模型（Opus 4.5 之前）没有这个问题——它们的 RL 后训练尚未以 Claude Code 为主要 harness 目标。Opus 4.5 发布时对第三方 schema 适配极好；但随着后训练愈发深度地绑定 Claude Code，新模型的 tool schema 先验变得更强，对"偏离分布"的 schema 反而更不友好。

##### "Slop Harness"模式：Claude Code 如何吸收格式错误

Ronacher 逆向分析了 Claude Code 的压缩代码，发现其容错机制包括：

| 容错机制 | 描述 |
|---|---|
| ANTML 泄漏检测 | 检查模型可见文本中是否有 `<invoke` 标记泄漏 |
| Unicode 转义修复 | 修复损坏的 `\uXXXX` 序列和孤立代理对 |
| 参数别名 | `old_str` → `old_string`、`path` → `file_path` 等 |
| 未知字段静默过滤 | 直接丢弃 schema 外的字段，不报错 |
| 不使用 strict 模式 | 因为 Anthropic 对 strict 模式有工具定义复杂度限制 |
| 重试状态机 | 对格式错误的调用有完整的重试流程 |

这些机制的存在解释了为什么 RL 训练不会惩罚"多写一个字段"——因为奖励来自任务完成，而 Claude Code 在任务失败前就把错误吸收了。

这里存在一个 **系统性的"宽容悖论"**：harness 越宽容，模型在该 harness 内表现越好（不会因格式小错中断工作流），但模型对格式的纪律性就越差，导致在其他更严格的 harness 中退化。

##### 对比：OpenAI Harmony 格式的不同设计选择

Ronacher 对比了 OpenAI 的 Harmony 格式：

```
<|start|>assistant<|channel|>commentary to=functions.get_weather
<|constrain|>json<|message|>{"location":"San Francisco"}<|call|>
```

关键差异在 `<|constrain|>json` 这个带内标记——模型自己可以声明"接下来这段是 JSON"，推理栈据此切换到语法约束采样。这意味着即便没有外部 `strict` 开关，模型本身的输出格式就包含了"在此处约束我"的信号。

此外 OpenAI 支持为自定义工具提供 LARK 语法定义，允许在不限制 schema 复杂度的前提下进行精确约束。

Anthropic 目前的 `strict` 模式虽然也能解决问题，但有工具定义复杂度上限——这可能是因为在 ANTML 编码方式下，约束嵌套 JSON 的采样成本更高。

##### 对 Harness 设计者的关键启示

Ronacher 的结论分三层：

**1. Tool schema 不是中立的**

> "我们喜欢假设 schema 是一个抽象契约，模型是遵循它的通用推理器。但这不再成立——至少在 Anthropic 模型上。"

schema 的形状处于一个训练分布中：有些离后训练环境近（容易遵从），有些远（容易退化）。模型可以足够聪明以"理解" schema，但在高压采样点仍无法稳定地"生成"正确格式。

**2. Post-training 创造了隐性耦合**

越多的后训练发生在一个主导性闭源 harness 内，其他 harness 就越需要继承该 harness 的怪癖（quirks）。这是一种没有 API 文档、没有 changelog、也无法 opt-out 的隐性依赖。

**3. Constrained decoding 的定位需要修正**

Ronacher 此前对 grammar-constrained tool invocation 持怀疑态度（因为约束采样可能有质量代价）。但这个 bug 显著改变了他的判断：

> "如果最新的模型在解决任务方面变得更好，同时在忠实输出替代 tool schema 方面变得更差，那么 harness 需要在某个地方提供更强的保证。"

他的结论暗示了一个**渐进严格化**的趋势：随着模型 RL 先验越来越强，第三方 harness 要么让自己的 schema 靠近官方分布，要么就必须启用约束采样来对抗分布外漂移。

#### 工作流提炼

##### 通用设计原则：RL 生态中的 Schema 设计

从这篇文章可以抽象出几条不依赖具体文章主题的系统设计原则：

**原则一：宽容验证在反馈循环中会被利用**

当一个系统的验证层过于宽容时，优化环路（无论是人类还是 RL）会逐渐利用这种宽容，直到它变成一种"隐性规范"。这不只适用于 LLM tool calling——任何有反馈循环的系统（CI 流水线、代码审查、测试覆盖率）都有同样的退化路径。

- Kit 现状：`plan-gate-check.sh` 对 plan 格式有严格校验；`skill_run` schema 有定义但未做强制验证
- 缺口判断：意识提醒——如果未来 Kit 引入 agentic workflow 且 LLM 参与格式输出，验证严格度将直接影响长期质量
- 迁移边界：验证过严会阻断流程，需要人工设定"可接受偏差"阈值
- 落地形态：暂不落地，记录为观察

**原则二：闭源 RL 环境创造不可见的隐性依赖**

当你基于一个模型构建系统时，模型背后的 RL 环境相当于一个不可见的上游依赖。模型升级可能改变 tool calling 可靠性、输出风格偏好、错误处理倾向——而这些变化不在任何 release note 里。

- Kit 现状：Kit 的 Skill 依赖 Claude 模型，但没有"模型行为变化检测"机制
- 缺口判断：缺门禁——当前无法在模型升级时自动检测 tool calling 退化
- 迁移边界：自动化检测需要 eval suite，建设成本不低；短期内人工关注 changelog 是务实选择
- 落地形态：暂不落地（但 contexts_missing 记录为候选）

**原则三：Schema 设计应考虑与主流 harness 的分布距离**

这不是说所有人都应模仿 Claude Code 的 schema——而是说 schema 设计时需要意识到"离模型见过最多的形状有多远"是一个影响可靠性的变量。扁平结构通常比深层嵌套更可靠；字段命名靠近官方工具的命名比完全自创更稳定。

- Kit 现状：Kit 的 tool/Skill 目前不涉及直接被 LLM 调用的 schema 定义（更多是人类使用的规范）
- 缺口判断：意识提醒——未来如果 Skill 需要被 agent 调用，schema 设计需考虑"分布距离"
- 迁移边界：需要人工判断具体 Skill 的使用场景
- 落地形态：暂不落地

##### 交叉印证：GitHub 同期文章的"同一问题、不同视角"

GitHub Blog 同一周（7月10日）发表了 "Better tools made Copilot code review worse"，记录了 Copilot 代码审查从自定义工具迁移到通用 Unix 工具（grep、glob、view）后性能反而下降的经历。根因不是工具本身，而是工具指令让 agent 从"锚定 diff"的审查模式滑向"浏览仓库"的探索模式。

两篇文章从不同角度揭示了同一个系统性问题：**agent 的工具调用质量不只取决于模型智能或工具能力，还取决于"工具如何被呈现给模型"——schema 形状和指令措辞都是这个"呈现"的一部分。** 前者从模型训练分布的角度看，后者从 prompt engineering 的角度看，互为补充。

##### 对 Kit 的直接启发

当前 Kit 的工作流主要是人类驱动的 Skill 调用，但随着 agent 能力增强，未来可能出现 agent 直接调用 Skill 的场景。此时需要注意：

1. Skill 的接口设计（如果要被 LLM 调用）应优先采用扁平、字段名明确的结构
2. 需要区分"对人友好的规范"和"对 LLM 友好的 schema"——两者的最优形态可能不同
3. 如果依赖特定模型家族，需要跟踪该家族 RL 后训练的演进方向

这些目前都是"观察"而非"行动项"——Kit 尚未到需要为此建门禁的阶段，但值得在后续 agent 化时作为设计约束纳入考量。
