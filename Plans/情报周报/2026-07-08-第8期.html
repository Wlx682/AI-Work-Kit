正在到来的循环：当 harness 而非模型来决定“活儿干完了没”

越来越多人在编码 agent 之上又套了一层循环：任务进队列、机器捡起来尝试、停下，然后由一个 harness 判断这算不算真的结束。任务的生命，被拖过了模型本来会说“我干完了”的那个点。

我已经不再 prompt Claude 了。我让一堆循环跑着去 prompt Claude、去决定接下来干什么。我的工作是写循环。— Boris Cherny，Claude Code 原作者

01 — 主题

把主线又往前推了一格，这次带着不安

前几期一直在追同一条线：agent 越来越能自己干长活。Armin Ronacher（Flask 作者、Sentry 前架构师）在《The Coming Loop》里把这条线再推一格——并且第一次带着明显的不安在推。

他观察到：越来越多人在编码 agent 之上又套了一层东西。把任务丢进队列，一台机器捡起来、尝试、停下，然后一个 harness（外壳）来判断这算不算真的结束。不算，就继续同一会话、注入新消息、或换个改过上下文的新会话、甚至甩给另一台机器。

i
这篇值得写，不是因为它又一次唱好 agent。作者是个明确想看懂自己 ship 的每一行代码的人——他一边承认循环范式不可逆地要来，一边诚实记录自己为什么不安。这种“既看好又警惕”的一手判断，比单纯唱好或唱衰都更有参考价值。
02 — 机制（全篇钥匙）

两个循环：内层 agent 循环 vs 外层 harness 循环

  • 内层·agent 循环：模型调工具、读结果、再调工具、读文件、改文件、跑测试，最后产出答案。这个循环我们熟悉很久了，它在每个编码 agent 内部。
  • 外层·harness 循环：agent 循环之外的循环。模型说“我干完了”之后，外层不认，由 harness 判断要不要再来一轮。它不新，但最近几周开始主导讨论。

关键的范式转变在于：“干完了没”的判断权，从模型手里转移到了 harness 手里。

作者点破：harness 需要的不是一个客观、二元的“完成”信号，它只需要一个“有用到足够驱动下一轮”的信号——可以是二元测试用例，也可以是另一个 LLM 当裁判。

03 — 适用边界

循环在哪里已经 work 得惊人

作者很诚实：不能假装这范式不 work。他给的成功案例有一个共同特征——这才是判断“该不该上循环”的核心标尺。

  • 代码移植/翻译：Bun 从 Zig 移到 Rust；他自己把 MiniJinja 移到 Go。
  • 性能探索：机器试实验、跑基准、丢掉失败的、继续搜。
  • 安全扫描 / 研究：探索复杂问题空间然后报告，不一定留下长期代码。
2
两层循环：内层 agent 循环 + 外层 harness 循环
产物寿命决定边界
短命 / 可机械验证 → 放手循环；长期维护 / 强不变量 → 人在环
信号“有用”即可
harness 不需要客观二元判断，够驱动下一轮就行
产出不需要长期存活的产物、或做清晰可验证的机械翻译的循环，比“harness 能不能机械地度量目标”本身更重要。

共同点是：它们要么不产生新代码（只转换已有代码），要么产出的东西本就不需要长寿命。循环的适用边界，取决于产物要不要长寿命、结果好不好验证，而不取决于 harness 有多强。

04 — 核心判断

为什么用循环写“要长期维护的代码”让他不安

当下模型倾向产出过度防御、过度复杂、推理过于局部的代码。它们回避强不变量，用加兜底代替让坏状态根本不可能出现。Karpathy 说模型“对异常怕得要死”——见到局部失败就加局部防御。

而在有重要不变量的系统里（持久化格式、核心基础设施），正确的修法不是“处理每种畸形输入”，而是让畸形状态根本无法被表示。这种代码 LLM 自然写不出；就算引导它写出来，它还会去处理那些已经不可能发生的错误。把这种行为套进循环，就会被放大：

!
作者甚至说：今天 Claude Code 开 ultracode 无人干预跑 30 分钟以上产出的代码，比去年秋天 human-in-the-loop 时更差——而且他看不到改善，甚至觉得方向在往错的方向走。把这种工具丢给缺引导的新人尤其危险：你问他们为什么加这么多兜底，他们还能振振有词。
05 — 比喻

软件从“确定性机器”变成“有机体”

作者用一个很准的比喻收束忧虑：我们正从把软件当确定性机器，转向把软件当有机体。

过去他被训练去理解机器：总有一层能剥开加深理解；好架构让新人也能在复杂代码库导航；团队总有人知道不变量住哪、哪些是承重的、哪些改动安全。“看不懂”一直被视为需要改进的缺陷。

而 LLM 把我们朝相反方向推得又远又快：不只写代码，还做诊断和修复。已经有工程师的生产事故第一反应是——让机器读日志、提根因、主动挂 patch，再由另一台机器 review、有时无人监督合进 main。代价是：我们可能不再以同样的方式理解整个系统。我们治疗它、监控它、稳定它，但不一定再理解它。

06 — 压强

你没法真正 opt out

最不适的一点：完全退出这个机器驱动的未来，可能不是选项。三个压强来源逼你入场：

  1. 安全：就算你不用循环建软件，别人会用循环攻击你的软件。curl 维护者已被 AI 生成的漏洞报告淹没——curl 核心几乎不用 AI，照样被动承压。
  2. 竞争：有团队靠原始速度把别人甩开，5 个人干过去 50 个人的活。有人直接拿机器对着你的产品循环、让它“做得跟那个一样”——只要用户满意，真有区别吗？
  3. 依赖：他最怕的。代码库由循环产出/review/patch/续命，那当你失去对同类系统的访问权（贸易限制、成本不可承受、或团队丧失不靠机器读懂代码的能力）会怎样？我们可能造出把“机器参与”当成维护前提的代码库。
i
这已经在发生：越来越多人合入自己无法完全解释的代码，越来越多人不借 LLM 就没法写 issue、没法把话在群里讲清楚。“认知依赖”正从一次性工具费，变成一种持续的、绕不开的依赖。
07 — 结论

问题不是“会不会循环”，而是“怎么循环而不放弃判断”

最该记住的一句：编码的未来是“写循环”，而核心权力转移是“干完了没”的裁判权从模型交到了 harness 手里。派生两条判断：

  • 循环的适用边界由产物决定，不由 harness 强弱决定。短命产物（移植、性能实验、安全扫描、研究）循环已好用；需长期维护、强不变量的核心代码，循环会逐轮放大“加局部防御”的坏习惯。
  • 没法完全 opt out，但可以选怎么入场。作者落点不是“别用循环”，而是：在满是循环的未来里，怎么不放弃判断力、保住好工程规矩、让负责任的人还能持续监督、重新架构代码以保住可理解性。

适用边界也说清：这是一篇观点/判断类一手文章，给的是“怎么想这件事”的框架和判据，不是“照这样配 harness”的步骤。它帮你在该不该上循环、上到什么程度上做决策。

08 — 复用

给我们工作流治理的一把判据尺

这篇不像前几期能直接改一个 Skill，但它给的判据很实用。四个落点：

一 · 把“产物寿命 + 可验证性”写成上循环/放手的判据

可二元验证/短命产物（批量重构、格式迁移、情报抓取去重）→ 可放手循环；改核心不变量、动持久化格式、写要长期维护的 Skill/Contexts → 强制人在环。这也解释了我们为什么规定“写 Contexts 前须用户确认”（CLAUDE.md 规则 2、7）——那类产物是长寿命的。

二 · 警惕我们自己的 Skill 也在“逐轮加局部防御”

直接照进本 Kit 一条铁律——“不为不可能的场景加兜底”“三行相似代码好过过早抽象”。动作：在 vault-evolve 的 review 判据加一问——“这次新增的规则/兜底，是在让坏状态不可能，还是只在给局部失败打补丁？”后者拒绝合入。这篇给了这条铁律一个更锋利的外部论据。

三 · 给“harness 的完成信号”留一个人类可读落点

作者最大的不适是外层循环里连“done”都失去意义、人被降格成信使。我们的 .meta.yaml（skill_run + contexts_missing）就是让循环产出对人保持 legible 的机制。动作：强化这个反馈回路，contexts_missing 累计 ≥2 才由人拍板沉淀——正是作者呼吁的“不放弃判断力”。

四 · 源多样性本身就是“不完全依赖单一机器”的实践
