01 — 文章介绍

两周冲刺站在多年积累之上

Asana 从 2022 年起把前端测试从 Enzyme 迁到 React Testing Library（RTL）。多个团队持续推进后，按原速度仍约需五年。团队随后把剩余工作交给 Codex，用约一周半工程时间、跨两个自然周清除了 Enzyme。

原文依次解释五年问题、实际运行方式、五句话为何足够、阻塞来自哪里，以及为什么 harness 已经成为产品。它没有证明“任意五年项目都能压成两周”，而是展示了一类适合 Agent 的任务形状：目标单一、工作可分区、正确范例已经进入仓库、完成条件可机器验证，人类则集中守住合并边界。

对工程团队，这是一个关于代码库可读性、反馈延迟和迁移组织方式的案例；对负责排期与投入决策的人，更重要的信号是：一些长期积压项目的经济性已经改变，但是否适合交给 Agent，必须先看验证结构，而不是先看模型能力。文章的五个主章节与成本附录共同给出了这种判断所需的正反证据。

证据边界：约 600 万美元是对完整人工范围的粗略估算；$12K 是模型和基础设施成本。两者不是独立审计的同口径对照，也未包含完整人工审查工时。
02 — 知识总结

迁移的不只是 API，而是测试哲学

Enzyme 已失去社区支持、难以适配新版 React，也鼓励测试组件内部实现。RTL 把目标转向用户能看到和执行的行为。因此任务不能靠机械替换 import 完成，Agent 必须从既有 RTL 测试、helper 与约定中判断正确结构。

此前多年推进并非无效。产品团队逐步迁走各自负责的部分，专项工程沉淀了正确范例和工具；这些积累后来变成 Codex 可读取的隐式规格。最终冲刺的吞吐量不能倒推成项目从零开始的速度。

旧测试也不能只做语法层替换。Enzyme 倾向于观察组件内部，RTL 强调用户可见行为；因此 Agent 需要判断测试意图、选择新的查询方式、沿用仓库 helper，并确保迁移后仍覆盖原行为。多年形成的 RTL 代码不是背景材料，而是执行期间最接近真实规范的参考实现。

03 — 运行机制

分目录并行，人类守住合并边界

团队没有搭建复杂调度器。最多四个 Codex Agent 同时工作，每个实例指向不同目录；机器持续在线，工程师每天早晚检查进度并审查 pull request。完整指令只表达目标、规范来源、目录范围、测试命令和优先顺序。

goal.txt
目标：把指定目录中的 Enzyme 测试迁到 RTL
约束：遵循代码库已有规范与最佳实践
范围：一次只处理一个目录
验证：运行指定测试命令
排序：优先迁移容易转换的文件

团队试过 ticket、持续 notes、额外 sub-agent 和更长的 RTL 规范，结果几乎都更差。准确的结论不是“提示词越短越好”，而是：当目标、范例和验证已存在于执行环境，额外协调层会复制状态并增加冲突机会。

五句话分别承担清晰职责：目标限定技术方向，目录限定写入边界，仓库规范提供风格与做法，测试命令构成即时验收，优先简单文件则让 Agent 先建立进展并减少早期阻塞。它们没有承担“解释所有 RTL 知识”的任务，因为那部分知识已经能从真实代码中读取。

这条链路的每一段都不可替代：任务可分区决定并行是否安全；仓库范例决定生成方向；自动检查决定错误能否快速暴露；人类审查承接语义例外和最终责任；“Enzyme 是否清零”则提供清晰、可查询的完成条件。任何一段缺失，都可能把四倍并行度变成四倍返工。

04 — 失败模式

真正的瓶颈是陈旧知识与慢反馈

第一个阻塞来自内部文档和 Agent 指南：部分近期内容仍把 Enzyme 写成推荐模式。对人类，这可能只是需要辨别的噪声；对主动检索并模仿上下文的 Agent，它会成为方向相反的控制指令。

第二个阻塞来自工具：lint 偶尔超过十分钟，本地检查与 CI 也不完全一致。Agent 必须等待反馈才能进入下一轮判断；反馈慢会限制吞吐，反馈不一致会制造“本地通过、远端失败”的无效循环。

原文因此把 harness 定义得很宽：不仅是模型外层的循环，还包括文档、约定、代码范例、测试工具和 CI。它们共同决定 Agent 能看到什么、模仿什么，以及多快知道自己错了。代码里的好品味会被批量复制，糟糕模式也会同样放大；文档过去只是参考资料，现在开始具有控制面的效果。

环境资产正向作用失效方式案例证据
代码范例把工程品味变成可模仿结构坏模式也被放大RTL 测试与 helper 让短指令可行
文档 / 指南提供显式规则和导航陈旧规则主动误导部分内容仍推荐 Enzyme
本地检查快速缩小错误范围运行慢时限制吞吐lint 偶尔超过 10 分钟
CI统一集成判定与本地不一致形成双重真相团队需要人工处理差异
PR 审查承接语义例外与责任容量不足成为新瓶颈工程师每天早晚复核
05 — 证据边界

数字说明机会，但不能直接外推 ROI

结果不仅清除了 Enzyme，还改善测试覆盖、修复质量较差的测试、清理遗留基础设施，并发现一套更老的测试框架。大规模遍历相似工作时，项目范围可能从“替换接口”扩展为“清理整个历史层”。

但文章没有给出测试文件总数、Agent 运行小时数、PR 数量、失败与回滚比例、迁移后缺陷率，也没有完整的人类审查工时。最可靠的结论是：这个成熟仓库里的特定迁移实现了数量级压缩。案例证明可行性与任务适配条件，尚未证明普遍的成本倍数。

Asana 与 OpenAI 还在持续合作，这让案例具有一手工程细节，也意味着数字来自项目参与方。模型和基础设施成本与完整人工成本估算并不是对照实验：后者包含额外测试修复和遗留清理，前者没有展开人类复核成本。更稳妥的读法，是把这些数字当成重新评估积压迁移的触发器，而不是预算模型的默认参数。

五句话不是信息少，而是把信息放在了更接近事实的位置：代码范例、验证命令和明确的完成条件。
06 — 工作流提炼

先把环境做成规格，再提高并行度

先做任务适配确认目标可判定、切片可独立、仓库有正确范例、反馈稳定快速。
文档属于控制面会被 Agent 读取的规则需要新鲜度与权威源检查，陈旧文档是执行风险。
反馈延迟决定容量并行度上升后，最慢检查和人类审查队列会成为共享瓶颈。

AI-Work-Kit 已有承载与真实缺口

Kit 已有需求验收、测试先行、纵向 Story、Gate 和 Contexts 漂移检测，能够约束“做什么”“何时完成”以及长期文档与代码脱钩的一部分风险。缺口不是再造一个四 Agent 功能，而是大规模 Agent 任务启动前的统一 harness readiness 预检：记录可分区边界、完成判据、范例来源、反馈命令、反馈耗时、CI 一致性和人工审查容量。

这个预检应该先作为 workflow checklist 候选进入进化链，而不是直接固化成脚本。它需要回答：切片之间是否共享可变状态；失败能否单独回滚；完成条件是否由命令而非主观描述判定；参考范例是否代表当前方向；验证命令是否足够快且与 CI 同构；人类审查队列能否承接并行产出。只有这些证据齐全，提高并行度才是扩容而非放大不确定性。

自动发现冲突，人类确认权威

预检可以扫描相反范例和陈旧指南，采集检查耗时、本地/CI 差异与重试证据；但关键词不能自动判断一段 Enzyme 内容是历史说明、兼容边界还是错误规范。解释冲突、确认权威源和决定是否优化慢检查，仍应由工程负责人完成。

Kit 的 verified_against 与 contexts_stale 已经覆盖一部分长期资料漂移，但本案例暴露的是更靠近执行时刻的冲突：仓库指南、代码范例与当前迁移目标可能同时存在，Agent 必须知道哪一个具有权威性。机器适合报告冲突位置和引用证据，不适合在缺少语义时自动删改规则。

把反馈回路当作系统容量

并行 Agent 增加后，最慢的 lint、测试与审查会成为共享瓶颈。本地和 CI 不一致还会把每个切片都推入额外重试。可以机器采集的不是一个武断的统一时限，而是单次检查耗时、波动、失败重试、环境差异和审查等待时间；是否足够快、是否值得为迁移专门优化，则由工程负责人结合风险与收益判断。

最终可迁移的是一条工程次序：先把正确范例、权威文档、可执行验收和快速反馈放进环境，再把目标压缩成短指令；先证明切片能独立验证，再提高并行度；最后把人类注意力集中到冲突、例外和合并责任上。
