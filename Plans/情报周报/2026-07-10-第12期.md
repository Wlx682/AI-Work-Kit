# Harness 工程与递归自改进：当部署架构开始优化自身

#### 文章介绍

Lilian Weng 是 OpenAI 应用研究负责人，她的个人博客以高密度研究综述闻名，每篇通常覆盖某一前沿方向的全部关键工作并附系统性归纳。2026 年 7 月 4 日发表的这篇 "Harness Engineering for Self-Improvement" 是一篇约 28 分钟阅读量的长文，主题是：围绕基础模型的部署基础设施——即 harness——如何成为递归自改进（RSI）的实际载体。

文章的核心问题是：递归自改进不仅取决于模型智能本身，更取决于模型被嵌入的系统架构。Harness 负责编排执行、管理上下文、调用工具、存储产物和评估结果，而这些环节本身也可以被优化甚至自我优化。

原文结构如下：

1. 递归自改进的定义与历史（I.J. Good 1965）
2. Harness 设计模式（三种基础模式 + 编码代理案例研究）
3. Harness 优化方法（上下文工程、工作流设计、自改进 Harness、进化搜索、联合优化）
4. 未来挑战（七个瓶颈）
5. 附录：评估基准（六个 Benchmark）

这篇文章值得深挖的原因：它把过去一年散落在不同论文和工程博客中的 harness 优化方法统一到一个递归自改进的框架下审视，提供了从"人写 harness"到"harness 改写自身"的完整谱系，并明确标注了每种方法的边界和失败模式。对于正在构建 AI 工作流系统的团队，这是一份难得的全景地图。

#### 知识总结

##### 递归自改进的现代含义

I.J. Good 在 1965 年提出"超智能机器"概念：一台能超越人类并设计更好后继者的机器。Lilian Weng 将这个经典定义拉回当下语境——现代 RSI 并非发生在"模型自己训练自己"这一步，而是发生在部署系统架构层面：改进训练流水线、改进部署系统，从而产出更强的后继模型。

文章给出的关键定义：

> Harness 是围绕基础模型的系统，负责编排执行并决定模型如何思考与规划、调用工具与行动、感知与管理上下文、存储产物、以及评估结果。

这个定义把"harness"从一个松散的工程术语提升为递归自改进的核心对象——如果 RSI 的目标是让系统变得更好，那么被优化的对象不一定是模型权重，更可能是 harness 代码本身。

##### Harness 设计模式

文章归纳了三种基础设计模式，它们构成后续所有优化方法的底座：

**模式一：工作流自动化**

建立目标导向的循环：规划 → 执行 → 观察/测试 → 改进。文章引用 Karpathy 的 autoresearch 仓库和 Codex 的 agent 循环作为例证，展示迭代轨迹和失败分析如何驱动下一轮行动。这个模式的关键不在于"循环"本身，而在于循环中的评估环节如何决定是否终止或回退。

**模式二：文件系统作为持久记忆**

长时域 agent 系统把持久状态写入文件而非依赖上下文窗口。文章强调"学会读写和编辑文件系统"是 LLM 的基础能力。这意味着 harness 的记忆机制不是对话历史的简单拼接，而是外部化的、可被其他进程（包括后续自改进循环）读取的结构化状态。

**模式三：子代理与后台作业**

Harness 生成并行的子代理进行假设测试和并发实验，强调显式可检视的并行性。结果以文件形式存储，支持中断后恢复。这个模式解决的是单线程 agent 的吞吐瓶颈——通过把猜测和验证解耦到不同进程，harness 可以同时探索多条路径。

**案例研究：编码代理的稳定化接口**

文章观察到主流编码代理（Claude Code、Codex、OpenCode）已经收敛到一组稳定的工具接口：

| 工具类别 | 代表操作 |
|----------|----------|
| 文件系统 | glob, grep, read, write, edit, apply_patch |
| Shell 执行 | bash, PowerShell |
| IO 操作 | LSP, git |
| 外部上下文 | MCP, Skills, web search |
| 后台进程 | 进程管理 |
| 代理委托 | agent delegation |

这张表的意义在于：harness 的工具层已经趋向标准化，差异化竞争正在上移到"如何编排这些工具"——即上下文工程和工作流设计层面。

##### Harness 优化：上下文工程

文章将上下文工程细分为三个递进层次，每层解决不同粒度的问题：

**Agentic Context Engineering (ACE)**

ACE 把上下文视为不断演进的操作手册，而非越来越长的提示词。它由三个组件协作：

- Generator：执行任务，产出轨迹（包括成功和失败的）
- Reflector：从轨迹中蒸馏洞察
- Curator：把洞察更新为结构化条目（标识符 + 描述），而不是重写整段提示词

Curator 的设计决策值得注意：输出结构化条目而非完整提示词重写。这意味着上下文的更新是增量的、可追溯的，不会因为一次失败的重写导致已有知识丢失。

**Meta Context Engineering (MCE)**

MCE 进一步将机制（如何管理上下文）与产物内容（上下文里放什么）分离，使用双层优化：

- 内层：给定一种管理技能，在训练数据上找最优上下文
- 外层：在验证数据上找最优管理技能

这是一个经典的 bi-level optimization 结构。它的价值在于认识到"上下文管理策略"本身也是可优化的超参数，而不是一次性的人工设计。

**Meta-Harness**

最高层级：优化"决定什么信息被存储、检索和呈现"的代码本身。使用编码代理作为提案者，在帕累托前沿上生成 harness 候选方案，执行历史通过文件系统可访问。

三层递进关系可以这样理解：ACE 优化上下文内容，MCE 优化管理上下文的策略，Meta-Harness 优化产出管理策略的代码——每一层都把下一层当作搜索空间中的一个点。

##### Harness 优化：工作流设计

文章介绍了五个代表性系统，展示"工作流本身如何被系统化设计甚至自动搜索"：

| 系统 | 核心机制 | 问题 | 证据/局限 |
|------|----------|------|-----------|
| AI Scientist | 想法→代码→实验→分析→论文→同行评审的完整管线 | 端到端自动化科研 | 完整管线验证；未报告可复现率 |
| ScientistOne | 每个主张必须追溯到证据源（引用/数据/方法） | 科研工作流的可验证性 | 强调证据可追溯；依赖人工验证的金标准 |
| Autodata | 挑战者/弱解/强解/验证者四角色协作合成训练数据 | 自动生成适当难度的训练/评估数据 | 角色对抗保证质量；规模化成本未报告 |
| ADAS | 将 agent 设计形式化为优化问题，元代理以代码形式提出新工作流 | 自动设计 agent 系统 | 在已有方案基础上变异；搜索空间爆炸 |
| AFlow | 工作流表示为图（节点=LLM 调用，边=逻辑操作），用 MCTS 优化 | 工作流结构搜索 | 图结构+MCTS 验证有效；长程依赖处理未明 |

ADAS 和 AFlow 的共同启发是：工作流不必是人类一次性设计出来的，它可以是搜索空间中的一个解——前提是你能把工作流表示为可操作的数据结构（代码或图）。

##### Harness 优化：自改进 Harness

这是文章最核心的部分——harness 不再由人优化，而是自己优化自己。

**Self-Taught Optimizer (STOP)**

STOP 实现了"改进改进器本身"的递归：

- 种子改进器接收解、效用函数和 LLM
- 元效用度量下游任务的平均效用
- 自改进更新公式：`I_t = I_(t-1)(û, I_(t-1); M)`

即第 t 轮的改进器，是上一轮改进器对自身施加改进操作的产物。这是递归自改进在代码层面的直接实现。

关键警示发现：STOP 在 GPT-4 上提升了性能，但在更弱的模型上反而退化。这说明递归自改进有一个能力地板——基础模型必须足够强才能有效地"理解并改进自己的改进策略"。弱模型在自改进循环中会积累错误而非消除错误。

**Self-Harness**

采用提议-评估-接受循环：

1. 弱点挖掘：将失败聚类为验证器锚定的模式
2. Harness 提议：基于失败模式建议有界编辑
3. 验证：在留入和留出数据上测试编辑，检查回归

"有界编辑"是关键设计——不是让模型重写整个 harness，而是在失败模式锚定的范围内做局部修改。这限制了搜索空间，也限制了灾难性回归的风险。验证阶段使用留出数据防止过拟合，这与传统软件工程中的回归测试思路一致。

##### Harness 优化：进化搜索

进化搜索方法将 harness 优化类比为生物进化——维护种群、施加变异、按适应度选择：

**Promptbreeder**

通过变异操作优化任务特定提示词，变异提示词本身也在进化。这是两层进化：内层优化任务提示词，外层优化变异策略。

**AlphaEvolve**

维护候选程序池，冻结的 LLM 生成代码差异（diff）进行改进。值得注意的设计：代码中用 `# EVOLVE-BLOCK-START` 和 `# EVOLVE-BLOCK-END` 标记可进化区域，限制了 LLM 的修改范围。这是一种"可控进化"——不是任意位置都可以变异，而是人类预先划定哪些代码块参与进化循环。

**Darwin Gödel Machine (DGM)**

明确以 harness 代码仓库为进化目标，允许 agent 修改自己的基础设施代码。这是本文所有方法中最激进的——self-modification 的对象不限于提示词或工作流配置，而是整个运行时代码。

**Hyperagents**

引入元代理控制如何修改现有任务代理，按性能正比、后代数反比选择父代。这增加了一层"进化策略的进化"——不只是谁活下来由适应度决定，怎么繁殖也在被优化。

四个进化方法的递进关系：

```
Promptbreeder: 进化提示词
    ↓ 扩大进化对象
AlphaEvolve: 进化标记区域内的代码
    ↓ 扩大进化范围
DGM: 进化整个 harness 代码仓库
    ↓ 增加元层
Hyperagents: 进化"如何进化"的策略本身
```

##### Harness 优化：联合优化（权重 + Harness）

**SIA** 将 harness 改进与模型参数更新结合：

- Meta-Agent：提出初始 harness
- Task-Specific Agent：执行任务
- Feedback-Agent：根据轨迹决定更新 harness 还是更新权重

这解决了一个根本问题：当任务失败时，是 harness 的编排有问题，还是模型的能力不足？SIA 的 Feedback-Agent 试图做这个归因判断，然后路由到正确的优化通道。

##### 七个未来瓶颈

文章在展示了优化方法全景后，诚实地列出了七个尚未解决的瓶颈。这些不是"未来方向"式的客套，而是当前方法的硬边界：

| 瓶颈 | 问题本质 | 为什么难 |
|------|----------|----------|
| 弱而模糊的评估器 | 研究品味、新颖性、科学价值难以客观度量 | 与代码正确性不同，无精确指标可优化 |
| 上下文与记忆生命周期 | 记忆管理必须补充长上下文的局限 | 什么该记、记多久、何时遗忘缺乏理论 |
| 负面结果 | 文献偏向成功，LLM 难以学会放弃假设和报告失败 | 训练数据中的幸存者偏差 |
| 多样性坍缩 | 进化循环利用已知模式，开放式研究需要多样性 | 选择压力天然减少变异 |
| 奖励黑客 | 自改进循环优化给定信号，可能走捷径 | 需要优化循环外的留出测试和人类监督 |
| 长期成功 | 外在优化处理沙箱奖励，忽略可维护性、所有权边界、向后兼容、调试负担 | 短期指标与长期质量目标冲突 |
| 人类角色 | 人类应上移到合适的抽象层提供监督，而非被移出循环 | 抽象层的正确位置随能力增长动态变化 |

几个特别值得注意的点：

"弱而模糊的评估器"是整个 RSI 框架的阿喀琉斯之踵——前面所有优化方法都假设存在一个可计算的效用函数，但真实世界中最有价值的任务（研究、设计、战略决策）恰恰缺乏这样的函数。

"长期成功"瓶颈直接挑战了"用 benchmark 驱动自改进"的范式。Benchmark 能度量的是沙箱内的即时表现，但真正的工程成功还包括可维护性、所有权边界、向后兼容性和调试负担——这些属性只在时间尺度上才能观测，无法在一次评估中捕获。

"人类角色"的表述很审慎：不是"人类不再需要"，而是"人类应该上移到合适的抽象层"。随着系统能力增长，合适的抽象层也在变化——这意味着人类监督的设计不能是静态的。

##### 附录：评估基准

文章用六个 Benchmark 量化了当前 agent 系统的真实水平：

| Benchmark | 规模 | 最佳成绩 | 基线对照 |
|-----------|------|----------|----------|
| PaperBench | 复现 20 篇 ICML 2024 论文，8316 条评分规则 | ~21% | ML PhD 学生表现更好 |
| CORE-Bench | 90 篇论文的 270 个可复现任务 | 最难子集 ~21% | — |
| ScienceAgentBench | 44 篇出版物的 102 个数据科学任务 | — | 四个学科跨度 |
| RE-Bench | 7 个 ML 研究工程环境 | agent 在 2 小时预算下得分是人类 4 倍 | 但 8-32 小时预算下人类反超 agent |
| MLE-bench | 75 个 Kaggle ML 竞赛 | 最佳配置在 16.9% 竞赛中达到铜牌水平 | — |
| KernelBench | 250 个 PyTorch GPU 核心任务 | 评估正确性和速度 | — |

RE-Bench 的发现尤其有启发性：agent 在短时间预算内效率极高（2 小时得分是人类 4 倍），但随着时间预算增加到 8-32 小时，人类反超。这暗示当前 agent 擅长快速执行已知模式，但在需要深度思考、回溯和重新框定问题的长时域任务上仍然不如人类。这恰好对应了"弱评估器"瓶颈——短任务有清晰的成功标准，长任务需要判断力。

PaperBench 的 ~21% 复现率说明：即使在有明确目标（复现已发表论文）的情况下，当前最强 agent 也远未达到专业研究者的水平。8316 条评分规则的精细粒度让我们能看到，失败不是"全错"而是"部分对"——这为自改进提供了精确的失败信号。

#### 工作流提炼

##### 通用设计原则萃取

从文章中 20+ 系统的共性和 7 个瓶颈中，可以抽象出以下不绑定具体产品的系统设计原则：

**原则一：优化对象可以上移**

从优化模型权重 → 优化提示词 → 优化 harness 代码 → 优化"优化 harness 的策略"，每一层都把下一层当作搜索空间中的一个点。设计系统时值得问：当前的瓶颈是模型能力不足，还是编排逻辑不对？如果是后者，优化 harness 比换模型更有效。

**原则二：有界编辑优于全量重写**

Self-Harness 的核心设计是"基于失败模式建议有界编辑"而非重写整个系统。AlphaEvolve 用标记块限定进化范围。这背后的共识是：自改进系统需要控制变更的爆炸半径——每次只改失败锚定的局部，用回归测试兜底。

**原则三：机制与产物分离**

MCE 将"如何管理上下文"与"上下文里放什么"分离为两层。这个原则的通用表述是：管理策略和被管理的内容应该独立演化，否则改策略时会意外破坏内容，改内容时会绕过策略。

**原则四：评估器的质量决定自改进的天花板**

七个瓶颈中"弱而模糊的评估器"排第一不是偶然——STOP 在弱模型上退化、奖励黑客、长期成功无法度量，本质上都是评估信号不足的表现。系统设计应优先投资评估能力，而非生成能力。

**原则五：人类监督层应随能力增长动态上移**

文章明确反对"移除人类"，主张"上移到合适的抽象层"。这意味着人机协作的接口不是一次性设计，而是需要随系统能力变化而重新校准的。

##### 小结

这篇综述的最大价值不在于介绍了哪个具体系统可以复用，而在于提供了一个分析框架：把任何 AI 工作流系统的改进路径分解为"优化什么层级 × 用什么搜索策略 × 用什么评估信号"三个正交维度。当 Kit 的某个环节表现不佳时，可以用这个框架定位：是该优化 Skill 内容（产物层），还是优化 Skill 的调度策略（机制层），还是优化"如何决定何时优化"（元层）。

当前最可落地的启发是"评估器质量优先"——Kit 的反馈回路已经有 contexts_missing 做缺口识别，但缺少对 Skill 执行质量的主动回归评估。这不需要复杂的自改进循环，只需要在 workflow-evolution 的聚合环节增加一个"本周期 Skill 产物质量是否回归"的检查点。具体形态待 feedback-aggregate 跑出足够数据后再定。
