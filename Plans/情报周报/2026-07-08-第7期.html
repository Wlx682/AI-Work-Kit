01 — 主题

那堵所有通用智能体都会撞的墙

让 Claude 填一张 PDF 表单、按公司规范写周报、走一套内部发布流程——这些知识不在模型权重里，得由你喂进去。老办法是为每个场景单独造一个定制智能体：改系统提示词、塞一堆工具、把边界情况一条条写死。结果每个智能体都成了一次性的手工艺品，彼此不能复用、不能组合、换个平台就报废。

Anthropic 工程团队的答案，是把“领域知识”从提示词里剥出来，装进一个普通文件夹——里面放一份 SKILL.md 说明书、几个脚本、几份参考资料。智能体在运行时自己发现它、按需加载它。他们给这套东西起名 Agent Skills，并已在 2025 年 12 月把它开放成跨平台标准。

i
作者的比喻很朴素：给智能体做一个技能，就像给新入职的同事写一份入职手册。你不会第一天就把公司所有制度倒给新人——你给他一份目录，让他用到哪一章翻哪一章。全文的技术分量，就压在这个“按需翻页”的机制上。
02 — 想法（全篇重心）

渐进披露：把知识分三批送进上下文

最简单的技能就是一个目录，里面有一个 SKILL.md。它必须以 YAML 头开场，只有两个必填字段：name 和 description。关键在于三个层次是分批进入上下文的，而不是一股脑全塞。作者把这套机制叫 progressive disclosure（渐进披露），它是整个 Agent Skills 设计的核心。

  • 第一级·元数据：启动时只把每个技能的 name 和 description 预加载进系统提示词。够 Claude 判断“这个技能什么时候该用”，但不占多少上下文。
  • 第二级·正文：Claude 判断某技能跟当前任务相关，才用 Bash 工具去读它完整的 SKILL.md。
  • 第三级及以后·附带文件：技能复杂到一个文件装不下时，拆成多个文件（如 forms.md）按名字引用。Claude 只有真的要填表单了，才会去读 forms.md。

为什么要费劲分三级？因为智能体有有限的注意力预算。把一个技能的全部内容无差别塞进上下文，注意力就被稀释，真正关键的指令反而被淹没。渐进披露的妙处在于——因为智能体有文件系统和代码执行能力，一个技能里能打包的上下文事实上没有上限：反正没用到的部分永远不进上下文。这句话把“上下文窗口有多大”和“技能能装多少知识”彻底解耦了。

注意一个容易被忽略的设计选择：加载技能靠 Claude 自己调 Bash 工具去读文件，而不是一套专门的“技能加载”系统机制。技能就是文件系统里的普通文件夹，加载它就是普通的读文件。这份简单是刻意的——正是它让组织、开发者、终端用户都能轻松造自己的技能。

04 — 代码 · 开发 · 安全

代码既是工具，又是文档

技能里还能放代码，让 Claude 按需当工具执行。作者点出一个常被忽视的道理：某些操作交给传统代码更划算。给列表排序，用 token 生成远比跑一个排序算法昂贵；更重要的是，很多场景需要只有代码能提供的确定性可靠性。

PDF 技能就带了一段 Python 脚本，读 PDF、抽取所有表单字段。Claude 可直接运行它，既不用把脚本读进上下文，也不用把 PDF 读进上下文。这里藏着一个双关：同一份代码，既能被 Claude 当工具执行，也能被读进上下文当参考文档——所以要写清楚到底让 Claude 跑脚本还是读脚本，否则它会拿不准。

建议要点

为规模而拆分SKILL.md 臃肿了就拆文件；互斥/罕用的上下文分开放，能省 token

和 Claude 一起迭代让它把成功做法、常犯的错沉淀成技能；这样能发现它真正需要什么，而不是去猜
!
安全边界不能略过：技能通过“指令+代码”给新能力，也意味着恶意技能可能引入漏洞、诱导泄露数据。只从可信来源装；来源存疑时逐个文件审计，特别留意代码依赖与连外部网络的指令。我们的 Skill 就带 scripts/，这条尤其相关。
更远的野心：让智能体自己创建、编辑、评测技能，把自己的行为模式固化成可复用的能力——今天是人给智能体写入职手册，将来是智能体自己写、自己改、自己验收。
05 — 结论

最该记住的一句话，和它的边界

渐进披露让“技能能装多少知识”和“上下文窗口有多大”彻底解耦。因为智能体有文件系统和代码执行能力，没用到的知识永远不进上下文，所以一个技能能打包的上下文事实上没有上限。它成立的边界也要说清楚：

  • 依赖文件系统 + 代码执行。没有这两样（纯 API 无沙箱），二三级披露无从谈起，退化成“要么全塞、要么不给”。
  • name/description 是触发命门。第一级完全押在这俩字段——描述写糊了，该触发的技能不触发，再好的正文也是死文件。
  • 简单是特性，不是缺陷。技能就是普通文件夹、加载就是读文件，别急着套复杂加载框架，那会废掉它最大的优点：谁都能造、谁都能审。
06 — 复用

这篇文章，几乎是逐点在给我们做体检

AI-Work-Kit 本身就是一套 Skill 体系。对照官方做法，有四个具体改动落点：

一 · Skill 正文该瘦身，互斥场景拆成按需加载文件

官方 SKILL.md 只留决策骨架，把“怎么填表单”这类互斥/罕用路径拆到 forms.md。反观我们的 weekly_intel_digest.md 有 200 多行，把“怎么挑/怎么排版/写作规范/自查清单”全塞在一份文件里。动作：把长 Skill 的互斥段落（如 figma-ui 的“业务门禁”vs“纯 UI 长文页”）拆成独立文件，主 SKILL.md 只留“何时读哪个”的路由骨架。

二 · 把 description 当触发命门经营

我们的 Skill 路由硬规则（CLAUDE.md 规则 4）同样押在 description 上。动作：给每个 Skill 的 description 做一次“从 Claude 视角”的复审，触发词与排除项（“不响应：xxx→yyy”）要写得像给新同事的说明书那样无歧义。weekly-intel-digest 已这么做，应推广到全部 Skill。

三 · scripts/ 标注双重身份并补安全审计

我们的 plan-gate-check.sh、sync-claude-skills.sh 就是 Skill 带的代码。动作：在引用脚本的 Skill 里写清“让 Agent 直接跑”还是“读进来当参考”；并对会连外部网络或改全局配置的脚本做一次审计留档。

四 · 把“智能体自己造技能”接到已有进化回路

每期 .meta.yaml 的 contexts_missing 就是“读这篇暴露 Kit 缺什么”的自我诊断，喂给 feedback-aggregate → vault-evolve。动作：把官方“从评测开始、针对缺口增量造技能”写进 workflow-evolution-assistant 的沉淀判据——先有 contexts_missing 累计 ≥2 的证据，再增量造。读这篇暴露的缺口本身就是一条：我们缺一份《Skill 分级拆分规范》。
