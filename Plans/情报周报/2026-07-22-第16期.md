# Agent PR 已进入 2,361 个项目，但 88.7% 仍由单人把关：AI 编程的瓶颈开始转向组织

#### 文章介绍

2026 年 7 月 16 日，Rochester Institute of Technology 的 Maliha Noushin Raida 与 Daqing Hou 发布论文《Early Adoption of Agentic Coding Tools by GitHub Projects》。论文已被 KDD 2026 的 Agentic Software Engineering（SE 3.0）Workshop 接收，研究对象不是实验室 benchmark，也不是厂商自报的使用量，而是 GitHub 上真实发生的 Agent Pull Request。

作者试图回答三个项目级问题：Agent 编程工具究竟被采用到什么程度；每位参与者需要管理多少 Agent PR；人类在审核、修改和合并 Agent 代码时形成了怎样的协作结构。此前研究多关注单个 PR 是否被合并、Agent 代码与人类代码有什么差异，或某项任务完成得更快还是更慢。本文把观察单位提升到仓库和团队，追问一个更接近组织落地的问题：即使 Agent 已经能开 PR，一个项目是否真的建立了持续使用和吸收这些贡献的能力。

论文使用公开的 AIDev-pop 数据集，筛选 2025 年 5 月至 7 月间由 GitHub Copilot、OpenAI Codex 和 Claude Code 创建、且结果已经可观察的 25,264 个 Agent PR，覆盖 2,361 个至少拥有 100 颗 GitHub Star 的活跃仓库。作者进一步通过 GitHub API 获取贡献者规模，并将项目分为小型团队（1–5 名贡献者）、中型团队（6–15 名）与大型团队（16 名以上），再从 commit、review、comment 和 timeline event 中还原人类参与者。

研究得到的主结论带有明显反差：Agent 工具已经出现在数千个项目中，但典型仓库三个月只有 1–2 个 Agent PR；只有 1% 的项目超过论文采用的“每位参与者三个月 36 个 PR”参照线；78.9% 的 Agent PR 由同一个人同时修改和审核，全部单人监督模式合计达到 88.7%。换句话说，Agent 的生成能力已经进入现实工程，但广泛采用、稳定吞吐与团队化监督还远未同步发生。

这篇论文值得读，是因为它把讨论从“Agent 能写多少代码”转向“项目能管理多少 Agent 贡献”。技术团队能从数据口径、参与者识别和协作类型中看到可观测指标；产品、管理和流程设计者则能看到，推广工具与建立组织能力是两件不同的事。原文也诚实限定了结论：样本只覆盖热门开源项目、三种 Agent 和三个月窗口，PR 数量不能等同于质量、价值或开发生产力。

原文地址：https://arxiv.org/html/2607.14037v2

#### 知识总结

##### 原文地图：从 PR 结果走向项目采用

论文共七个主体章节。引言提出项目级采用缺口与三个研究问题；相关工作梳理 Agent PR、生产力和人机分工研究；方法章节说明数据筛选、人类参与者识别、团队规模分组和五种协作模式；结果章节分别回答采用广度、每位参与者的 Agent PR 活动量与协作结构；讨论把三组发现汇总为组织吸收问题；有效性威胁限定样本、识别和指标边界；结论重申 Agent 能力必须与审核和治理流程共同演进。

| 研究问题 | 观察单位 | 核心指标 | 作者真正想判断的事情 |
|---|---|---|---|
| RQ1：采用程度 | 仓库、贡献者 | 人类参与率、仓库 Agent PR 数 | 工具是广泛进入日常流程，还是只被少数人试用 |
| RQ2：项目级活动量 | 仓库、Agent 流程参与者 | 三个月 Agent PR / 人类参与者 | 一个项目的参与者实际管理了多大规模的 Agent 贡献 |
| RQ3：协作结构 | 单个 Agent PR | reviewer 与 committer 的人数和身份关系 | 监督责任落在个人，还是形成团队化分工 |

这里最重要的方法变化，是不再把“检测到一个 Agent PR”直接当成“项目完成采用”。作者同时看项目中有多少人参与、产生多少 PR，以及这些 PR 由谁审核和修改。采用因而从二元安装状态变成三个相互制约的维度：覆盖面、活动强度和监督结构。

##### 数据集：真实工作流比受控 benchmark 更接近组织问题

AIDev-pop 原始数据包含 2,807 个热门仓库的 33,596 个 Agent PR。本文只保留 2025 年 5–7 月创建、已经合并或关闭、能够获取贡献者信息的样本，最终得到：

| 数据项 | 数量或范围 | 用途 |
|---|---:|---|
| Agent PR | 25,264 | 分析采用、活动量与人机协作 |
| GitHub 仓库 | 2,361 | 项目级比较 |
| Commit | 291,866 | 识别人类是否修改 Agent 代码 |
| 观察窗口 | 2025 年 5–7 月 | 保证所有项目处于同一三个月周期 |
| Agent | Copilot、Codex、Claude Code | 覆盖三种主流 Agent PR 来源 |
| 项目门槛 | 至少 100 Stars 且活跃 | 聚焦有现实维护活动的热门开源项目 |

这套数据的价值在于包含 PR、commit、review、review comment 和 timeline event，能够还原从 Agent 提交到人类审核、修改、关闭或合并的生命周期。受控 benchmark 擅长测模型能否完成既定题目，却很难回答谁承担审核、一个团队能否持续吸收生成结果，以及真实项目是否把工具变成日常流程。

但真实数据并不天然等于精确因果。论文观察到的是已经发生的 GitHub 活动，无法证明团队规模导致采用差异，也无法看到未进入 GitHub 的本地交互、被放弃的尝试或私有仓库实践。它更适合描述早期采用结构，而不是给任何组织预测采用结果。

##### 人类参与者如何被识别

作者没有把 PR 页面上的一个 reviewer 当作全部人类监督，而是连接多类 GitHub 记录：

1. 从 PR 表取得 Agent 标签、生命周期状态和时间。
2. 从 commit detail 提取作者、提交者与提交信息；包含 codex、claude、copilot、bot、github 等 Agent 或自动化标识的 commit 被排除，其余 distinct committer 视为人类代码贡献者。
3. 从 review 和 review comment 识别正式审核者与讨论参与者。
4. 从 timeline event 获取合并、关闭等生命周期动作的执行者。
5. 合并所有角色，再过滤 `[bot]`、web-flow、mergify、sre-ci-robot、cursor 等自动化账号，形成每个 PR 的 distinct human participant set。

这个参与者集合有两个用途：一是判断某个仓库有多少贡献者真正进入 Agent 工作流，二是用参与 Agent PR 的人数归一化 PR 活动量。它比简单统计 Agent PR 总数更合理，因为一个拥有数百名贡献者的大仓库和一个只有两人的项目，不应直接比较绝对数量。

识别方法也有误差边界。关键词过滤可能漏掉没有明显 bot 标识的自动化账号，也可能把名称恰好包含关键词的人类账号排除。timeline actor 代表参与了生命周期动作，却不一定完成了实质性技术审核。因此“人类参与”应理解为可从 GitHub 工件观察到的互动，而不是完整的认知投入。

##### 团队规模与活动量指标

论文通过 `/repos/owner/repo/contributors` 获取默认分支上至少有一次 commit 的非 bot 账号，把它作为项目团队规模代理。最终样本包括 343 个小型项目、456 个中型项目和 1,562 个大型项目。

作者为 RQ1 定义两项互补指标：

\[
Participation\ Ratio = \frac{参与至少一个 Agent\ PR 的贡献者数}{仓库非 bot 贡献者总数}
\]

以及三个月内每个仓库的 Agent PR 数。前者测“参与有多广”，后者测“活动有多强”。只看其中一个会产生误导：小团队可能参与率很高但总量不大；大团队可能绝对 PR 较多，却只由极少数先行者使用。

RQ2 使用 `Agent PR / 人类参与者` 作为项目级 Agent PR productivity 的代理。这个名字容易被过度解读，作者明确指出它只代表每位参与者生成和管理的贡献量，不包含 PR 大小、复杂度、质量、审核成本或最终价值。因此，更准确的中文理解是“每位参与者对应的 Agent PR 活动量”，而不是完整生产力。

##### 五种协作模式：同一个人既修改又审核占绝对多数

作者按 reviewer 与 committer 的人数和身份关系，将 Agent PR 归入五类主要模式：

| 模式 | Agent 是否独立写代码 | 人类分工特征 | 治理含义 |
|---|---|---|---|
| 1 名 reviewer，无人类 committer | 是 | 一个人审核，Agent 输出原样进入后续流程 | 审核集中，但代码责任边界相对清楚 |
| 1 名 reviewer + 1 名 committer，同一人 | 否 | 同一个人修改 Agent 代码并审核 | 个人闭环，缺少职责分离 |
| 1 名 reviewer + 1 名 committer，不同人 | 否 | 修改与审核由不同人承担 | 接近传统双人制约 |
| 1 名 reviewer + 多名 committer | 否 | 多人共同修改，由一人集中审核 | 修改分布、审核集中 |
| 多名 reviewer，无人类 committer | 是 | 多人审核 Agent 原始输出 | 团队共审，但无人工改码 |

数据中最常见的是“同一人既修改又审核”，共有 19,488 个 PR，占 78.9%。第二常见的是“一名 reviewer、无人类 committer”，共有 2,476 个 PR，占 9.8%。两种单人监督模式合计 88.7%；涉及两名及以上人类的模式只有 11.3%。

这不是说 88.7% 的 PR 没有任何检查，而是监督责任高度集中在一个人身上。Agent 并未消除人类整合工作，只是把生成、修改、判断和责任重新压到一个开发者的局部闭环中。大型项目的多人与职责分离比例略高，但单人监督依旧占主导。

##### RQ1：工具已出现于数千仓库，日常采用仍集中在少数人

2,361 个仓库中，998 个项目的参与率低于 5%，占 42.27%；1,657 个低于 20%，占 70.18%；1,776 个低于 30%，占 75.22%。也就是说，在超过三分之二的项目中，不到五分之一贡献者参与过 Agent PR。

团队规模与参与率之间存在显著关系。论文在数据不服从正态分布后采用 Kruskal–Wallis 非参数检验，并报告大效应量：约 61.6% 的参与率差异与项目规模分组相关。Dunn 事后检验显示小、中、大三组两两差异均显著；将分组边界改为 1–20、21–100、100+ 后，结论仍保持，说明结果不依赖唯一一套团队规模定义。

小项目的平均 Agent PR 数为 50.2，远高于中型项目的 5.6 和大型项目的 6.7；但所有规模的中位数都只有 1–2。平均数与中位数的巨大差距说明分布极度偏斜：少量非常活跃的仓库拉高了均值，典型项目仍处在试用或零散采用阶段。不能用平均 50.2 推断一般小团队都会高频使用 Agent。

大项目的 PR 数分布更宽，说明大型仓库之间差异更大；小项目虽然总体参与率高，也只有少数项目产生极大量 PR。研究能证明项目规模与参与结构相关，但没有识别原因。审批层级、维护者容量、代码所有权、风险承受度、任务类型和工具接入方式都可能是中间变量。

##### RQ2：只有 1% 的项目越过 36 PR 参照线

作者引用行业观察，把“每位开发者三个月 36 个 PR”画成上下文参照线，并反复强调它不是普适生产力标准。在 2,361 个项目中，只有 25 个，也就是约 1%，超过每位 Agent 工作流参与者 36 个 Agent PR。绝大多数项目低于这条线。

一人或少数人参与的项目离散程度最大：有的只有少量 Agent PR，有的达到数百。参与人数增加后，项目更多聚集在较低的每人活动量区间。这提示高吞吐可能依赖少数人对 Agent 工作流的深度熟练，也可能只是小团队的分母较小；论文没有足够数据区分工作流质量、任务可并行性和统计分母效应。

更重要的是，这个指标测的是“生成并管理了多少 PR”，没有测 PR 是十行文档修改还是大型功能，没有测审核耗时、缺陷率和上线价值，也没有减去 Agent 带来的额外返工。它能反驳“只要部署工具就会自然出现高吞吐”，却不能证明超过 36 就代表高质量团队。

##### RQ3：Agent 时代的默认组织形态仍是个人监督

78.9% 的“同一人修改并审核”模式表明，当前 Agent PR 最常被当作个人生产工具，而不是新的团队成员。开发者向 Agent 委托任务，然后自己修正输出、自己判断是否可合并。这个结构启动成本低、反馈快，尤其适合小团队；但当 Agent PR 数上升时，生成速度和个人审核容量会形成新的不对称。

多人的职责分离只占少数，说明传统工程中的双人复核、代码所有者、领域专家与发布责任并未自动迁移到 Agent 工作流。大团队虽然更常出现分布式协作，仍没有改变主导模式。这支持论文的核心判断：成功集成取决于人类和组织流程，而不仅是 Agent 能力。

单人监督本身不一定错误。低风险、可回滚、测试充分的改动由一人闭环，可能是合理的效率选择。问题在于项目是否显式按风险分层，还是所有 Agent PR 都因默认工作流而落到同一个人身上。论文没有评价各种模式的质量差异，因此不能从 88.7% 直接推出“单人审核导致更差结果”；它提供的是治理结构的基线，而不是因果结论。

##### 有效性威胁：这是一张早期快照，不是行业全景

| 局限 | 可能造成的偏差 | 阅读时应保留的边界 |
|---|---|---|
| 只含至少 100 Stars 的热门开源仓库 | 排除长尾、私有和企业项目 | 不外推为所有软件团队的采用率 |
| 只含 Copilot、Codex、Claude Code | 忽略其他 Agent 与自研工具 | 结论属于三种主流来源的早期实践 |
| 只观察 2025 年 5–7 月 | 模型与产品迭代很快 | 这是时间切片，不是长期趋势 |
| 依赖关键词识别 bot 与人类 | 可能误识别参与者 | 人数与协作模式存在测量误差 |
| contributor count 代理团队规模 | 历史贡献者不等于活跃决策者 | 规模是近似分组，不是组织结构 |
| PR / participant 代理生产力 | 不含大小、质量、价值和审核成本 | 只能解释为活动量，不能当 ROI |

作者没有分析哪些项目因素导致高采用，也没有比较五种协作模式的合并率、缺陷率或审核质量。这些未回答的问题恰好构成下一阶段研究方向：持续追踪采用演化，把项目治理、工作流设计和审核容量与质量结果连接起来。

#### 工作流提炼

##### 原则一：把“工具出现”与“工作流采用”分成不同状态

原文中，数千仓库出现 Agent PR，但典型仓库三个月只有 1–2 个，且大多数项目只有少数贡献者参与。通用原则是采用不能用安装、授权或单次成功表示，至少要区分发现、试用、重复使用、多人扩散与稳定治理。

AI-Work-Kit 已有 Epic、workflow run、事件日志和 `skill_run`，能够记录一次流程是否完成；缺口是缺少 workflow adoption 指标，无法区分某个 Skill 被一个人反复使用、被多人偶尔试用，还是已经成为团队默认路径。合适的落地形态是聚合视图：按周期统计 unique user、repeat run、success gate、人工回退和跨角色参与，而不是新增一套复杂状态机。

迁移边界是不要用运行次数直接评价个人绩效，也不要因为使用率低就自动淘汰 Skill。低频高价值流程本来就不会高频触发；采用数据应服务流程改进和培训决策，需要结合任务类型由人解释。

##### 原则二：吞吐指标必须绑定审核容量与质量成本

论文只有 1% 项目越过 36 PR 参照线，同时提醒 PR 数不是完整生产力。通用原则是生成吞吐不能脱离吸收能力评价：Agent 创建更多候选，只在审核、测试、返工和发布风险没有失控时才形成净收益。

Kit 已有测试 plan、code review、NFR、部署门禁和 WBS 证据，可承载质量检查；缺口是这些门禁与 Agent 生成量之间没有统一的 flow efficiency 视图。可补充 `agent_outputs_created`、`human_review_minutes`、`rework_cycles`、`gate_reject_rate` 与 `accepted_value` 等聚合字段，形成从生成到吸收的漏斗。

这些字段不应强制每次手填，也不能把 PR 数或 token 数设成目标。优先从 Git、测试和 workflow event 自动取证；“业务价值”和复杂度仍需人工判断，避免指标成为刷小 PR 的激励。

##### 原则三：单人闭环是默认态，职责分离应按风险触发

88.7% 的 Agent PR 由单人监督，说明团队不会因为引入 Agent 就自然形成新的制衡结构。通用原则不是禁止单人闭环，而是让监督强度随变更风险上升：低风险改动允许一人完成，高风险变更要求独立 reviewer、领域 owner 或发布批准者。

Kit 已有破坏性动作审批、Contexts 写入确认、code review 和部署阶段；缺口是缺少统一的 agent-generated change risk classification，使职责分离依赖各 Skill 自己判断。可在 workflow gate 增加风险因子：权限与凭证、数据迁移、公共 API、跨模块影响、不可逆外部写入和安全边界。命中高风险时要求 reviewer 与 implementer 不同，或至少增加独立验证证据。

迁移边界是小团队未必有足够人员实施严格双人制。此时可以用独立测试、第二模型 review、延迟发布和可回滚机制部分补偿，但不能把“另一个 Agent 看过”自动等同于人类独立责任。

##### 原则四：先观测参与结构，再设计推广和培训

小项目参与率更高、大项目使用更集中，且规模分组解释了大部分参与率差异。通用原则是组织推广不能只有统一安装指南：小团队的瓶颈可能是验证能力，大团队的瓶颈可能是权限、所有权、跨角色协调和局部先行者无法扩散。

Kit 的 follow、Skill 文档和 workflow-router 能帮助发现与进入流程，但缺少 adoption cohort 视角。可按团队规模、角色、仓库风险和熟练度查看首用到复用的转化，识别卡在权限、上下文准备、测试门禁还是 review 阶段。是否调整培训和默认流程仍由负责人决定，数据只提供定位证据。

##### 原则五：指标名称必须携带测量边界

论文把 PR / participant 称为 productivity，同时在方法和局限中明确它只是活动量代理。这揭示一个普遍风险：指标名称会比脚注传播得更快，最终把代理量当成目标本身。

Kit 在 `skill_run`、WBS 和周报中已经强调证据，但缺少 metric contract。凡进入看板或复盘的关键指标，应同时记录定义、观察窗口、分母、数据来源、未覆盖内容和禁止解释。例如 `agent_pr_per_participant` 必须注明“不代表质量、复杂度或 ROI”。合适的落地形态是 Context 中的指标契约模板与看板 tooltip，而不是在每篇报告重复长段免责声明。

这篇研究最有价值的不是证明 Agent 普及得快或慢，而是提供了一套组织级观察框架：覆盖多少人、产生多少可管理贡献、监督责任如何分布，以及指标不能解释什么。Agent 能力继续提升后，真正稀缺的资源会逐渐从生成 token 转向清晰责任、验证证据和团队吸收能力。
