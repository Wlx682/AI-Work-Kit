Zig 时代的稳定性债务

01 — WHY REWRITE

问题不是 Zig 失败，而是稳定性阶段需要不同约束

Bun 起初靠 Zig 快速完成了一个范围极大的 runtime：transpiler、bundler、package manager、test runner、Node.js API、HTTP/WebSocket 等都在同一系统里。到这篇文章发布时，Bun CLI 已有超过 2200 万月下载量，Claude Code 和 OpenCode 也把它作为 runtime。

真正推动迁移的是稳定性债务。原文列出的 bug 样本集中在 use-after-free、out-of-bounds、SSL session 泄漏、watcher 无法 GC、zlib/http2/UDP/Buffer 等复杂边界。单个问题可修，但长期看，团队面对的是一类会持续冒出来的内存和生命周期问题。

迁移的判断不是“哪门语言更酷”，而是：下一阶段的质量目标是否需要语言、工具链和验证系统共同提供更强约束。
02 — WORKFLOW UNIT

大规模迁移的单位不是 prompt，而是可验证 workflow

作者没有让模型一次性“重写 Bun”。他把迁移组织成约 50 个 dynamic workflows：生成 porting guide、机械转写文件、修复 crate 编译错误、拉通子命令、跑通测试、清理 Windows 和 unsafe 等。每个 workflow 都是任务、输出、审查、反馈的循环。

Workflow 类型失败信号可迁移原则
机械迁移类型/生命周期映射错误先固化迁移指南，再批量执行
编译修复crate-by-crate errors把编译器输出当 work queue
对抗审查行为不一致、指南未遵守实现者和审查者职责分离
CI 收敛平台测试失败让平台差异成为显式队列
发布后 fuzzingparser crash / repro PR合并后继续验证，不把 merge 当终点
03 — VERIFICATION

实现者不审查自己，审查者只负责攻击

原文中最值得复制的是 adversarial review：一个实现者配两个或更多审查者。实现者的任务是完成 port，审查者的任务是找 bug、找 Zig/Rust 语义差异、找 porting guide 没遵守的地方。审查者不实现，实现者不审查。

这改变了人类 review 的抽象层。作者不是逐行读一百万行 diff，而是检查审查系统是否真的能捕捉行为差异，同时人工抽样关键代码。人类从“每一行的手工改写者”变成“loop 质量和 release confidence 的负责人”。

04 — RESULT & LIMIT

结果真实，边界也真实

Rust rewrite 带来多种可测收益：重复 Bun.build 的内存不再线性泄漏；Linux 和 Windows 二进制结合后续优化约缩小 20%；HTTP throughput 和常见 app/CLI workload 多数提升 2% 到 5%；Claude Code 使用 Rust port 后 Linux p50 启动约快 10%。

但原文也给出边界：这次迁移引入了 19 个已知回归，来自 debug_assert!、slice cast、bounds checks、comptime format strings 等语义差异；约 4% Rust 代码仍在 unsafe block 中，因为 Bun 仍与 JavaScriptCore 和 C/C++ 库交互。Rust 改善的是可治理性，不是让跨语言边界自动消失。

成本口径：
uncached input tokens  ≈ 5.9B
output tokens          ≈ 690M
cached input reads     ≈ 72B
API price estimate     ≈ $165K

比较基线不是“免费写代码”，而是“三个全上下文工程师一年 + 期间无法推进其他稳定性/安全/功能工作”。
05 — TRANSFER

对 AI-Work-Kit 的工作流启发

把子任务改造成可验证队列

Kit 已有 Plans 和 workflow 蓝图，但很多任务仍是人读的拆分。高风险任务需要显式记录失败信号、验证命令、回归范围和自动重试边界。不是每个任务都要并发 agent，而是每个可并发任务都要先有可观测失败信号。

实现者/审查者职责隔离

高风险变更不应由同一个上下文“实现后顺便自查”。实现 agent、对抗审查 agent、人工抽样 review 应该有独立输入、攻击维度和通过标准。审查 agent 可以提高覆盖率，但 release confidence 仍由人类承担。

长任务需要 loop health checkpoint

作者持续修改的是 workflow，而不只是单个文件。Kit 的长任务 plan 可以增加中段 checkpoint：失败模式是否收敛、是否反复修同类问题、是否出现跳过测试或追求绿灯、是否需要修改 loop 本身。

合并不是终点

大规模 AI 生成变更需要发布后验证台账：known regressions、fuzzing、安全审查、监控观察项和回滚条件。只有当变更规模、不可逆性或底层依赖影响足够大时启用这套重流程，避免把所有小改都流程化到失去速度。
