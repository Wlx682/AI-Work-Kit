# Agent 会提问，为什么还是做不对：一场覆盖 480 个项目的编码实验

#### 文章介绍

假设你让一个编码 Agent 开发文件解析器，只告诉它：“读取一种配置文件，解析后返回结构化数据。”

这句话看起来像需求，真正动手时却远远不够。文件可能采用什么编码？遇到重复字段怎么办？空文件是返回空对象，还是抛出异常？调用方希望使用命令行、函数 API，还是两者都要？这些答案会影响接口、依赖、目录结构和错误处理，但它们通常不会在第一句话里一次写全。

人类开发者遇到这种情况，会阅读上下文、提出问题、做一个小实验，再根据反馈修改方案。现有的大多数编码评测却跳过了这个过程。它们先把接口、边界和验收条件整理成完整题目，再让 Agent 写代码。这样的评测能回答“Agent 能否照着一份清楚的说明实现功能”，却回答不了一个越来越现实的问题：

> 当需求本身还不完整时，Agent 能否主动发现缺口，并在与用户的往返中把产品真正做出来？

ICAE-Bench 正是为这个问题设计的。论文全名是《ICAE-Bench: Evaluating Coding Agents as Interactive Project Builders》，由复旦大学、南洋理工大学、美团等机构的研究者共同完成，于 2026 年 7 月 23 日提交到 arXiv。

研究团队没有给 Agent 一份完整产品说明，而是只提供一份很短、故意省略部分细节的需求。Agent 可以向一个模拟用户提问，最多问 16 次，然后必须交付一个能够构建和运行的完整代码仓库。最后，评测系统用 Agent 从未见过的测试检查结果。

整个基准包含 480 个由真实开源项目改造而来的任务，覆盖 12 种编程语言。实验比较了六个模型、两套 Agent 框架，以及不同的提问次数、思考配置、运行环境和测试条件。最好的模型在完整基准上也只通过了 38.2% 的测试。

不过，38.2% 并不是这篇论文最值得记住的数字。真正重要的发现是：让 Agent 获得更多信息，不一定能让它做得更好；把信息变成可以直接运行的测试，却能带来非常明显的提升。

换句话说，当前编码 Agent 面对的困难不只是“缺少需求”，还有“拿到需求以后，没能把它稳定地落实到设计、代码和验证中”。论文把前者称为“需求访问缺口”，把后者称为“信息到执行的缺口”。后面的实验会显示，第二个缺口可能更难解决。

#### 知识总结

##### 过去的评测，通常把最难的一步提前替 Agent 做完了

编码评测的发展大致经历了三步。

最早的一类是 HumanEval 这样的函数题。题目会说明输入、输出和预期行为，模型只需补出一小段代码。随后出现 RepoBench、SWE-bench 等仓库级任务，模型要理解更多上下文，在已有项目中定位问题、修改代码并避免回归。再往后，Commit0、RepoGenesis、PRDBench、ProjectEval 等开始要求 Agent 从零搭建整个仓库。

任务越来越大，需求的呈现方式却没有根本变化。无论是函数题、Issue 修复还是从零建项目，Agent 通常一开始就能看到决定实现方向的主要信息。评测重点仍然是：给定规格后，能不能正确编码。

另一些研究开始关注“Agent 会不会提问”，例如 HumanEvalComm、Orchid、Ask or Assume。它们会故意在题目里留下歧义，观察模型是否应该追问。但这类工作多集中在函数或局部补丁上。即使问题问错，影响范围也比较有限。

ICAE-Bench 把这两条路线合到了一起：任务既是从零构建完整仓库，初始需求又不完整。在这种任务中，一个没有问清楚的约束，可能不只导致某个函数返回错误，还会让公共 API、依赖方案、运行方式和整体架构一起走偏。

| 评测类型 | Agent 开始时拿到什么 | 主要观察什么 | 仍然忽略什么 |
|---|---|---|---|
| 函数级代码题 | 完整的局部说明 | 能否生成正确函数 | 仓库结构和需求发现 |
| Issue 修复 | 问题描述与现有代码 | 能否定位、修改、回归 | 从零设计与产品意图 |
| 从零生成仓库 | 较完整的 PRD 或脚手架 | 能否实现一个完整项目 | 规格缺失时如何推进 |
| ICAE-Bench | 简短需求和运行环境 | 能否提问、构建并验证 | 真实用户的变化和开放式创新 |

这一区别看起来只是“需求长一点还是短一点”，其实改变了评测对象。Agent 不再只是施工者，也要参与形成施工图。

##### 模糊需求很容易评错，论文先解决了这个公平性问题

要评测模糊需求，有一个绕不开的困难：如果需求真的没有明确答案，评测者凭什么说某种实现是错的？

例如，用户只说“做一个配置文件解析器”，开发者选择 JSON、YAML 或自定义格式都可能合理。如果研究者事后拿自己偏好的格式去判分，就不是在测 Agent，而是在惩罚它没有猜中评测者的心思。

ICAE-Bench 的解决办法是反过来构造任务：不是先编一份模糊需求，再决定答案；而是先找到一个已经有明确行为的真实项目，再从这个确定答案中隐藏一部分信息。

每个任务都从一个能在受控环境中正常构建、原始测试全部通过的开源仓库开始。研究团队先根据代码和测试整理出完整需求，称为 GroundPRD，可以理解为“经过验证的完整产品合同”。随后，他们把原有测试改造成与具体编程语言无关的黑盒输入输出测试。

等完整合同和测试都准备好后，团队才从 GroundPRD 中删去部分 API 规则、边界行为和架构约束，生成 Agent 最初看到的 Fuzzy PRD，也就是“模糊版需求”。被删掉的内容没有消失，而是保存在 User Agent Data 中。只有当编码 Agent 问到相关问题时，模拟用户才会返回对应答案。

整个任务可以写成：

```text
T = (Df, E, P, U, B)

Df：Agent 最初看到的模糊需求
E ：已经准备好的开发和运行环境
P ：公开示例，部分可以通过提问获得
U ：模拟用户掌握的隐藏需求记录
B ：最终用于判分的完整黑盒测试
```

这个设计里最重要的一点是：模拟用户知道的内容 `U`，并不等于最终测试 `B` 的所有答案。Agent 可以通过提问获得关键线索，却不可能把隐藏测试逐条问出来。它仍然需要从有限的回答中归纳出更完整的行为规则。

还是以文件解析器为例。Agent 可以问“遇到空文件怎么办”，模拟用户可能回答“返回空对象”；但最终测试还会检查损坏编码、嵌套深度和异常字段。评测要看的不是 Agent 有没有背下一个例子，而是它能否把例子背后的规则落实成稳健实现。

##### 为了让失败可信，研究团队还要验证“题目本身没有问题”

从真实仓库生成需求和测试，并不意味着基准天然正确。自动提炼的需求可能漏掉约束，模型生成的新测试也可能与原项目行为矛盾。论文因此设计了五个构造阶段。

1. 先筛选能在统一环境中稳定运行的真实仓库。
2. 从原始测试和实现中整理完整 GroundPRD，并生成黑盒测试。
3. 从完整需求中隐藏部分信息，生成三种模糊程度不同的需求。
4. 打包开发环境，保留运行时和依赖，但删除原始代码、测试及答案痕迹。
5. 让模型仅根据整理出的需求重建项目，再用原始行为反复校正需求和测试。

最终测试分成两类。Native 用例来自原项目，保证基准没有偏离真实软件；Enhanced 用例专门补充边界值、特殊约束和压力场景。每个 Enhanced 用例都必须先在原始项目上运行通过，才能进入评测。

研究团队还让 Claude Opus 4.8 在删除源码的环境里，仅根据 GroundPRD 重建仓库。如果重建项目无法通过原始测试，他们会检查究竟是需求漏写了，还是测试转换出了问题。之后，再用 GPT-5.5 检查模糊需求加上所有可恢复回答后，是否仍与完整需求表达同一个目标。

在用于高成本实验的 50 个轻量任务中，最模糊版本与完整需求的平均语义相似度为 0.952，较详细版本为 0.942；没有任务被判断为会因为需求合同矛盾而必然失败相同测试。这个验证不能证明基准绝对无误，但它显著降低了“Agent 其实是被坏题目坑了”的可能性。

##### Agent 实际经历的任务，比“看短需求写代码”多了一个交互阶段

三档模糊需求共享同一个最终目标，只是第一眼暴露的信息不同。

最模糊的 L1 平均只有 276 个英文词元，大致接近一段简短的产品需求。L2 会补回一部分细节，L3 则接近完整需求。作为对照，完整 GroundPRD 平均有 6,764 个词元；模拟用户保存的可恢复信息平均还有 7,091 个词元。

这意味着初始需求虽然短，任务真正需要的知识并不少。它们只是从“开场一次性给出”，变成了“开发过程中按问题逐步获得”。

默认的模拟用户由 DeepSeek-V3.2 驱动，但它并不自由扮演用户。每条隐藏需求都有固定标识、可能的问法和预先写好的回答。编码 Agent 提问后，系统从这些记录中匹配最多三个相关技术点；没有匹配到，就返回统一的兜底回答。它不能根据常识临时增加需求，更看不到原始源码和隐藏测试。

这种设计牺牲了一些真实性。现实用户会表达含糊、临时改口，也可能自己不知道答案；ICAE-Bench 的模拟用户不会。作为交换，研究者可以重复运行同一个任务，并区分两种情况：到底是 Agent 没问到关键问题，还是用户这次回答得不一样。

交互结束后，Agent 要交付一个完整仓库，而不是一段答案。评测系统随后在全新的容器中注入测试。开发期间手工改过环境、临时运行成功，却没有进入最终仓库的操作，都不会被计分。

##### 评测为什么不能只看一个总分

一个项目测试失败，原因可能完全不同：可能是核心逻辑写错，也可能是项目根本构建不起来；可能 Agent 没问到需求，也可能它问到了却在后续修改中忘了。

因此，ICAE-Bench 同时保留四组证据。

第一组是功能正确性。Public 测试是 Agent 能直接看到或通过提问获得的示例；Native 测试继承原项目行为；Enhanced 测试补充未公开的边界场景。论文的 Overall 指标，是 Native 与 Enhanced 中每条测试的平均通过率。

第二组是仓库内容是否与目标相似。一个评审模型会比较生成仓库与原项目的功能语义、公共 API 和设计质量。这些分数可以帮助判断“方向是否接近”，但不能替代真正运行测试。

第三组是结构。研究者会比较文件数、代码行数、类和方法等，观察 Agent 是否少做了大量模块，或反过来过度扩张。结构接近原项目不代表一定正确，只是一种诊断信号。

第四组是交互质量。系统记录 Agent 找回了多少隐藏约束、提出多少没有命中的问题，以及用了多少提问预算。这个维度尤其关键，因为后面的实验会证明：找回更多约束，不等于最终通过更多测试。

##### 第一组结果：公开示例能做对，未展示的边界很快失守

主实验让六个模型都运行在 Claude Code 框架中，从最模糊的 L1 需求开始，最多提问 16 次。

在完整的 480 个任务上，Claude Opus 4.8 的 Overall 最高，为 38.2%；GPT-5.5 紧随其后，为 37.2%。这个比例按测试用例计算，并不是说 38.2% 的项目已经完整交付。事实上，每个模型只有 1 到 13 个仓库通过了全部测试。

公开示例与隐藏边界之间的差距更能说明问题。Claude Opus 4.8 在 Public 用例上通过 48.5%，到了 Enhanced 用例只剩 35.5%；GPT-5.5 分别为 50.3% 和 32.8%。Agent 能较好地复现已经展示的行为，却难以把局部示例推广到没有出现过的异常和边界。

不同评价维度之间也没有稳定的一致关系。GPT-5.5 找回的隐藏约束更多，Overall 却比 Claude Opus 4.8 低一个百分点。Claude Sonnet 4.6 在轻量基准上获得最高的语义相似度，功能 Overall 却只排第五。仓库“看起来接近”、问到的信息更多、生成的代码更多，都不能单独证明项目正确。

语言差异同样复杂。Claude Opus 4.8 在 Go、TypeScript、Rust 等语言上领先，GPT-5.5 在 PHP、Ruby、Dart 上更好。研究者把所有非 Python 任务统一改用 Python 实现后，总分从 26.6% 小幅升到 29.9%，但 PHP 任务下降 14.6 个百分点，C++ 任务上升 17.3 个百分点。熟悉的语言有时有帮助，却不是普遍解法。

##### 第二组结果：把所有回答提前给 Agent，仍然不如一份整理好的完整需求

为了判断问题究竟出在“没有问到”，还是“问到了也没做好”，论文设置了五种需求条件。

L1、L2、L3 逐步增加初始信息。RecoveredPRD 更进一步：研究者把 L1 中所有可以通过提问得到的回答，一次性附在需求后面。这样 Agent 不再需要判断问什么，也不会因为问题没有命中而漏掉信息。最后一档 GroundPRD 则是研究团队整理过的完整、连贯需求。

如果 Agent 的主要瓶颈只是找不到信息，那么 RecoveredPRD 应该接近 GroundPRD。实验结果却不是这样。在六个模型中的四个上，GroundPRD 明显更好。

两份材料在“包含哪些事实”上已经很接近，差别在组织方式。RecoveredPRD 像一叠问答记录：每条回答解决一个局部问题，但 Agent 仍要判断它影响哪个接口、是否与其他约束冲突、应该落在哪些文件、后续修改有没有破坏它。GroundPRD 则已经把这些碎片整理成一份连贯合同。

由此，论文把失败拆成两个阶段：

```text
模糊需求
   │
   ├─ 能否发现缺少什么，并问到答案？       需求访问缺口
   │
   └─ 答案能否进入设计、实现和验证？       信息到执行缺口
                                              │
                                              ↓
                                       正确、可运行的仓库
```

交互主要帮助填补第一个缺口。第二个缺口需要状态保持、约束整合、代码修改和持续验证。Agent 可以把问题问对，也可以在十几轮之后忘掉早期回答；可以正确理解边界条件，却没有把它变成测试；也可以实现过一次，随后在重构中破坏。

这正是整篇论文最有价值的判断：对复杂编码任务来说，“信息是否出现过”不是一个足够好的完成状态。

##### 第三组结果：把文字示例变成可运行测试，带来了最大提升

论文最醒目的实验没有提供任何新需求。研究者只是把原本通过模拟用户返回的公开输入输出示例，提前做成工作区内可以直接运行的测试文件。

在 GLM-5.1 think-8k 和 50 个轻量任务的设置中，Overall 从 37.4% 提升到 61.8%，增加了 24.4 个百分点。与此同时，Agent 找回隐藏约束的比例反而从 63.8% 小幅下降到 61.2%。

也就是说，Agent 知道的并没有更多，做对的却明显更多。

原因并不神秘。自然语言回答只告诉 Agent“应该是什么”，Agent 还要自己决定如何调用项目、怎样构造输入、怎样判断输出。可运行测试把这些内容组合成一条即时反馈：修改代码、运行测试、看到失败、定位问题、再次运行。信息从一段需要记住的话，变成了可以反复触发的外部约束。

这个结果不能被解读成“任何项目多写测试都会固定提升 24.4 个百分点”。它只来自一个模型、一组思考配置和轻量子集。但它有力支持了一个更稳妥的结论：

> 对 Agent 来说，可执行、可重复验证的信息，往往比只是出现在上下文里的信息更有用。

测试也不是完整答案。公开用例只覆盖一部分行为，Agent 仍可能针对样例写出投机实现。因此，ICAE-Bench 继续使用未公开的 Native 和 Enhanced 测试，检查实现有没有从示例归纳出更一般的规则。

##### 第四组结果：模型之外的框架、预算和环境，同样决定结果

论文还做了一系列消融实验，试图找到“多给一点资源是否会更好”。答案几乎都不是简单的“是”。

先看 Agent 框架。同一模型、同一批任务，从 Claude Code 换到 OpenHands 后，六个模型的 Overall 全部下降，幅度在 5.5 到 21.8 个百分点之间。GPT-5.5 从 53.3% 降到 31.5%，排名也发生变化。它甚至找回了更多需求，最后实现却更差。

框架并不是一个透明外壳。它决定 Agent 怎样编辑文件、运行命令、保存状态和判断何时结束。换框架可能让同一个模型更容易丢失早期回答，也可能让构建和调试循环变得不稳定。因此，所谓“模型能力”实际上是模型、工具、环境和控制逻辑共同产生的系统结果。

再看提问次数。把预算从 8 次增加到 16 次时，Overall 从 22.9% 上升到 37.4%；继续增加到 24 次，Agent 找回的隐藏约束从 57.9% 增加到 71.4%，Overall 却回落到 34.4%。

多出来的问题带来了更多信息，也带来了更多需要整合的碎片。没有稳定的约束管理时，继续扩大上下文反而可能增加重复、冲突和遗忘。好的提问策略不应追求“把预算用完”，而应优先解决会改变架构、接口或验收方式的问题。

思考模式整体上更有帮助。Gemini 3.1 Pro 开启 thinking 后从 26.7% 提升到 36.6%；GLM-5.1 使用自适应思考时，也比固定的 think-8k 从 37.4% 提升到 40.0%。但更多思考仍然没有消除需求整合和执行验证的问题。

更丰富的运行环境甚至带来了负面结果。加入更多现成依赖后，GLM-5.1 的 Overall 从 37.4% 降到 28.4%，生成文件数达到原项目的 191%，代码行数达到 674.1%。可选工具变多后，Agent 倾向于构建更复杂的方案，有限的推理和调试预算被分散到更多模块和接口上。论文并没有证明“依赖越少越好”，它只是提醒：更大的行动空间也意味着更多失败点。

##### 这些数字能说明什么，又不能说明什么

ICAE-Bench 的 480 个任务覆盖 C#、C++、Dart、Go、Java、JavaScript、Kotlin、PHP、Python、Ruby、Rust 和 TypeScript，每种语言 40 个。原始仓库平均包含 35,533 行代码和 258 个文件，最大仓库超过 290 万行。这个规模让结论不只停留在玩具函数上。

高成本的消融实验没有全部运行在 480 个任务上，而是使用 50 个较小项目组成的 ICAE-Bench-Lite。Lite 与完整基准的模型排名 Spearman 相关系数为 0.71，能保留大体趋势，但第一、第二名会互换。因此，Lite 适合快速比较配置，不能代替完整榜单和逐语言结论。

API、语义和设计质量由另一个模型评分。研究者请三名研究生人工复核 200 个仓库后发现，模型评分与人工均分的 Pearson 相关分别为 0.372、0.381 和 0.471。这些指标可以辅助诊断，却远没有可靠到能够替代实际运行测试。

更重要的限制来自模拟方式。ICAE-Bench 的 User Agent 只会从预先写好的记录回答，不会像真实用户那样含糊、改口或产生新的想法。任务目标来自已有开源仓库，因此总有一个可以验证的原始实现；现实中的创新产品往往没有这样的标准答案。当前测试也更擅长判断后端输入输出，对视觉界面、多模态交互和主观体验覆盖有限。

所以，38.2% 不能被理解成“最强 Agent 完成真实软件项目的成功率”。它只描述特定模型、框架、预算和评测协议下的测试通过情况。

这篇论文更可靠的贡献，不是给模型排出一个永久名次，而是用多组对照实验揭示了同一个方向：项目开发中，需求信息从被发现到真正生效，中间还有一条很长、很容易断裂的执行链。

#### 工作流提炼

##### 澄清需求以后，要能看见它去了哪里

ICAE-Bench 最直接的启发是：一条需求“已经讨论过”，不代表它“已经进入产品”。

通用做法是为重要约束建立从来源到证据的关联。一次澄清如果改变了行为，就应该能追踪到至少一种下游结果：设计决策、实现位置、可执行验收，或明确的人工评审项。这样，后续修改发生时，团队才知道哪些旧结论可能被破坏。

AI-Work-Kit 已经有事件风暴、实例化需求、需求分析、plan 和测试计划，缺少的不是再增加一种需求文档，而是让这些材料之间的约束关系更容易追踪。适合补强的是 requirement-to-evidence trace，而不是复制论文里的模拟用户。

并非所有需求都适合自动测试。视觉偏好、商业取舍和体验判断仍需要负责人确认。关键是明确证据类型：无法自动验证，不等于可以没有验证。

##### 用生命周期保存约束，不要只保存最新版文档

长任务中的约束会经历发现、确认、实现、验证，也可能被新决定替代。只保留一份最新版 PRD，会丢失“为什么改”“旧实现是否还在”“哪个结论已经过期”等信息。

可以把重要约束表示为：

```text
discovered → confirmed → mapped → verified
                           └────→ superseded / rejected
```

`mapped` 表示约束已经关联到实现或验收，`verified` 才表示证据真正通过。`superseded` 保留被替代的历史，避免 Agent 在长会话或任务恢复时重新采用旧结论。

Kit 已有 plan、WBS、事件日志和 workflow gate，可以承载这些状态。状态变更可以由工具记录，但需求是否确认、冲突偏好如何取舍，仍应由人决策。

##### 高价值需求要尽快转成可以失败的东西

测试脚手架让 Overall 增加 24.4 个百分点，支持一个跨工作流原则：重要信息越早拥有可执行反馈，越不容易只停留在上下文里。

Kit 已有 spec-by-example 和 test-generator。输入输出、错误路径、边界值和状态迁移适合直接转成验收测试；UI 和文案可以转成截图基线、结构检查、可访问性规则或人工评审清单。形式可以不同，但都要让“没做到”变得可观察。

公开示例和独立验收必须分层。前者帮助 Agent 快速调试，后者检查它有没有只针对样例优化。不能为了可执行性，把所有隐藏验收答案都交给执行 Agent。

##### 评估 Agent 时，要记录整个运行系统

Claude Code 与 OpenHands 造成最高 21.8 个百分点的差异，说明模型名称不足以描述一次 Agent 运行。

可复现的最小记录至少应包含：模型与版本、Agent 框架版本、可用工具、权限和审批方式、环境或依赖摘要、思考配置、交互预算、执行命令以及验收版本。可以把它们组织成 agent-run manifest。

Kit 的 skill_run 已经记录技能和上下文效用，但还不能完整区分模型升级、框架改变与环境变化。补充运行清单的目的应是复现和定位问题，而不是把 token 或耗时变成绩效指标。

##### 先判断链路断在哪里，再决定让 Agent 重做什么

ICAE-Bench 把最终失败分为输出不匹配、功能缺失、构建运行失败和测试入口缺失。对真实工作流，还可以进一步区分：

| 断点 | 典型现象 | 下一步动作 |
|---|---|---|
| 没有发现需求缺口 | Agent 直接做出高风险假设 | 补充澄清 |
| 已获得但没有保留 | 早期回答在后续修改中丢失 | 修复约束状态与传递 |
| 已理解但没有实现 | 文档正确，代码行为错误 | 回到实现与代码审查 |
| 项目不可执行 | 构建、依赖或入口失败 | 修复环境和交付协议 |
| 验收合同不足 | 运行成功但边界不可判断 | 补充独立验证 |
| 等待人工决定 | 多个合理方案无法自动取舍 | 明确责任人和决策期限 |

这能避免所有失败都被归结为“提示词不够好”。自动分类可以提出候选原因，但需求是否合理、用户是否改变主意、架构取舍是否接受，仍需要人工确认。

##### 提问的目标不是覆盖更多，而是改变后续行动

8、16、24 次提问的实验表明，沟通轮数和需求覆盖率都不是质量代理。真正有价值的问题，应该能够改变设计、接口、实现顺序或验收方式。

工作流可以记录每次澄清影响了哪个决策或测试。如果连续几个问题都没有产生新的映射，就提示 Agent 从继续收集信息转入实现和验证。对于探索型需求，目标本来就会演化，不应机械限制提问；对于交付型任务，则应该更早收敛并记录变更。

核心原则不是“少问问题”，而是不要让提问成为一种看起来很忙、实际上没有改变任何执行状态的活动。
