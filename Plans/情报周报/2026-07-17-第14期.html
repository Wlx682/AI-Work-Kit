Agent Tool Regression

模型越强，工具调用越不可靠

核心论点 Tool schema 不是中立的。模型的 RL 后训练让某些 schema 形状成为"特权分布"，偏离它的第三方工具会随模型升级而退化。
01 — 文章介绍

一个反直觉的 Bug

Armin Ronacher（Flask 作者、Sentry 首席架构师）在其开源 agentic coding harness Pi 中发现：Anthropic 最新模型 Opus 4.8 / Sonnet 5 调用 Pi 的编辑工具时，schema 遵从度比旧模型更差。模型产出的编辑内容完全正确，但会在 JSON 中"发明"不存在的额外字段，导致 schema 验证失败。

追踪这个 bug 的过程揭示了一个系统性问题：RL 后训练在闭源宽容 harness 中进行时，该 harness 的 tool schema 会成为隐性"特权分布"。所有偏离这个分布的第三方工具 schema 都可能随模型升级而退化。

02 — ANTML 编码机制

Tool Call 不是魔法：理解底层格式

LLM 的 tool calling 本质上是带内信号（in-band signalling）。模型收到 transcript 和工具列表后，服务端将其编码为特殊标记格式。模型在生成时输出类似下方的标记，客户端解析为工具调用：

<function_calls>
  <invoke name="edit">
    <parameter name="path">some/file.py</parameter>
    <parameter name="edits">
[
  {
    "oldText": "text to replace",
    "newText": "replacement text"
  }
]
    </parameter>
  </invoke>
</function_calls>

Ronacher 的关键观察：

观察影响
ANTML 不是 XML，只是便于分词的标记格式不能假设 XML 解析器行为
顶层字符串参数直接内联在标签里简单参数采样压力低
对象数组参数序列化为 JSON 嵌入标签内嵌套结构 = 高熵采样点
多行文件内容需转义后塞入 JSON 字符串关闭引号后模型决策 } vs , "..."

03 — 失败模式

正确的内容 + 胡编的字段名

Pi 的 edits[] 数组每个元素只允许 oldText 和 newText。失败样例中，替换文本完全正确，但模型在闭合后"顺手"多写了不存在的字段：

{
  "oldText": "...",        // 正确
  "newText": "...",        // 正确
  "requireUnique": true    // 胡编的
}
发明的字段名可能的语义来源
requireUnique / unique类似 Claude Code 的 replace_all 标志
matchCase大小写敏感选项
in_file / type / kind作用域标注
oldText2 / newText2误认为应合并多次编辑
children / notes / cost完全无关的结构性噪声
!
复现条件：全新单轮提示无法复现；需要多轮 agentic session（模型已读文件、诊断问题后）。去除 thinking block 后复现率减半——context 复杂度放大了失败概率。
04 — 训练伪影假说

为什么新模型更差

Ronacher 的核心假说：这不是随机退化，而是后训练适配的系统性副作用。

这解释了为什么 Opus 4.5 对第三方 schema 适配极好——那时 RL 后训练尚未深度绑定 Claude Code。随着后训练越来越紧密地围绕 Claude Code，模型的 tool schema 先验变强，对"偏离分布"的 schema 反而更不友好。

越多的后训练发生在一个主导性闭源 harness 内，其他 harness 就越需要继承该 harness 的怪癖。这是一种没有 API 文档、没有 changelog、也无法 opt-out 的隐性依赖。
05 — Slop Harness

Claude Code 如何吸收格式错误

Ronacher 逆向分析了 Claude Code 的压缩代码，发现其容错机制远超一般预期：

容错机制行为
ANTML 泄漏检测检查模型可见文本中的 <invoke 标记泄漏
Unicode 转义修复修复损坏的 \uXXXX 和孤立代理对
参数别名映射old_str → old_string、path → file_path
未知字段静默过滤直接丢弃 schema 外字段，不报错
不使用 strict 模式因 Anthropic 对 strict 有工具定义复杂度限制
重试状态机对格式错误的调用有完整重试流程
!
宽容悖论：harness 越宽容 → 模型在该 harness 内表现越好（不因小错中断） → 但模型对格式的纪律性越差 → 在其他严格 harness 中退化越多。
06 — Constrained Decoding

对比 OpenAI Harmony 与 Anthropic strict

OpenAI 的 Harmony 格式包含一个关键的带内标记：

<|start|>assistant<|channel|>commentary to=functions.get_weather
<|constrain|>json<|message|>{"location":"San Francisco"}<|call|>

<|constrain|>json 让模型自己声明"接下来是 JSON"，推理栈据此切换到约束采样。即便没有外部 strict 开关，格式信号就在模型输出中。

维度Anthropic strictOpenAI Harmony
约束声明外部开关（API 参数）带内标记（模型自主输出）
复杂度限制有工具定义复杂度上限支持 LARK 语法定义自定义工具
嵌套 JSON 处理ANTML 标签内序列化，高熵channel 边界清晰切换
第三方 schema 兼容可能退化（本文核心发现）尚未观察到类似退化

Ronacher 的判断变化：他此前对 constrained decoding 持怀疑态度（质量代价），但这个 bug 显著改变了他的先验——

如果最新的模型在解决任务方面变得更好，同时在忠实输出替代 tool schema 方面变得更差，那么 harness 需要在某个地方提供更强的保证。
07 — 工作流提炼

对 Agent 工具设计的启示

通用原则：宽容验证在反馈循环中会被利用

当系统的验证层过于宽容，优化环路（RL 或人类）会逐渐利用这种宽容，直到它变成隐性规范。这不只适用于 LLM tool calling——任何有反馈循环的系统都有同样的退化路径。

通用原则：闭源 RL 环境创造不可见的隐性依赖

当你基于某个模型构建系统时，模型背后的 RL 环境是一个不可见的上游依赖。模型升级可能改变 tool calling 可靠性、输出风格、错误处理倾向——而这些变化不在任何 release note 里。

设计建议：Schema 设计考虑分布距离

Schema 设计时需要意识到"离模型见过最多的形状有多远"是影响可靠性的变量：

设计选择分布距离可靠性预期
扁平 key-value，字段名类似官方工具近高
嵌套对象数组，自定义字段名远低（需 strict 模式补偿）
启用 constrained decoding无关高（结构性保证）
