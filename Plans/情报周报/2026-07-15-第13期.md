# 用 11 天重写 Bun：Agent 时代的大规模迁移不是“多生成代码”，而是重建验证系统

#### 文章介绍

2026 年 7 月 8 日，Bun 作者 Jarred Sumner 在 Bun 官方博客发布了《Rewriting Bun in Rust》。这是一篇少见的工程长文：它既讲一门基础设施级 JavaScript runtime 为什么从 Zig 迁移到 Rust，也把迁移过程里 Claude Code dynamic workflows、对抗式审查、编译错误队列、CI 回归和发布后安全验证全部摊开。

这篇文章的一手性很强。作者本人是 Bun 的主要创建者，Bun 在 2025 年 12 月被 Anthropic 收购，文中也明确说明迁移过程使用了预发布的 Claude Fable 5 和 Claude Code。它不是外部观察者写的“AI 写代码”新闻，而是项目负责人对一次真实大迁移的复盘。

原文结构可以分成四层：

1. 为什么重写：Bun 的 Zig 代码规模大、手工内存管理和 JavaScriptCore/C/C++ 边界带来大量稳定性问题。
2. 为什么选 Rust：不是因为 Zig 失败，而是 Rust 的 Drop、借用检查、Miri、LeakSanitizer 和跨语言 LTO 更适合下一阶段稳定性工程。
3. 怎么用 Claude Code 执行：约 50 个 dynamic workflows 连续运行 11 天，峰值约 64 个 Claude 并发，配合实现者/审查者分离、编译错误队列、平台 CI 和人工监控。
4. 迁移结果与边界：全平台测试通过、已知 19 个回归全部修复、内存和体积显著改善、性能提升有限但真实，同时仍保留一定 unsafe 和 C/C++ 边界。

这篇文章值得深挖的原因不是“一个人用 AI 改了 100 万行代码”这个表层数字，而是它展示了 Agent 时代大规模工程迁移的实际组织形态：人类不再逐行改代码，但也没有退出循环；真正的能力跃迁发生在任务拆分、验证口径、失败修复和审查边界被系统化以后。

#### 知识总结

##### Bun 为什么要离开 Zig

Bun 起初是 Jarred Sumner 把 esbuild 的 JavaScript/TypeScript transpiler 从 Go 迁移到 Zig 后发展出来的项目。它的范围很大：transpiler、minifier、bundler、npm-compatible package manager、Jest-like test runner、Node.js API 实现、HTTP/WebSocket client 等都在同一个 runtime 里。到原文发布时，Bun CLI 已经有超过 2200 万月下载量，Claude Code 和 OpenCode 也把 Bun 作为 runtime。

Zig 对 Bun 的早期成功很重要。作者没有把迁移写成对 Zig 的否定，而是反复强调：没有 Zig，很难在早期一年内完成这样大范围的系统。但随着项目进入生产稳定性阶段，原来的优势开始伴随新的成本。原文开头列出了一串 Bun v1.3.14 修复的问题：use-after-free、out-of-bounds read/write、SSL session 泄漏、watcher 无法 GC、zlib/http2/UDP/Buffer 等场景的边界崩溃。

这些问题有共同特征：它们往往发生在 JavaScript 回调、C/C++ 库、JavaScriptCore、线程池和手动资源释放交错的边界处。单个 bug 可以修，但长期看，团队实际面对的是“稳定性债务会持续从边界冒出来”的系统问题。作者给出的判断很直接：继续在 Zig 上逐个修复当然可行，但这意味着把大量工程精力长期花在同一类内存安全问题上。

##### 为什么不是 C/C++，也不是渐进式重写

原文专门讨论了 C/C++。Bun 本来就嵌入了大量 C/C++ 组件，例如 JavaScriptCore、uWebSockets/usockets、BoringSSL、SQLite 等。C++ 会带来构造/析构函数，能减少一些 extern wrapper；但作者认为它不能从语言层面解决他们最需要的安全约束。Rust 的吸引力不是“更现代”，而是它能把一部分资源生命周期问题提前到编译期或结构化清理阶段。

更有意思的是“是否渐进式迁移”的取舍。作者选择的是接近“一次性机械迁移”的路线：让 Rust 代码尽可能像 Zig 代码被转写过来，保持架构、性能和功能集一致，先把系统迁过去，再逐步减少 unsafe、重构成更 idiomatic 的 Rust。这样做的目标是降低团队认知成本：懂原 Zig 代码的人也能读懂新 Rust 代码。

这不是常规软件工程里最稳妥的路线。一次性大迁移会带来巨大的 review、CI 和回归压力。它成立的前提是：有足够强的测试套件，有能持续修复失败的 agent workflow，有人工监控这些 workflow 的能力，也有可以把迁移拆成可验证队列的工程纪律。

##### Dynamic workflows：大规模代码迁移的基本单位

原文最核心的技术组织单位不是“prompt”，也不是“64 个 Claude”，而是 dynamic workflow。作者把日常工程抽象成循环：任务从待办列表弹出，实现者产出代码，审查者检查回归和正确性，再把反馈应用回结果。

这次迁移大约有 50 个 dynamic workflows 持续运行 11 天，覆盖的任务包括：

| Workflow 类型 | 解决的问题 | 关键产物 |
|---|---|---|
| 生成迁移指南 | 把 Zig pattern/type 映射到 Rust pattern/type | PORTING.md、LIFETIMES.tsv |
| 机械迁移文件 | 把每个 .zig 文件转成 .rs 文件 | 初始 Rust 文件批次 |
| 修复 crate 编译错误 | 将错误列表变成可消费 work queue | crate-by-crate fix commits |
| 拉通子命令 | 让 bun test、bun build 等命令恢复运行 | 可执行 smoke path |
| 跑通完整测试 | 让 Bun 全量测试在本地和 CI 变绿 | 平台 CI 通过 |
| 清理和重构 | Windows cleanup、去重、减少 unsafe | 可维护性改进 |

这个表的关键点在于：迁移不是“一条巨型指令生成项目”，而是多个带目标、输入、验收和反馈的循环。Claude Code 在这里像一个 workflow runtime：它负责连续执行、修复、提交；人类负责观察 loop 是否在正确方向上收敛，并在发现系统性问题时修改 loop，而不是只修某个输出文件。

##### 对抗式审查：实现者和审查者必须分离

原文强调了一个简单但重要的机制：实现者不审查自己的代码，审查者不实现代码。每个实现者配两个或更多 adversarial reviewers，审查者的职责是找 bug、找与原 Zig 行为不一致的地方、找 porting guide 没遵守的地方。

这解决的是 LLM 生成代码时常见的“自证正确”问题。如果同一个上下文窗口既生成代码又解释为什么它正确，模型很容易被自己的局部叙事绑定。把实现和审查拆到不同上下文窗口后，审查者不背负“让代码通过”的任务目标，反而更容易攻击实现。

更重要的是，作者 review 的对象也发生了变化。他不是只看一百万行 diff，而是检查 adversarial review agents 是否真的在捕捉 Zig/Rust 行为差异，是否在执行迁移指南和 lifetime guide。换句话说，人类 review 的抽象层上移了：从“逐行证明每个修改正确”变成“证明审查系统和验证系统足够可信，同时抽样读关键代码”。

##### 编译错误和 CI 失败被变成队列

在初始迁移之后，系统面对的是大量编译错误。原文给出过一个阶段性画面：约 16000 个错误等待处理。作者让 Claude 写 workflow crate-by-crate 地修复编译错误。这一步的关键不是“Claude 会修错误”，而是编译器提供了非常清晰、可枚举、可消费的失败信号。

随后进入测试阶段。第一次 CI 运行后，失败测试文件数在两天内从 972 降到 23，又过了一天半 Linux 全绿；最终 6 个平台全部通过。这个过程说明，适合 agent 大规模执行的任务往往有两个条件：失败可以被机器稳定观测，下一步行动可以从失败输出中派生。

这也是为什么这篇文章比普通 AI 编码演示更有价值。它不是在说“AI 可以写 Rust”，而是在展示什么样的工程系统能把 AI 输出纳入可靠收敛路径：编译器、测试套件、CI 平台、worktree 隔离、commit replay、人工验证共同构成了外层 harness。

##### 数字：这不是低成本魔法

原文披露了非常具体的数字。迁移在 2026 年 5 月 3 日开始，5 月 14 日合并。最终有 6502 个非 merge commits，diff 落地约新增 1009272 行。峰值运行 4 个 workflows，每个 workflow 在独立 worktree 中有 16 个 Claude，合计约 64 个 Claude 并发。

测试规模同样惊人：Debian 13 x64、macOS 14 arm64、Windows 2019 x64 三个平台上，各自都有约 100 万级别的 expect 调用和 5.7 万到 6 万个测试。作者强调没有跳过或删除测试。

成本也很清楚：预合并阶段消耗 59 亿 uncached input tokens、6.9 亿 output tokens 和 720 亿 cached input token reads，按 API 价格约 16.5 万美元。作者估计，如果由三个完全熟悉代码库的工程师手工迁移，可能需要一年，而且这一年里团队无法同时推进兼容性、安全和新功能。现实替代方案很可能不是“慢慢手写重构”，而是继续留在旧状态里修同类 bug。

这组数字带来的结论很克制：Agent 不是把迁移变成免费，而是把“原本组织上不值得做、机会成本过高”的迁移，变成一次昂贵但可控的工程投资。

##### 迁移后真的变好吗

原文没有只讲 agent 过程，也给出了迁移收益。

内存方面，Rust 的 Drop 让某些资源释放从“每个调用点记得 defer”变成“值离开作用域自动清理”。Bun 改进了 LeakSanitizer 集成，追踪 native allocations。一个例子是同一进程中重复 Bun.build：v1.3.14 每次 build 泄漏约 3 MB，跑到 2000 次后内存约 6745 MB；v1.4.0 则在 609 MB 左右趋于平稳。

体积方面，Rust rewrite 初期让二进制在 Windows、macOS、Linux 上分别减少数 MB；结合 ICU 变更和 identical code folding，Linux 和 Windows 上最终约缩小 20%。性能方面，Bun v1.4.0 在 Linux x64 上的 HTTP throughput 和常见 app/CLI workload 大多提升 2% 到 5%，不是惊天动地，但稳定且可测。Claude Code 自 v2.1.181 起使用 Rust port 的 Bun，Linux p50 启动从 517ms 降到 464ms，约快 10%。

生产验证也不是空口。Prisma Compute public beta 在 Rust rewrite 上测试过原来遇到的 memory leak 和 VM pause/resume 后 connection pool 恢复问题，结果符合预期。

##### 边界：19 个回归、unsafe 和语言语义差异

原文最值得信任的部分，是它没有把迁移写成完美胜利。作者明确说，这次 rewrite 引入了 19 个已知回归，后来都修复了。回归主要来自两类语言“看起来相似但语义不同”的地方。

例如 Zig 的 assert 是函数，参数在所有 build 中都会执行；Rust 的 debug_assert! 是 macro，release build 会把整个表达式消掉。某段代码把有副作用的 insert_stale 放进 debug_assert! 后，debug build 正常，release build 中热更新图不再更新，导致 HMR 场景出错。

再如 Zig 的 reinterpretSlice(u16, bytes) 会忽略结尾奇数字节，而 Rust bytemuck::cast_slice 会 panic；Bun 需要恢复原行为。还有 bounds checks、comptime format strings、Rust release build 的检查行为等差异。它们都说明：机械迁移不等于语义等价，必须靠对照审查、测试和真实用户场景来捕捉。

unsafe 也没有消失。原文披露写作时约 4% 的 Rust 代码在 unsafe block 中，约 13000 个 unsafe keywords、27000 行左右，原因是 Bun 仍然和 JavaScriptCore、C/C++ 库交互。作者预期 unsafe 会随着重构下降，但不会归零。这是成熟工程判断：Rust 改善了可治理性，不是给跨语言边界发一张免死牌。

##### 迁移之后的稳定性系统

文章后半段讲“work continues”。合并以后，Bun 完成了 11 轮 Claude Code Security review 并处理发现；同时为 parser 加了 24/7 coverage-guided fuzzing，覆盖 JavaScript、TypeScript、JSX、CSS、JSON5、JSONC、TOML、YAML、Markdown、INI、Bun Shell scripts、semver ranges、patch files、CSS colors 等。Fuzzer 会把发现的问题交给 Claude 提 PR 复现和修复，再由人类 review。原文披露，fuzzer 已执行 parser 约 1000 亿次，带来约 15 个 PR。

这说明迁移完成不是“AI 写完代码就结束”，而是验证系统继续运行。Rust rewrite 的真正收益之一，是让团队拥有更强的稳定性工具链：borrow checker、Miri、LeakSanitizer、fuzzing、安全审查和更清晰的 unsafe 搜索面。

#### 工作流提炼

##### 原则一：不要把 Agent 并发当作核心能力，核心能力是可验证队列

原文最容易被误读成“64 个 Claude 同时写代码”。但真正可迁移的不是并发数量，而是作者把迁移拆成了多个带明确失败信号的队列：编译错误队列、测试失败队列、平台 CI 队列、unsafe 清理队列、安全审查队列。

对 AI-Work-Kit 来说，这对应已有的 `Plans/`、workflow 蓝图和测试/部署门禁，但缺口在于：很多 plan 仍然是人读的任务拆分，还没有统一要求每个子任务绑定“机器可观测失败信号”。可落地形态不是新增一个“大规模迁移 Skill”，而是在 `task-splitter` 和功能开发 plan 模板里加入字段：失败信号、验证命令、回归范围、可自动重试边界。迁移边界也要写清楚：需求判断、验收口径变更、业务取舍不能自动重试。

##### 原则二：审查者和实现者需要在上下文与职责上分离

Bun 的 adversarial review 机制说明，Agent 代码审查不能只是同一个会话最后说一句“检查一下”。实现者目标是完成任务，审查者目标是找反例；二者应该有不同上下文、不同提示、不同成功标准。

Kit 已有 `code-review` Skill，也有阶段门禁，但缺少“同一任务内实现 agent 与审查 agent 的角色隔离协议”。可落地形态是为高风险变更增加 review plan：实现产物、审查输入、必须攻击的维度、审查结论和人工抽样位置。迁移边界是：审查 agent 可以提升覆盖率，但最终 release confidence 仍要由人类基于业务风险、历史缺陷和用户影响做判断。

##### 原则三：人类监督应该上移到 loop 质量，而不是消失

作者在 11 天里并不是“离开电脑等结果”，而是持续读 workflow 输出，发现问题后让 Claude 修改 loop。这个动作非常关键：当 agent 能大量执行时，人类的高价值位置从“改每一行”转为“判断循环是否在收敛、失败模式是否被正确建模、验证是否在骗人”。

Kit 目前已有任务结束后的反馈记录，能把能力缺口回流到进化链，但它更多发生在收尾时。Bun 的案例提示我们，长任务执行中也需要中途 loop health 检查：是否反复修同类问题、是否跳过测试、是否只追求绿灯、是否产生不可维护副作用。可落地形态可以是长任务 plan 的中段 checkpoint：记录当前失败模式、已修改的 loop、人工确认的继续条件。

##### 原则四：迁移成功不等于 diff 合并，发布后验证是同一条链

Bun 在 merge 后继续做安全 review、fuzzing、known regressions 修复和生产验证。这里的通用原则是：大规模 agent 产物需要发布后持续验证，不应把 PR merge 视为终点。

Kit 已有部署和复盘 Skill，但和功能开发产物之间的证据链还可以更硬：对于“大 diff / 大迁移 / AI 主导生成比例高”的任务，plan 应强制记录发布后观察项、fuzz/回归/日志监控结果、已知回归台账和回滚条件。迁移边界是：不是每个小改动都要这么重；只有当变更规模、不可逆性或底层依赖影响大时才启用。

##### 原则五：Agent 的成本要按机会成本评估，而不是按 token 单价单独评估

16.5 万美元听起来很高，但作者的比较基线是三名全上下文工程师一年，外加这一年里无法修兼容性、安全和新功能。Agent workflow 的经济性需要放在机会成本、延迟成本和长期稳定性收益里看。

Kit 的工作流目前更关注效率和质量，较少显式记录“为什么这个自动化值得跑”。可落地形态是高成本任务的 plan 增加一行 cost rationale：人力替代基线、等待成本、验证成本、失败回滚成本。迁移边界是：无法度量的探索任务不必伪造 ROI；但如果要用大量 agent 运行时间，就应该写清楚为什么不是过度自动化。
