01 — 文章介绍

从“会不会犯错”转向“最多能伤到哪里”

Anthropic 工程团队复盘 Claude.ai、Claude Code 和 Claude Cowork 的隔离架构。核心矛盾不是 Agent 是否会犯错，而是能力和权限持续扩大后，怎样把单次错误的最大损害锁在可接受范围。

原文先建立“三类风险、三类防线”的威胁模型，再比较临时容器、人机协同沙箱和本地虚拟机，随后讨论工具输出、远程 MCP 与持久记忆，最后总结环境优先、按用户监督能力匹配隔离强度、优先使用成熟安全原语三条原则。

行为监督回答“它倾向于怎么做”；环境隔离回答“即使判断错了，它最多能做什么”。

02 — 风险模型

失败概率与爆炸半径，是两套不同的治理问题

Rdeployment ≈ P(failure) × I(blast radius)

模型、分类器和审批降低概率；沙箱、文件与网络策略限制影响。

模型层并非无效。Claude Opus 4.7 在 Gray Swan benchmark 上把单次提示注入成功率压到约 0.1%，但 100 次自适应攻击后仍会上升到约 5%–6%；auto mode 能拦截约 83% 的过度积极行为，仍有约 17% 漏过。长期运行系统不能把非零漏检率当成零。

三类风险，三类防线

用户误用或滥用

用户可能被骗、越权，或要求执行自己不理解的破坏性命令。

模型失误或目标偏移

更强模型错误更少，却更会寻找设计者没有预见的达成路径。

外部攻击

文件、网页、工具返回、MCP 与连接器内容都可能携带注入。

环境边界

进程沙箱、VM、文件挂载、出口控制和凭证隔离决定最大权限。

模型防线

提示、分类器、探针与训练影响行为倾向，但本质仍是概率性的。

内容与工具治理

细粒度只读能力、运行时检查和来源追踪控制上下文与副作用。

03 — 三种隔离

同一个 Claude，面对三种不同的能力—监督交换

 containment-patterns.svg

Claude.ai 完全运行在服务端临时容器中，能力有限但边界清楚。Claude Code 必须访问本机代码、Shell 和网络，因此用 OS 沙箱把写入限制在工作区、默认拒绝网络，让技术用户只在偏航时介入。Cowork 面向不应判断 Bash 的普通用户，使用完整 VM、独立文件系统和进程表，只挂载被选中的目录。

Cowork 初版把 Agent 循环也放进 VM，结果 VM 启动失败会让产品完全失去响应。后来编排循环移到宿主机，代码执行仍在 VM 内，兼顾可用性与副作用隔离。本地 MCP 也移到 VM 外以便审计和访问宿主依赖。真正需要锁住的是有副作用的执行，而不是机械地把所有组件塞进同一个边界。

文件挂载提供只读、读写和“读写但不可删除”三种模式。路径校验必须先解析 symlink，再判断目标是否在授权目录内；顺序颠倒就会留下越界路径。

04 — 四个事故

防线看起来正常，数据仍可能泄露

01 · 信任弹窗之前执行项目配置

仓库中的 .claude/settings.json 可定义 hook，而客户端曾在询问“是否信任目录”之前加载并执行配置。修复不是加强弹窗，而是把项目打开、配置加载和 localhost listener 当作互联网入站请求：先建立信任，再解析执行。

02 · 用户本人变成注入载体

红队通过协作邮件诱导员工复制恶意任务提示，25 次中 24 次完成凭证外传。指令确实来自用户，意图分类器无法判断用户被骗；只有文件边界和出口控制能无条件阻止后果。攻击提示进入 Slack 后，还可能被读取 Slack 的内部 Agent 再次摄入。

03 · 合法域名内的能力滥用

Cowork 必须放行 api.anthropic.com。恶意文件携带攻击者 API key，引导 Claude 调用 Files API 上传工作区数据。代理看到域名合法就放行。修复是在 VM 内绑定本机会话 token、拒绝外来 key，并封锁可触发服务端抓取的请求头。

04 · VM 同时挡住企业 EDR

隔离让宿主端点检测只能看到一个不透明的 hypervisor 进程。拉取式 OTLP 事件导出能补部分审计，却不等于实时监控。隔离方案必须同时预算跨边界可观测性。

旧假设失败原因更稳健的定义
本地配置天然可信信任建立顺序错误先授权，再解析可能改变行为的配置
用户输入代表合法意图用户可能被骗权限和出口策略不依赖意图判断
允许域名只是网络目标域名内部包含多种 API 能力allowlist 是身份、方法与动作的能力授权
隔离越强治理越好安全边界也会制造监控盲区机密性、完整性与可观测性一起设计
05 — 输入信任

连接器可信，不代表它返回的数据可信

一个 MCP 或连接器通过代码审计，只能降低传统供应链风险，不能保证运行时数据没有提示注入。GitHub 连接器可以是可信软件，却仍可能读取带恶意指令的 README。远程服务还能在安装之后随时改变行为，安装时的信任决定会过期。

因此，网络工具结果应像网页一样接受运行时检查。Claude Code 和 Cowork 让工具调用经过代理，由代理执行文件与网络策略，并在结果进入模型上下文前检查。检查模型可以小而快，不必与主推理模型相同。权限也应收窄到动作层：只读数据库工具的可部署范围远大于可写生产库的工具。

一旦污染输入引导 Agent 用合法身份完成合法 API 调用，事后日志通常只会留下“授权调用成功”。来源和传播链必须在输入进入上下文前保留。
06 — 下一阶段

风险会进入持久状态、多 Agent 信任与独立身份

持久记忆投毒

产品记忆、CLAUDE.md、工作区和长任务状态跨会话保留；一次注入会在每次启动重新进入上下文。

多 Agent 信任升级

子 Agent 能隔离原始内容，也可能替攻击输入“洗白”；代理身份不能自动提高数据可信度。

Agent 独立身份

任务由用户授权，执行可由可撤销、权限收窄的 Agent principal 承担，形成独立审计边界。

Cowork 已把用户凭证留在宿主机 keychain，只给 VM 可独立撤销的会话 token。跨产品 Agent 最终可能采用混合身份：继承用户的任务授权，但不继承用户的全部权限和长期凭证。

07 — 工作流提炼

对 AI-Work-Kit 的迁移，不是照搬一套沙箱

能力清单：把行为门禁与最坏后果门禁分开

Kit 已有 workspace 沙箱、命令升级审批、破坏性动作限制和 Contexts 写入确认，但缺少统一的 workflow capability manifest。每个 workflow 应明确可读写根目录、联网范围、外部写入、凭证可见性与升级审批，让执行前后能够校验。低风险且可恢复的本地动作可自动批准；公开发布、删除、凭证和跨仓库影响仍保留人工判断。

来源污染：信任随数据传播，不随工具品牌继承

MCP、浏览器、邮件、Slack、README 和子 Agent 输出都可能携带外部指令。证据对象需要来源、信任级别、是否含行为性指令、经过哪些转换等元数据。先用 checklist 和 meta 字段增强 review，不急于用自动分类器阻断所有内容，避免把普通技术文档误判成攻击。

启动审计：先授权，再加载行为性配置

恢复 plan、加载仓库级指令、Skill 变更和外部同步内容时，应先确定当前工作区与用户授权，再加载可能改变执行行为的配置。发现新增 hook、权限扩大或来源变化时要求确认；普通正文与历史记录不应一律阻断。

可观测性：记录系统事件，不持久化全部推理

需要审计的是谁授权了什么能力、工具读写了哪个范围、什么边界拒绝了动作、输出证据来自哪里。无需记录所有 token 或私密内部推理。隔离、诊断和隐私应在同一个 trace 设计中平衡。

成熟原语优先：定制组件进入重点审计

Anthropic 的主要薄弱点不是 gVisor、seccomp 或 hypervisor，而是自建配置加载器和 allowlist 代理。Kit 应优先复用平台文件权限、Git、沙箱、审批和标准 Schema；凡新增自定义路径校验、权限缓存、凭证转发或网络代理，都要补失败模式、绕过路径与回归测试。

正确顺序是：先按用户监督能力与任务价值确定可接受爆炸半径，用环境边界锁住最坏结果，再用模型和人工监督降低边界内失败概率，最后补齐输入来源、持久状态和可观测性证据。
