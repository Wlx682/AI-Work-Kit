# Code Review：自适应知识图谱实现架构审计

**创建日期**：2026-08-08
**PR/分支**：当前工作区未提交实现
**审查范围**：已采纳架构中的 RQ-G01～RQ-G04、Graph Quality、Graph Governance、Observability，以及对应 US-001～US-003 实现

---

## 一、审计结论

**结论：修改后通过。当前实现不建议作为“图谱质量闭环已完成”验收。**

自动化回归是绿色的，但发现 3 个高优先级正确性问题和 3 个中优先级架构/安全问题。最关键的不是规则过严，而是为了提高模型通过率加入了“适配器内审计 + 静默拓扑修复”，使生产 DeepSeek 路径偏离了已确认的 Application 质量编排；同时节点删除路径能够发布无法通过初始严格结构校验的图谱。

当前代码只完成架构的第一阶段：富节点契约、确定性字段门禁、版本/快照/回滚和审计卡。架构中的 Coverage/Granularity/Dependency/Source/Assessment Critic、人工差异审核、自适应活动与学习效果评价尚未落地；这部分属于已声明的后续范围，不计为本轮代码缺陷，但意味着系统还不能宣称“保证学习效果”。

## 二、Findings（按严重度）

### [高] F-01：生产智能适配器越权执行质量门禁，形成双层重试并改变失败语义

- **位置**：
  - `backend/infrastructure/deepseek_intelligence.py:141-184`
  - `backend/application/service.py:1424-1456`
  - `backend/tests/test_learning_intelligence.py:319-339`
- **架构约束**：
  - 架构要求 Application 编排 Graph Authoring → Graph Quality → Graph Governance；Infrastructure 只是智能端口适配器。
  - US-001 落点明确写明“Infrastructure 仅实现智能端口”；US-002 明确写明“候选审计在 Application 内完成；Infrastructure 只生成 schema，不能决定发布”。
- **问题**：`DeepSeekLearningIntelligence._parse_publishable_course_graph()` 直接调用 `audit_course_graph_draft()`，把 Critical 转为 `INVALID_INTELLIGENCE_OUTPUT` 并在适配器内重新生成；Application 随后又做一次相同门禁与重试。
- **影响**：
  1. 单层设计的“最多重试一次”在真实组合路径中最多会触发 4 次模型调用（适配器 2 次 × Application 2 次）。
  2. Production DeepSeek 与 Scripted/Fake Intelligence 的业务语义不同；AC2 的无残留拒绝测试只覆盖 Fake 路径，不能证明生产路径遇到首个 Critical 时会返回 `GRAPH_AUDIT_FAILED`。
  3. DRAFT/AUDITING/NEEDS_REVISION 状态、首次审计结果和修订差异没有进入 Governance/Debug，失败候选不可追踪。
  4. 重试只带错误文本，没有传入原图，实际是“全量重生成”，不是架构定义的 `revise(graph, findings)`。
- **建议**：适配器只负责模型调用、JSON 解析与 schema validation；在 Application 中实现唯一的 `generate → audit → revise(draft, findings) → re-audit` 编排，并保存每轮 draft/audit/trace。为真实 DeepSeek 适配器组合路径增加“总调用次数不超过 2、首轮 Critical 可观测、最终失败错误码稳定”的契约测试。

### [高] F-02：静默修复拓扑并复制后代学习元数据，会让“形式通过”冒充“语义对齐”

- **位置**：
  - `backend/application/intelligence.py:414-482`
  - `backend/infrastructure/deepseek_intelligence.py:165-168`
  - `backend/tests/test_learning_intelligence.py:280-317`
- **架构约束**：Schema/Structural Gate 失败应直接拒绝；Assessment Audit 要验证 Objective、Activity、Rubric、Evidence 对齐；图谱修订应形成可审计的新草稿/差异。
- **问题**：`normalize_course_graph_draft()` 遇到非根单子节点时，把子节点提升到祖父节点，同时把原父节点变成叶子，并从所有后代复制 `key_questions`、`activity_capabilities`、`mastery_rubric` 直到满足最小数量。
- **影响**：
  1. 后代的掌握量规和活动能力不一定能评价原父主题，数量满足不代表目标—活动—评价对齐。
  2. 模型原始知识结构被改变，却没有 GraphOperation、finding、diff 或 provenance，用户无法知道系统修了什么。
  3. 现有测试只断言“修复后严格 validator 和字段计数通过”，因此把架构偏差固化成了绿色测试。
- **建议**：删除发布前的语义数据拼接。结构问题由确定性 Gate 产出 finding，再由 Graph Authoring 基于原 draft + findings 生成完整修订稿；每个叶子的 objective/question/activity/rubric 必须由同一节点语义重新生成并独立审计。

### [高] F-03：节点变更和回滚使用宽松结构校验，可发布系统自身严格 validator 不接受的图谱

- **位置**：
  - `backend/application/service.py:1233-1241`
  - `backend/application/service.py:510-524`
  - `backend/application/graph_quality.py:85-100`
  - `backend/tests/test_learning_api.py:719-734`
- **架构约束**：所有 expand/split/update/delete 都基于新草稿重新审计；Structural Gate 失败直接拒绝；发布版本必须满足相同不变条件。
- **问题**：初始生成使用严格 `validate_course_graph_draft(draft)`，但变更和回滚都传 `allow_single_child=True`。随后 `audit_course_graph_draft()` 又无条件把 `structure` 写成 `True`。
- **运行态复现**：从合格 v1 删除叶子 `runtime-state` 后，系统发布 v2 且 audit=`passed`；把已发布 v2 再交给严格 validator，得到 `INVALID_INTELLIGENCE_OUTPUT: internal decomposition nodes must split into at least two child topics`。
- **影响**：同一 GraphVersion 契约因入口不同而漂移；审计卡会向用户显示 Passed，但图谱无法通过首次发布所使用的结构门禁。历史快照还会在回滚时继续被宽松接受。
- **建议**：创建、变更、快照恢复使用同一个严格 validator。删除叶子后若父节点只剩一个孩子，应拒绝 Proposal，或要求 Proposal 同时给出明确 merge/reparent 操作并让最终候选满足严格不变条件。`GraphQualityAudit.structure` 必须来自实际结构校验结果，不能写死。

### [中] F-04：图谱发布与回滚不是原子操作，I/O 失败会造成 active projection、版本、审计和快照不一致

- **位置**：
  - `backend/domain/contracts.py:801-805`
  - `backend/domain/contracts.py:1281-1284`
  - `backend/domain/contracts.py:2051-2067`
  - `backend/application/service.py:1294-1392`
  - `backend/application/service.py:532-564`
- **架构约束**：图谱版本不可原地覆盖；长流程可恢复；发布/回滚保持一致；非法回滚零领域写入。
- **问题**：JSON Repository 将 course、多个 node、edges、version、audit、snapshot 分别直接写到最终文件。变更流程先在 `apply_graph_operation_api()` 覆盖当前 course graph，再创建新版本/审计/快照；回滚则先改两个 version 状态，再覆盖 active course graph。
- **影响**：任意中间写失败都可能出现“图已变但 active_version_id 仍旧”“vN+1 active 但快照缺失”“两个版本状态与 course 指针不一致”或单个 JSON 半写损坏。现有测试只覆盖业务输入错误，没有故障注入。
- **建议**：把发布/回滚收敛为 Repository Unit of Work。先在临时目录写完整 immutable version/audit/snapshot 并校验 hash，使用原子 rename 提交，最后原子切换唯一 active pointer；启动时检测并清理未完成事务。增加每个写入步骤失败的故障注入测试。

### [中] F-05：Debug 默认持久化完整学习/模型 Payload，且没有架构要求的 trace/span 关联

- **位置**：
  - `backend/infrastructure/debug_events.py:33-74`
  - `backend/infrastructure/deepseek_intelligence.py:103-118`
  - `backend/application/service.py:171-203`
- **架构约束**：默认只保存脱敏摘要；用户明确开启“详细 Payload”后才记录内容，并提供隐私提示与清除；事件共享 `trace_id/span_id/parent_span_id`。
- **问题**：当前所有 LLM messages、模型完整响应、HTTP request/response 都默认写入 `events.jsonl`。脱敏仅按少量 secret key 名处理，不会移除学习目标、回答、偏好或可能含个人信息的自由文本；事件只有可选 `correlation_id`，没有 trace/span 层级。
- **影响**：用户未显式授权就长期落盘学习内容；Debug 无法可靠还原一次请求内 agent/tool/data 的父子调用链。Capabilities 也只声明 Skills 未启用，尚未覆盖架构中的 policy/graph/evaluation 分类。
- **建议**：默认只写 hash/ref/字段规模/状态/耗时；增加显式 Payload 开关、保留期、隐私提示和清除 API/UI；引入 trace context 并贯穿 HTTP → Application → Agent/LLM/Tool → Repository。

### [中] F-06：失败门禁没有把 finding 暴露给用户，错误不可行动

- **位置**：
  - `backend/application/service.py:1442-1455`
  - `app/lib/src/localization/message_localizer.dart:78-86`
  - `app/lib/src/nexus_app.dart:3023-3095`
- **架构约束**：`GRAPH_AUDIT_FAILED` 客户端处理为“展示审计报告，不允许发布”；GraphAudit 响应包含 finding、node 和 suggested operation。
- **问题**：服务端失败时只拼接规则 code 到 message，没有返回结构化 audit/details；Flutter 又把该 code 固定映射为通用文案，丢弃服务端 message。审计卡只展示通过后版本、分数、检查项和问题数量，不展示 findings。
- **影响**：用户只能看到“请重试或缩小目标”，无法知道哪个节点缺少量规/活动、结构哪里不合法，也无法选择修订或调整目标。这与当前截图表现一致，并削弱 Human Review/Graph Governance 的可用性。
- **建议**：错误 envelope 返回 `audit_id/status/scores/findings`；前端提供失败审计详情（节点、规则、建议操作）及“按 findings 修订”入口，同时保留简洁顶层提示。

## 五、建议修复顺序

1. **先修 F-03**：封住“Passed 但严格非法”的发布路径，并补统一不变条件测试。
2. **再修 F-01/F-02**：把 audit/revise 编排收回 Application，停止静默复制学习元数据。
3. **修 F-04**：建立原子发布/回滚与故障恢复，避免后续真实数据损坏。
4. **修 F-06**：让失败 finding 对用户可见、可行动。
5. **修 F-05**：在继续扩大 Debug 数据采集前完成默认摘要、清除和 trace/span。
6. 上述稳定后，再进入 Critic、多样化活动和学习效果闭环，避免在不可靠图谱版本基座上继续扩功能。
