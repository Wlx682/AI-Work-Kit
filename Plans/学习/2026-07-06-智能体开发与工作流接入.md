# 智能体开发与工作流接入

> 学习方法：理论一句讲清，实践落到 AI-Work-Kit 可核验路径，最后沉淀成能接入工作流的自研智能体工具。
> 管理方法：学习进度也走工作流式闭环，按 Plan 勾选推进；每个知识点都单独跑一轮“理论 → 测试先行 → 工程实践 → 接入试跑 → 复盘”，再决定下一步学什么和改什么。
> 建设原则：工作流建设必须测试先行，先定义验收样例和失败样例，再实现流程、Prompt、脚本或 Skill。
> 工程边界：AI-Work-Kit 只管理学习计划、蓝图、门禁、复盘；智能体源码、依赖、运行命令和自动化测试放在独立工程。

## 一、与前课关系

- 前置能力链：LLM/提示词 → 上下文管理 → RAG → Agent → Skill → MCP → 评估与安全 → Kit 综合实践。
- 本项目不跳过基础课，但每一步都围绕同一个实践主线：让智能体理解 `AI-Work-Kit` 的 workflow 蓝图、Plan 状态和下一步动作。
- 推荐贯穿案例：`workflow-router` + `workflow-status.py` + `.workflows/blueprints/*.json`；第 4 课后对照 `learning-audit-assistant` 的多步审计链。

## 四、工作流推进方式

| 阶段 | 目标 | 进度证据 | 退出条件 |
|------|------|----------|----------|
| 学习输入 | 补齐当前实现所需理论 | 本 plan 对应小节勾选、学习笔记 | 能说清本轮要解决的 Agent 能力 |
| 测试先行 | 先定义验收与失败样例 | 测试用例、输入输出样例、人工验收清单 | 没有测试样例，不允许进入工程或工具开发 |
| 工程选型 | 创建独立智能体工程并定技术栈 | 工程路径、README、测试命令、技术选型记录 | 没有独立工程和可运行测试命令，不允许进入工具开发 |
| 工具开发 | 做出一个最小能力 | 脚本、Skill 草案或伪实现 | 能在本地对一个 workflow 样例输出结果 |
| 工作流接入 | 接到 AI-Work-Kit 的实际入口 | 触发词、命令或 Skill 路由说明 | 能通过真实请求调用 |
| 效果观察 | 看智能体是否真有用 | 成功/失败样例、friction 记录 | 明确下一轮保留、修正或放弃什么 |
| 反馈进化 | 把结论回填计划 | 本 plan 勾选、skill_run 或学习笔记 | 下一轮任务清晰 |

每个知识点只做一个小闭环：学一个点 → 写验收/失败样例 → 在独立工程实现一个工具动作 → 接入一个入口 → 跑一个真实样例 → 记录效果。

#### 第 1 轮理论摘要

1. Token 是模型读写的最小单位；上下文越长，成本越高，也越容易把无关材料带进判断。
2. 上下文窗口是模型一次能看见的材料上限；工作流智能体不能把全库塞进去，应只给本轮相关的 Skill、蓝图和 Plan。
3. 结构化 Prompt 是一次任务契约：说明背景、角色、任务、输出格式、不可做事项和判断标准。

#### `workflow-router` 边界拆解

| 类别 | 内容 | 对路由 Prompt 的含义 |
|------|------|----------------------|
| 触发条件 | 全流程开发、启动项目、客户端功能、电脑管理、`workflow=client-dev`、`workflow=client-dev`、`workflow=computer-mgmt` | 可以输出具体 workflow，并给下一步命令 |
| 不响应场景 | 单阶段任务、普通代码任务、普通资料整理、未知 workflow | 不强行归类到默认蓝图，必要时返回 `needs_clarification` |
| 输出边界 | 只选蓝图、确保 Epic/看板、运行状态脚本、必要时看 gate 详情 | 输出下一步建议，不写需求、方案、代码或测试 |
| 禁止事项 | 不替代阶段 Skill、不靠 `lifecycle_state` 推进、不把 Epic 当状态机 | Prompt 必须把写入和推进动作留给后续确认 |

#### 最小路由 Prompt v0

```text
你是 AI-Work-Kit 的只读 workflow 路由建议器。

背景：
- 你只负责把用户自然语言请求映射到 workflow 蓝图和下一步命令。
- 你不写需求、方案、代码、测试、部署内容。
- 你不修改 Plan、Contexts、Epic，也不跳过 workflow-gate。

可选 workflow：
- client-dev：客户端功能、做个功能、全流程开发、启动项目。
- computer-mgmt：电脑空间、电脑管理、清理电脑、磁盘满了、释放空间、备份电脑、系统加固。
- unknown：显式 workflow 不存在，或请求不属于工作流入口。
- needs_clarification：信息不足，无法安全选择。

判断规则：
1. 如果用户显式给出 workflow=xxx，优先使用该 workflow；若不在可选 workflow 中，返回 unknown。
2. 如果是单阶段任务，如 PRD 评审、日报、学习审计、Figma 对稿、测试计划、部署清单、代码 review，不要路由到 旧版通用执行器，返回 needs_clarification。
3. 如果是普通代码任务、修 bug、开发环境报错、普通资料整理，不要默认路由到 client-dev。
4. 只有明确是客户端功能/全流程开发，才选择 client-dev。
5. 只有明确是电脑管理/清理/备份/加固，才选择 computer-mgmt。

输出必须是 JSON，不要输出多余文字：
{
  "workflow": "client-dev | computer-mgmt | unknown | needs_clarification",
  "reason": "一句话说明命中或不命中的依据",
  "next_command": "建议用户执行的下一步命令；不能安全建议时填空字符串",
  "allowed_actions": ["只读建议"],
  "blocked_actions": ["不写文件", "不跳门禁", "不替代阶段 Skill"]
}

用户请求：
{{user_request}}
```

#### 自测答案：为什么这个 Prompt 还不是 Agent？

它只是一次性分类和格式化输出，还没有形成 Agent 循环。真正的 Agent 至少要能规划下一步、调用工具、读取观察结果、根据结果修正判断，再输出最终建议。这个 Prompt 目前不会读取 `.workflows/blueprints/*.json`，不会运行 `workflow-status.py`，也不会根据脚本输出重新规划，所以它只是后续 Agent 的“路由判断模块”，不是完整 Agent。

### 6. MCP 与工具接入：给智能体标准插头

理论：MCP 是工具连接层，负责让 Agent 以标准方式访问外部系统或本地能力。

实践：先复用已有脚本和文件系统能力，再评估是否需要把自研 Agent 能力包装成 MCP。

- [ ] 读 `Contexts/MCP进阶指南.md`，说明 MCP 和普通脚本工具的边界。

- [ ] 自测：什么时候「先写脚本」比「马上写 MCP」更稳？

### 7. 评估与安全：别让智能体误驱动工作流

理论：Agent 接入工作流后，最重要的是边界、可追溯、可回滚和人类确认点。

实践：为自研 Agent 定义最小评估集和禁止动作。

- [ ] 写 5 个测试用例：正常路由、缺 plan、蓝图不存在、门禁阻塞、用户要求越权。
- [ ] 定义禁止动作：不擅自写 Contexts、不擅自改 Epic 驱动状态、不擅自跳过门禁。

### 8. 综合实践：接入 AI-Work-Kit 的最小可用智能体

理论：一个可用 Agent 应该先成为现有工作流的好公民，再逐步扩大权限。

实践：产出一个基于 DeepSeek API 的 MVP，可以辅助判断当前工作流状态并建议下一步，但写入动作必须显式确认。

- [ ] 明确 MVP 输入：自然语言、workflow 名、plan 或 epic 路径。

- [ ] 设计模型适配边界：业务循环不直接依赖 DeepSeek SDK，只依赖 `llm_complete(messages)` 这类薄封装。
- [ ] 完成最小实现或伪实现，并用 `client-dev` / `bugfix` 各跑一个样例。
