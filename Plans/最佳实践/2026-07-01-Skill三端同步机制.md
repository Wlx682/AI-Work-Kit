# 用校验脚本消除 Skill 三端定义的漂移风险

**王龙祥 · 技术 · 2026-07-01**

> 摘要：AI-Work-Kit 的每个 Skill 定义需在三处（Cursor、Claude Code、人类文档）保持一份完全一致的副本。此前依赖手工同步与肉眼核对，随 Skill 数量增长易出现漏改。引入一个校验/同步脚本后，单次同步操作从约 8–10 分钟（估算）降至数秒，19 个 Skill 保证字节级一致，并可作为 pre-commit 门禁拦截不一致提交。

## 问题

Kit 中每个 Skill（如「续做」「日报」等触发词能力）的定义分布在三个位置，三份内容必须严格一致：

```
一个 Skill = 三份必须一致的副本
├─ .cursor/skills/<name>/SKILL.md   Cursor Agent 入口
├─ .claude/skills/<name>/SKILL.md   Claude Code 入口
└─ Skills/<name>.md                 人类阅读的真理源
```

每次修改一个 Skill，都需要将改动手工同步到另外两端，并逐份核对一致性。当 Skill 数量增长到 19 个后，仅靠人工记忆和肉眼比对，「改一端漏两端」的概率明显上升，且没有任何强制机制兜底。

## 方案

编写 `scripts/sync-claude-skills.sh`（151 行），提供两个模式：

- `--check`（默认）：逐字节比对三端，校验三项——三端 Skill 名称集合一致、同名 Skill 内容字节级一致、每个 Skill 在 `Skills/` 存在真理源；任一项不满足即以 `exit 1` 失败。可挂入 pre-commit 或 CI 作为门禁。
- `--sync`：以 `.cursor/skills` 为基准，将 `.claude/skills` 及用户全局副本强制刷新为一致，同时保留用户自装的 Skill 不被误删。

修改 Skill 的流程固定为：改 `.cursor` 副本 → `--sync` 同步 → `--check` 验证。

## 踩到的坑：`--sync` 在存在差异时反而不执行同步

第一版脚本有两处缺陷，使 `--sync` 恰恰在最需要它的场景（三端不一致）下失效。

**缺陷一：控制流顺序颠倒。** 同步逻辑被放在了「校验失败即 `exit 1`」之后。因此当三端存在差异时，脚本在校验阶段就报错退出，永远执行不到同步代码；只有三端本已一致时才会进入同步分支，属无效操作。修复：在 `--sync` 模式下检测到差异时不提前退出，改为以 `.cursor` 为基准强制覆盖。

**缺陷二：`set -euo pipefail` 与 `diff` 退出码冲突。** 打印差异的 `diff -u | head` 中，`diff` 在发现文件不同时返回非零退出码，被 `errexit` 判定为错误并中断整个脚本，导致差异信息还没打印脚本就终止了。修复：该行追加 `|| true`，避免非零退出码中断脚本。

两处修复见提交 `00dae1d`。修复后 `--sync` 才真正可用，`--check` 才能稳定作为门禁。

## 效果

| 指标 | 之前 | 之后 |
|------|------|------|
| 单次同步 + 核对耗时 | 约 8–10 分钟（估算） | 一条命令，数秒 |
| 一致性保障方式 | 人工记忆 + 肉眼比对 | 逐字节校验 19 个 Skill |
| 漏改后果 | 可能长期未被发现 | `--check` 当场 `exit 1`，提交被拦 |
| 可复用性 | 每次人工重走流程 | 已固化为脚本，可挂门禁 |

> 说明：8–10 分钟为**估算**。脚本引入前未留存工时记录，此处依据「三端 × 定位 + 编辑 + 核对」的手工步骤估算，非实测，如实标注。

## 复用说明

- 前提：仓库采用 `.cursor` / `.claude` / `Skills/` 三端结构，且已有 `scripts/sync-claude-skills.sh`。
- 建议下一步：将 `--check` 挂入 pre-commit 或 CI，使「三端不一致」在提交时即被拦截，而非事后发现。
- 溯源：脚本 `scripts/sync-claude-skills.sh`（151 行）；修复提交 `00dae1d`；`--check` 输出「✓ 三端一致：19 个 Skill」。

小结：本质是将「多端定义一致性」的保障方式，从依赖人工核对改为脚本逐字节强制校验并可作为提交门禁，从机制上消除漏改风险。
