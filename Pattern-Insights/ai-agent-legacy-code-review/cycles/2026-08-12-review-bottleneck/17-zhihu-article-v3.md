编码 Agent 真正进入团队后，最先改变的是产出速度：以前需要几天完成的分析、修改和测试，现在可能在几个小时内连续生成。随之出现的显性问题，是代码审查开始排队，回归压力不断上升。

很多团队因此把它理解成新的“评审瓶颈”：Agent 写得太快，人审不过来，所以要补充规则、细化需求、增加检查，再让更多人参与验收。

这些措施有用，却没有触及更深的变化。Agent 加速的不只是代码生产，也加速了误解在需求、方案、代码和测试之间的传递。等人类在末端发现问题时，错误往往已经被一整套相互支持的产物证明成了“正确”。

真正失配的不是人的阅读速度，而是系统暴露错误的速度。

本文的判断是：当 Agent 开始大幅提高执行速度，技术负责人首先要建设的不是更厚的规则手册，而是一套能让系统级错误尽早显形、限制后果、支持恢复，并把真实失败转化为新控制能力的反馈架构。

## Agent 加速以后，错误也改变了形态

传统开发中，一个理解偏差通常随着人的工作节奏逐步展开。需求、设计、实现和测试之间存在时间间隔，同事也可能在交接时发现不一致。

Agent 把这些环节压缩到同一条高速生成链上。它可以根据一份不完整的任务说明生成方案，再根据方案写代码，最后根据同一套理解补齐测试。每一份产物都能支持下一份产物，整条链内部越来越自洽。

问题在于，内部自洽不等于外部正确。

一个 Agent 可以完整执行任务、通过所有代码检查，却仍然理解错了目标、采用了错误的代理指标，或者漏掉没有进入测试的下游约束。此时没有异常迫使系统停下来，任务只会顺利走向 Done。

所以，Agent 带来的新风险不只是“写出错误代码”，而是“把错误任务顺利完成”。前者通常会在代码层留下红灯，后者可能一路全绿。

## 代码断言仍然有效，只是错误越过了它的边界

代码断言没有失效。输入不合法、状态不可能、返回值越界，仍然可以被测试、类型检查和运行时约束迅速发现。

但这些机制只能检查已经进入代码世界的约束。它们能回答“实现是否符合已写下的要求”，不能自动回答“这次任务是否仍然服务于真实目标”。

假设团队让 Agent 重构遗留系统中的计价模块。Agent 删除重复实现、补齐单元测试，所有检查都通过。随后，团队用历史订单重放，发现少量账单金额发生了变化：公式没有写错，重构却改变了舍入顺序。

这是一个假设场景，但它能说明边界在哪里。函数测试证明每个局部满足预期，历史账单才是任务层的外部证据。没有后者，Agent 完成的是“代码重构”，不一定是“在保持业务行为不变的前提下完成重构”。

错误没有逃过所有检查。它只是发生在现有检查没有观察的系统层。

*图 1｜当任务级证据缺席，局部检查全绿也可能把错误一路送到完成声明。*

这条链真正缺少的，是代码检查之后、完成声明之前的任务级证据：系统凭什么相信目标已经实现，哪些结果一旦出现就必须拒绝 Done。

## 为什么增加规则仍然追不上开放任务

已经认识到的风险当然应该写成规则。

[AgentSpec](https://arxiv.org/abs/2503.18666) 展示了如何把约束表达为触发条件、检查谓词和干预动作，在 Agent 运行到关键位置时直接执行。关于 [LLM Agent 实时失败检测与修复](https://arxiv.org/abs/2608.02464) 的研究也表明，逐步遥测、完成度检查、确定性验证和回滚能够让一部分失败在最终输出前暴露。

这些工作同时说明了同一个边界：规则擅长处理已经被表达出来的错误，却无法预先穷举开放任务中的全部偏差。一个结果如果形式上完全合理，只是偏离了没有写下来的真实意图，系统仍然需要外部结果来校准。

因此，真正的问题不是“还缺哪条规则”，而是“系统发现未知失败以后，能不能让下一次更早失败”。

第一次出现的未知错误未必能够完全避免。但它不应该直接获得无限影响范围，也不应该在复盘后仍只停留在人的记忆里。工程系统能做的，是控制第一次失败的成本，并缩短同类错误从未知变成可执行判断的路径。

## 架构首先要改变错误的成本

一套围绕 Agent 的反馈架构，不需要预先规定 LLM 每一步怎么走。它首先应稳定提供四种能力：

| 系统能力 | 它改变什么 |
|---|---|
| 看得见 | 知道 Agent 接受了什么目标、依据什么证据、做出什么关键判断 |
| 有边界 | 让高风险探索先发生在历史回放、影子环境、小范围灰度或受限权限内 |
| 可恢复 | 发现偏差后可以停止、隔离、回到检查点，而不是只能接受最终结果 |
| 会进化 | 把静默失败、误报和真实结果变成下一版任务证据、评估器或控制规则 |

这四种能力不是四条新的提示词。它们需要生成、证据与控制、受控进化三部分协同工作。

*图 2｜真实结果先形成候选进化，再经过回放、比较、灰度和批准进入系统。*

生成与探索保留 LLM 寻找新路径的价值；证据与控制判断它是否仍在允许边界内、是否有资格宣布完成；真实结果进入进化环节，形成候选修改，再经过回放、比较和灰度进入下一版系统。

这里的控制目标不是消灭不确定性。没有探索能力，Agent 只会退化成固定流程。真正要管理的是不确定性的后果：让探索继续发生，但让错误更早出现、影响停在局部、失败能够恢复。

## 进化本身也必须接受控制

这套架构最危险的反方也很直接：如果系统能够根据反馈持续修改提示、技能、评估器和工作流，它可能成为一个更难审查的自修改系统。

一次偶然失败可能被错误地固化成普遍规则；Agent 与评估器可能共享同一种盲点；系统也可能为了提高代理指标，牺牲真正重要但难以量化的目标。

因此，真实失败不能直接改写生产系统。它首先只能形成一个候选变更：准备改变什么，依据哪些证据，试图修复哪类失败，又可能损害什么能力。

候选变更需要在历史轨迹上回放，与旧版本比较，在有限范围内试运行，并保留撤销路径。只有证据支持它确实降低了目标错误，而且没有制造不可接受的误杀，才进入正式系统。

换句话说，进化本身也必须可观察、可比较、可回退。

这并不保证每次改进都正确。它保证的是，即使改错了，错误进化也不会无声地扩散到所有任务。

## 技术负责人应该先接通哪条反馈链

当 Agent 开始提高交付速度，继续扩大并发会让旧反馈结构里的延迟更加危险。一个更稳妥的起点，是选择一类高频、结果可验证的任务，先把下面这条链接通：

1. 明确任务想改变什么，以及什么结果绝不能改变。
2. 找到 Agent 自我总结之外的完成证据，例如历史重放、下游状态或真实用户结果。
3. 在证据不足时拒绝任务进入 Done，并让高风险探索停留在有限范围。
4. 把漏判保存成候选断言或评估器，在历史任务上回放后再进入下一版工作流。

这条链不会一次解决所有 Agent 可靠性问题。它解决的是更基础的一件事：让系统开始拥有可用的错误信号。

没有这种信号，自动进化只能围绕自己的代理指标循环；有了它，团队才能逐步知道哪些规则值得增加、哪些权限应该收缩、哪些失败可以自动恢复。

代码工程化的价值，是让错误代码尽早失败。

智能体工程化的第一步，则是让错误任务无法悄无声息地完成。
