## 材料 2：[Research Update: Algorithmic vs. Holistic Evaluation](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons/)

- 我原来以为：
- 我现在注意到：代码断言没有失效；智能体已经不会再生产触发这些断言失败的代码。真正缺失的是智能体系统级错误的快速反馈：任务可以顺利完成、代码断言全部通过，但实际结果是错的，而且没有人知道。
- 我同意/不同意，因为：材料证明自动测试与整体可合并性之间有缺口，但只描述评估缺口，没有进一步研究如何让“表面成功、实际错误”的任务立即失败。
- 与其他材料的联系/冲突：材料 1 说明评估成为中心，材料 2 说明现有断言不足；两者共同留下“怎样低成本地产生有效错误信号”的空白。
- 我还缺的证据：系统级正确性的参照信号是什么；怎样把“任务顺利完成但结果错误”转化为即时、可定位的失败信号；快速失败能力是否是自动进化的必要前提。
- 想保留的原话：让智能体快速出错，是我们必须优先要解决的问题，不然自动进化也无从谈起。
- AI 追问：当代码断言全部通过时，什么产物或结果可以证明整个任务其实是错的？

## 用户对既有批注的关键修正

- 代码断言本身没有失效。
- 智能体已能稳定生成不触发既有代码断言的实现。
- 真正的盲区位于智能体系统层：局部检查全部通过，任务被宣布完成，但系统目标并未实现，而且没有及时反馈。

- 想保留的原话：就像做 Linux 系统一样，重要的是系统架构，不是规则细节。

## 用户对控制内核模式的修正

- “所有关键行为经过统一执行边界”方向基本正确，但尚未体现进化模块。
- 进化不是规则细节，也不是事后复盘，而必须进入智能体系统的核心架构。

## 用户对 Linux 类比边界的修正

- 三平面方向基本准确，但这套系统的核心必须围绕 LLM 智能体，而不能死板套用 Linux。
- Linux 的核心任务是可靠地发挥确定性计算；智能体系统的核心任务是发挥和管理强大 LLM 的不确定性，二者的核心矛盾不同。
- 系统控制的目标不是消灭不确定性，而是让有价值的探索和生成得以发生，同时控制错误的可见性、影响范围与反馈成本。
- 想保留的原话：智能体系统是发挥和管理不确定性的强大 LLM。
