## 材料 1：How Do Practitioners Build SE Agents?

- 原文：[How Do Practitioners Build SE Agents? Insights from a Mixed-Methods Study](https://arxiv.org/abs/2607.10856)
- 作者：Yunbo Lyu、David Williams 等
- 版本：2026-07-25，arXiv v2
- 研究对象：构建软件工程 Agent 的从业者，不是普通团队使用 Agent 改造遗留代码的直接研究

### 一句话摘要

**来源结论：** Agent 让实现变便宜，但没有消灭软件工程工作；瓶颈转向需求、协调、评审、评估和维护，开发过程开始由持续评估驱动，提示词、技能、上下文和脚手架也成为需要测试、版本管理和持续维护的一等工程产物。

### 研究怎么做的

- 对 12 个组织的 20 名从业者进行半结构化访谈。
- 对访谈做主题分析和混合卡片分类，并把结论交还受访者核对。
- 再调查 80 名有 SE Agent 构建经验的从业者，验证工作流、过程变化、挑战和实践。
- 研究样本偏向大型科技公司和研究/工程岗位；结论主要来自自述，并记录的是 2026 年 2—5 月这一快速变化窗口。

### 摘要导读式翻译

软件工程 Agent 已能理解大型代码库并以较少人工干预执行工程任务，但业界究竟怎样构建这些 Agent，此前缺少直接研究。作者发现：随着实现成本降低，瓶颈并未消失，而是发生转移。需求、协调和部署等原有工作变得更显眼，审查生成代码和评估 Agent 行为则成为新增的核心劳动。

团队逐渐采用一种七阶段的循环工作流，并出现五项过程变化。其中最关键的是“评估驱动开发”：评估不再只是最后验收，而是更早定义并持续引导每轮迭代。同时，规格也发生变化——提示词、技能、上下文定义和脚手架行为成为与代码一起测试、评审和版本控制的工程产物。

但评估本身并不可靠：信号可能无效、随机波动、迅速过时或成本过高。此外，Agent 生成代码的速度可能超过人的理解速度，形成“理解债”；外部模型即使团队什么都没改，也可能因供应商升级而改变行为。

### 七阶段循环

1. **需求**：定义预期行为、边界、输入、输出和约束；规格同时写给人和 Agent 读。
2. **评估**：提前建立成功标准、基准、阈值和结果指标，用来比较迭代并判断系统是否足够好；部署后仍持续运行。
3. **数据**：为评估和必要时的训练提供基准、真值、运行轨迹、真实提交中的标准补丁等材料。
4. **系统构建**：模型策略通常从成本最低的现成模型/API 开始；跨模型复用的脚手架则包含上下文、记忆、工具、技能、权限和编排。
5. **测试、评估与部署**：测试确定性正确性，评估非确定性的任务能力；两者共同决定是否发布。
6. **人的反馈环**：通过内部试用、人工评审、验证 Agent、小范围发布和 A/B 测试获取反馈，并回写评估案例、提示词、脚手架和训练数据。
7. **自适应维护**：基础模型变化后，重新评估能力、失败模式及既有脚手架，更新需求、评估集、模型选择和系统设计。

### 五项过程变化

| 变化 | 来源结论 | 问卷支持 |
|---|---|---:|
| 实现变便宜 | Agent 把实现推到更高抽象层，使单项工作更快或单轮产出更多 | 84% |
| 劳动被显露并新增 | 原有需求、协调、部署问题变得显眼，同时新增大量生成产物评审和行为评估 | 95% |
| 评估驱动开发 | 评估由终点检查变为定义更早、贯穿迭代的控制机制 | 82% |
| 角色边界缩小 | 可运行产物变便宜，研究、产品和工程职责更容易合并 | 71% |
| 规格成为核心产物 | 提示词、技能、上下文和脚手架行为与代码一起测试、评审、版本化 | 77% |

受访者对整个七阶段循环的认同度为 91%。这些数字是对作者表述的认同度，不等于这些实践已经证明能提升交付绩效。

### 六类挑战及作者整理出的应对方向

1. **评估缺少可信信号**：测试可能只因“已有”而成为裁判，却无法覆盖性能、可维护性、安全和工程品味；同一配置还可能多次运行得分不同。建议从生产结果反推验证信号、先设计验证再分配任务、分层并持续更新评估集，同时控制评估成本。
2. **什么都没改，但一切都变了**：模型供应商升级可能让行为突变，也可能使为旧模型弱点制作的脚手架变成负担。建议区分长期有效的基础设施与暂时补偿模型缺陷的规则。
3. **性能领先于安全**：团队可能因安全约束降低效率而绕开它。高风险限制应放在提示词以下，由权限、沙箱、工具拦截和人工授权强制执行。
4. **Agent 只能取回写下来的知识**：设计缘由、历史约束和项目惯例常存在人脑里；一次塞入更多上下文也会制造语义混乱。建议把反复出现的知识沉淀为技能，渐进提供最小充分上下文，遇到未外显知识时升级给人。
5. **理解债**：代码进入系统的速度超过人的理解与审查速度，评审负担被推向下游。论文提出两种应对：继续把维护交给 AI，或保留规格、测试、约束和基础设施，使软件可重新生成和验证；作者指出这仍未解决。
6. **生产力指标失效**：代码量和提交数上涨不代表团队或业务价值上涨，个人看似加速也可能给其他人制造审查与维护成本。代码量最多只能作为诊断信号，不能作为绩效目标。

### 与本期研究的关系

**直接支持：**

- 评估不是单次门禁，而是贯穿需求、构建、部署和维护的循环机制。
- 提示词、技能、上下文、评估集和脚手架都是应被测试、版本化和维护的产物。
- 人的反馈与自适应维护共同说明“进化”必须进入正式工作流。
- 实现加速会把瓶颈转移到需求、审查、理解和评估，与我们的起点高度一致。

**没有直接证明：**

- 论文研究的是“怎样构建 SE Agent”，不是“怎样用 Agent 改造遗留系统”。
- 它没有证明所有环节的每个输入、输出产物都必须评估。
- 它没有提出 PID 或“微分项”，也没有测量产物评估结果的跨轮次变化率。
- 七阶段循环与我们的“执行环 + 进化环”相似，但双环结构是我们的解释，不是论文原结论。

**AI 关联推断：** 这份材料为双环假设提供了现实原型，但我们的增量在于：把“进化”从末端维护提升为横跨所有工作产物的规则进化机制，并研究如何依据质量趋势而非单次评分来调节流程。

### 深读时最值得看的部分

- Figure 2：七阶段循环和反馈箭头。
- Shift 2：为何实现变快后，需求和审查劳动反而成为中心。
- Shift 3：评估驱动开发。
- Shift 5：规格成为一等工程产物。
- Challenge 1：评估信号为何失真、波动和过期。
- Comprehension Debt：生成速度如何把理解和评审负担推向下游。

## 材料 2：Algorithmic vs. Holistic Evaluation

- 原文：[Research Update: Algorithmic vs. Holistic Evaluation](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons/)
- 作者/机构：David Rein / METR
- 日期：2025-08-13
- 研究对象：早期 2025 Agent 在两个成熟开源仓库中完成真实任务后的 PR 质量

### 一句话摘要

**来源结论：** 自动测试能够确认部分核心功能，却严重低估了产物距离“可直接合并”还有多远；因此评估不能只有一个可执行分数，还要覆盖测试充分性、文档、格式规范和可维护性等整体质量。

### 实验怎么做的

- 从两个成熟开源仓库抽取 18 个真实问题：15 个来自约 800 万行代码的 `stdlib-js`，3 个来自约 10 万行代码的 `hypothesis`。
- 原维护者完成这些任务平均需要约 1.3 小时。
- 使用 Claude 3.7 Sonnet 和基础 ReAct 脚手架生成 PR。
- 第一层评估：运行原维护者编写的测试。
- 第二层评估：人工判断 PR 能否无需大量额外工作便直接合并。
- 人工评估五类失败：核心功能、测试覆盖、文档、格式/类型、其他代码质量。

### 关键结果导读式翻译

- 按维护者测试计算，Agent 的平均成功率为 **38%（95% 置信区间 ±19%）**。
- 人工审查的 15 个 PR 中，**没有一个可以原样合并**。
- 让这些 PR 达到可合并状态，估计平均还需 **42 分钟**人工修复。
- 即使只看已经通过测试的 PR，平均仍需 **26 分钟**修复；这相当于原任务平均人工完成时间的大约三分之一。
- 在 4 个通过测试的 PR 中，测试覆盖不足出现于 100%，文档问题与格式/类型问题各为 75%，其他代码质量问题为 50%，核心功能问题仍有 25%。
- 是否通过自动测试，与这些非功能失败没有显示出明显关系；不过样本很小，不能把比例当成普遍规律。

### 它真正说明了什么

自动测试回答的是一个窄问题：“这个实现是否满足这些已写出的测试？”工程团队真正需要回答的是另一个问题：“这个产物是否满足进入下一环节的全部条件？”

二者之间存在评估缺口。缺口包括没有充分测试、没有项目要求的文档、格式或类型不合规、实现冗余脆弱、难读难维护。一个产物可以在局部判定上成功，却把大量成本转移给下游审查者。

### 与本期研究的关系

**直接支持：**

- 工作流产物不能只用单一自动判定评估。
- 每个输出进入下游前，需要同时保留确定性检查和整体质量判断。
- “通过测试”不等于“可交接”，输入—输出之间必须显式定义转换完成条件。
- 评估规则本身存在漏判，需要根据下游修复和返工证据不断进化。

**没有直接证明：**

- 研究只评估代码 PR，没有覆盖需求、架构、测试计划等所有工作产物。
- 它比较的是自动评估与一次人工整体评估，没有研究跨轮次趋势，也没有证明“双环”优于其他流程。
- 人工修复时间是研究者估计，不是原维护者的实际测量。

**AI 关联推断：** 对我们的工作流而言，下游返工不是单纯执行失败，而是上游评估规则的训练信号。进化环应记录“哪个判定放过了这个缺陷”，再修改对应产物的评估标准；否则整体评审只会成为更昂贵的末端兜底。

### 重要边界

- 只有两个成熟且质量要求很高的开源仓库，未必代表所有团队。
- 任务经过筛选，原 PR 都包含较高质量测试，可能比一般需求更明确。
- 使用的是较基础的 Agent 脚手架，结果不是能力上限。
- 样本只有 18 个任务，人工整体审查只有 15 个 PR。
- 未来 Agent 可能采用不同于当前人类工程规范的产物形态；现有“可合并”标准也可能继续演化。

### 深读时最值得看的部分

- TL;DR 与 Methodology：两种评估口径怎样定义。
- Evaluation：五类人工失败判定。
- Results：38% 自动成功率与“无一可直接合并”的落差。
- Understanding the gap：通过测试的 PR 仍缺什么。
- Caveats：这组证据不能外推到哪里。

## 两份材料放在一起看

### 来源共同指向

1. Agent 首先压低的是实现成本，而非端到端交付成本。
2. 评估正在从末端验收变成组织工作流的核心控制机制。
3. 自动化判定只能覆盖产物质量的一部分，可信评估本身是高成本工程。
4. 规格、评估集、上下文和脚手架都必须作为正式产物维护。
5. 高速生成会把理解、审查和修复成本推向下游。

### 两份材料留下的空白

- 如何为需求、架构、计划、代码、测试、评审等不同产物定义共同又不过载的最小评估协议？
- 如何区分真实质量趋势与评估噪声？
- 哪些下游结果应回写为评估规则的进化证据？
- 如何证明规则越来越好，而不是越来越多？
- 如何把进化机制放进每个环节，而不是只放在部署后的维护阶段？

这些空白正是本期“执行环 + 进化环 + 产物评估”假设需要继续验证的部分。

## 材料 5：Real-Time Detection and Repair of LLM Agent Failures

- 原文：[Real-Time Detection and Repair of LLM Agent Failures](https://arxiv.org/abs/2608.02464)
- 作者：Sunny Dubey
- 日期：2026-08-03
- 状态：非常新的预印本，尚不能按成熟同行评审结论对待
- 研究对象：运行中的工具型 Agent 轨迹；重点是任务中途发现错误并触发修复，不是软件开发工作流全生命周期

### 一句话摘要

**来源结论：** Agent 的部分失败可以在执行过程中，通过低成本的轨迹趋势监控、确定性结果校验和完成度检查及时发现；发现后回滚并告知“哪个检查失败”，能显著提高任务成功率。但对于“输出看起来完全合理、实际值却错了”的静默错误，运行轨迹本身没有足够信息，必须引入外部参照。

### 它在解决什么问题

Agent 会在任务中途进入循环、连续遭遇工具错误、偏离目标、编造结果，或者静默吸收被污染的内容。常见做法是让另一个 LLM 逐步评审，但评审成本可能高于执行 Agent 本身，而且 LLM 裁判也不是稳定的测量仪器。

论文提出的问题是：能否仅依靠每一步可观察到的遥测——输出内容特征、token 不确定性、工具调用与返回、延迟和结果长度等——用微秒级监控器在最终失败前发出警报？

### 方法结构

论文实际形成了四层，而不是一种万能检测器：

1. **确定性检查**：重新计算 Agent 声称的总数、检查任务要求的调用是否全部发生、检查工具返回是否符合可能的数据结构。
2. **完成度检查**：识别空输出或停留在裸工具调用等“静默中止”。
3. **时序异常监控**：只用健康轨迹训练正常基线，持续观察每一步行为变化；用 CUSUM 累积小而持续的偏移，在错误扩散前报警。
4. **升级与修复**：确定性检查覆盖不了的情况升级给更昂贵的裁判或外部参照；已标记的轨迹回滚到检查点后重新执行。

### 实验范围

- 共使用 2,823 条已提交的 Agent 运行轨迹，覆盖 25 个数据集。
- 其中 770 条运行使用真实工具，涉及自定义循环、LangGraph 和 AutoGen。
- 模型包括 Qwen2.5 7B/3B、Llama 3.1 8B 与 Gemini 2.5 Flash。
- 同时使用带已知故障起点的受控注入实验，以及没有人工注入错误的自然失败实验。
- 论文测试了循环、工具级联、目标漂移、内容污染等故障，但作者明确说明它们只是 Agent 故障空间的一部分。

### 关键结果导读

#### 1. 单靠行为趋势监控并不可靠

- 在合并实验中，时序监控在 5% 误报预算下检测约 71% 的失败，AUROC 为 0.872。
- 但监控器不能直接跨部署复用：从一个模型或配置迁移到另一个部署时接近随机，必须用新部署的健康轨迹重新校准。
- 在自然产生的失败中，行为监控只捕获 3 次编造中的 1 次；整体排序甚至处于随机水平附近。
- 即使按相同温度重新建立健康基线，健康任务的误报率仍达到 36%，不能作为可部署证据。

这说明“观察轨迹是否异常”可以成为辅助传感器，但不能成为系统正确性的唯一断言。

#### 2. 与故障机制匹配的简单断言更有效

- 一个很简单的完成度检查捕获了 7/7 次静默中止，并且没有误报。
- 确定性校验重新计算 Agent 声称的数字、确认必要工具是否真的调用：在相同任务上捕获 60% 的失败，加入调用覆盖检查后达到 96%，而健康任务中为 0/63 误报。
- 在后续独立种子的 120 条轨迹中冻结规则后复验，数字一致性检查捕获 54%，加入覆盖检查后捕获 93%，健康任务仍为 0/64 误报。
- 工具契约检查能在异常工具结果出现后一个步骤内触发大部分警报。

关键不是“检测器越智能越好”，而是断言必须贴着故障机制：遗漏用完成度断言，数字编造用可追溯重算，工具污染用工具返回契约。

#### 3. 失败信号必须闭合到修复动作

- 论文在错误被标记后回滚，并重新运行任务。
- 只重新采样恢复 16% 的失败。
- 只告诉 Agent“哪个检查失败”，不提供具体错误值，恢复率达到 45%，并通过多重比较后的显著性门槛。
- 在 120 条轨迹上，整体成功率从 52% 提高到 73%，且没有破坏原本正确的运行。
- 直接把正确答案或计算值交给 Agent 并没有带来更好结果；可定位的失败信号比代替 Agent 解题更有效。

这为“执行环”提供了一个具体闭环：断言失败 → 定位检查 → 回滚 → 重试或升级。

### 最关键的负结果

论文明确指出：**一个数值即使错误，只要它看起来合理、格式正常，便无法仅靠轨迹遥测判断。它需要外部参照。**

这意味着：

- “行为看起来正常”不等于任务正确。
- “与历史健康轨迹相似”也不等于任务正确。
- 系统可断言性的核心，不只是增加监控，而是为每类主张建立能够独立验证它的参照关系。
- 如果外部世界的真实状态、用户实际意图或下游业务结果没有进入观测面，智能体仍可顺利完成一个错误任务。

### 与本期研究的关系

**直接支持：**

- 快速失败可以作为运行时基础设施，而不必等到任务结束后人工复盘。
- 相比笼统地再加一个 LLM 裁判，贴近具体故障机制的确定性断言成本更低、误报更少。
- 断言失败应直接连到回滚、重试、停止或升级，否则检测本身没有价值。
- CUSUM 对跨步骤微小偏移的累积检测，与我们提出的“微分/趋势反馈”存在直接机制联系。

**没有直接证明：**

- 论文没有解决需求、设计、代码、测试和发布等所有工作产物的系统断言。
- 它主要判断运行轨迹是否偏离健康分布，无法证明任务是否实现了真实业务目标。
- 它没有让断言规则自动进化；确定性规则来自研究者检查既有失败后编写。
- 它没有证明“自动进化必须以快速失败为前提”。

**AI 关联推断：** 智能体系统可断言性可能不能依赖一种统一裁判，而应采用“故障类型—参照物—断言—恢复动作”的组合。执行环负责实时运行这些断言；进化环则从新出现的静默失败中识别缺失的参照物，增加或修改断言。

### 对我们的模式形成的修正

原来的想法偏向“观察所有产物质量的变化趋势”。这篇材料提示需要分成两类：

1. **已知且可形式化的错误**：优先写成确定性系统断言，直接失败；不要依赖统计趋势或 LLM 裁判。
2. **未知或暂不可形式化的错误**：用轨迹趋势和下游结果寻找异常，但必须控制误报，并把新静默失败送入进化环，尝试转化为下一版确定性断言。

因此，微分不是系统断言的全部。它更适合发现尚未被规则覆盖的变化和漂移；确定性契约才负责对已知错误快速失败。

### 阅读时只需要盯住的三个问题

1. 你是否同意“每类失败必须匹配自己的断言机制”，而不是追求统一的智能裁判？
2. “合理但错误必须依赖外部参照”是否正是你所说的系统控制难点？
3. 在你的工作流里，第一个应该被做成系统断言的静默失败是什么？
