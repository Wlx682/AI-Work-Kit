# 研究立项

## 主问题

AI Agent 大幅提高实现和迭代速度后，中型团队应如何改造工作流，使智能体系统像代码一样可以轻松断言，让“局部检查全绿、任务顺利完成、整体结果却是错的”这类静默失败在影响扩大前自动暴露？

### 问题演化

- 不变的研究方向：AI Agent 进入中型团队遗留代码改造后，端到端工作流应如何改造。
- 初始症状入口：编码提效为何常转化为新的审查瓶颈和回归排查负担。
- 当前机制假设：需求在迭代中涌现时，可否借鉴 PID 的“微分项”设计反馈，抑制传递误差震荡。
- 当前核心问题：怎样让智能体系统获得类似代码的可断言性；PID、全环节产物评估和执行环—进化环都是服务于这个目标的候选机制。

## 为什么现在值得研究

AI Agent 已显著提高实现和迭代速度，但团队的需求沟通、产物评估、审查与反馈机制仍按较低频率设计。工作流若不能同步进化，局部提效会更快地放大传递误差、返工和回归排查负担。

## 目标读者与他们当前的困境

负责评估、引入和治理 AI Agent 的技术负责人。他们需要判断：局部编码速度的提升，是否真的能转化为团队交付吞吐；以及如何避免新增代码产量压垮有限的审查能力。

## 暂定假设

- 用户修正：需求意图稳定本身就是伪命题；如果等一切明确再开始，就已经晚了，而且很多需求只能通过测试或迭代逐步形成。
- 用户观察：AI Agent 大幅提高迭代效率后，传递误差不再只是单次偏差，而会以增量方式积累并产生大幅震荡；因此迭代过程本身需要重新设计。
- 用户提出的工作流设计机制：把协作工作流看作类似 PID 的自适应系统，重点研究其中的“微分”。
- 用户范围确认：“微分机制”覆盖工作流所有环节，而不是只设置在需求、审查或测试中的某一个节点。
- 用户关键判断：所有工作环节的输入产物与输出产物都必须被评估；产物评估是工作流改造的关键。
- 用户关键判断：产物的评估判定不可能一次完善，需要在真实执行中一点点迭代；因此“进化”本身也是工作流的主要模块。
- 用户关键判断：代码断言没有失效；智能体已经不会再生产触发既有断言失败的代码。真正缺失的是智能体系统级错误的快速反馈：任务可以顺利完成、代码断言全部通过，但实际结果是错的，而且没有人知道。必须优先建立“让智能体系统快速出错”的能力，否则自动进化没有反馈基础。
- 用户确认的研究目标：让智能体系统变得像代码一样可以轻松断言。这不是当前已有答案，而是本期工作流改造要解决的核心问题。
- 用户架构判断：现阶段制定规则不是最重要的，首要问题是以什么形式监控智能体系统。Linux 只能用于说明“架构先于规则细节”，不能作为系统目标的直接类比。
- 用户补充：控制内核架构必须直接体现进化模块；只有观测、拦截和回滚而不能演化的内核仍然不完整。
- 用户对核心矛盾的修正：Linux 面向确定性计算，智能体系统则围绕强大的 LLM 展开，目标是发挥并管理其不确定性；二者的核心问题不同，不能硬套 Linux。
- AI 结构化推断（待确认）：研究对象需要从“系统断言规则”上移到“管理不确定性的可进化运行架构”。它不追求把 LLM 的每一步变成确定程序，而是在保留探索、生成和适应能力的同时，让不确定性的表现可观测、后果有边界、失败可恢复、经验可进入进化回路。
- 用户判断：以前的代码需要工程化，现在的智能体需要精确的系统控制。
- AI 结构化推断（待验证）：Agent 提高了系统增益和迭代频率；如果反馈仍滞后，误差变化会在多轮传递中被放大。所谓“微分机制”应关注误差的变化速度或趋势，在大规模回归之前提前阻尼，而不是等待需求先稳定。
- AI 结构化解释（待验证）：这是一种以产物为观测面的分布式反馈原则。每个环节评估收到的输入产物和交付的输出产物；跨环节、跨轮次比较评估结果，识别误差是在收敛还是扩大。微分项观测的不是抽象沟通状态，而是产物质量及输入—输出转换偏差的变化趋势。
- 用户已确认的结构化假设：工作流包含两个相互嵌套的反馈环。执行环用现有判定评估每个输入、输出产物并调节当前工作；进化环根据误判、漏判、返工和回归证据，持续修改“评什么、怎样判、何时阻尼”。评估规则本身也是一种需要被评估和迭代的工作产物。
- 提醒：PID 是服务于工作流改造的研究类比和待验证机制，不是研究方向本身，也不是已经成立的事实模型。

## 什么证据会推翻或缩小它

- 如果只有某个单点环节需要趋势反馈，其他环节的局部反馈不能降低端到端震荡，则“覆盖所有环节”的范围需要缩小。
- 如果偏差的变化趋势不能比偏差绝对值更早预测返工或回归风险，则“微分机制”假设需要弱化或推翻。
- 如果对输入、输出产物的评估无法定位误差从哪个转换环节产生，或者不能减少下游返工与排查负担，则“产物评估是关键观测面”的假设需要缩小。
- 如果评估规则的迭代不能提高其预测返工、回归风险的能力，或规则增长带来的流程负担超过减少的返工，则“进化是主要模块”的实现方式需要调整。

## 本期不研究

- 绿地项目中的 AI Agent 开发
- 个人开发者的编码效率或使用技巧
- 单纯的模型能力排行
- 脱离中型团队协作和遗留代码改造场景的泛化结论

## 时间盒与停止条件

### 用户已确认

- 首批只研究 5 份核心材料，并由用户至少实质批注其中 2 份。
- 至少找到 1 个支持“双环工作流”的真实案例，以及 1 个反例或失败案例。
- 能画出一条端到端链路，说明各环节的输入产物、输出产物、评估结果以及评估规则如何进化。
- 新材料连续两次不再改变该链路或核心假设时，停止扩展本期资料。
