1. **编码提效制造了新的系统盲区**：Agent 能更快地产生通过既有代码断言的实现，但“局部全绿”不等于系统目标已实现；发现整体错误反而变得更昂贵。

3. **核心矛盾不是确定性，而是不确定性的利用与治理**：架构不能把 LLM 压缩成确定程序，而要让其不确定性可观测、后果有边界、失败可恢复、经验可进化。
4. **工作流需要生成、证据控制和进化形成闭环**：生成端保留探索；证据与控制端管理副作用和完成声明；进化端根据真实成败修改下一轮系统。
5. **最强反方：进化会制造更危险的自修改系统**：如果进化可以直接改变评估器和控制策略，系统可能优化错误代理指标，把审查瓶颈转移到进化机制。
6. **AI 提出的回应（待用户检验）**：进化模块不能位于控制之外。每次进化都应成为可观察、可比较、可回放、可版本化和可回滚的工作产物；目标不是证明每次变化必然正确，而是限制错误进化的影响范围并积累下一轮证据。换言之，进化本身也必须可断言。
7. **对技术负责人的含义**：工作流改造的优先级应从“补更多规则”转向“先建立能够承载不确定性、快速失败和受控进化的系统架构”。

## 草稿

### 智能体系统需要的不是更多规则，而是一套管理不确定性的可进化架构

AI Agent 进入中型团队以后，最容易被看到的变化是编码速度，最容易被抱怨的新问题则是审查跟不上。于是许多改造方案自然地指向更多规范、更完整的需求、更细的验收标准和更多自动检查。

这些做法没有错，但它们还停留在问题表面。

真正发生的变化不是“代码生产得太快”，而是整个工作系统的反馈结构已经与 Agent 的执行速度失配。过去一个偏差可能在一次开发周期里缓慢传递；现在 Agent 可以连续生成、修改和交付多个产物，同一个传递误差会以增量方式快速累积。等人类在末端审查或回归阶段发现问题时，任务已经顺利完成了很多次。

这才是新的审查瓶颈：不是人审得不够快，而是系统没有在错误影响最小时让它暴露。

#### 代码断言没有失效，错误迁移了

代码断言仍然有效。它能把一个已经被表达出来的不变量变成即时失败：输入不合法、状态不可能、返回值越界，程序立刻停下，问题在距离起点很近的地方暴露。

但成熟的编码 Agent 越来越擅长生成不会触发这些既有断言的代码。它可以通过编译、单元测试、静态检查和代码规范，甚至完整执行任务流程。与此同时，任务仍然可能是错的：理解了错误的目标，采用了错误的代理指标，遗漏了未被写进测试的约束，或者让某个局部正确的产物破坏了下游系统。

因此，不能说代码断言失效了。更准确的说法是：错误从代码能够观察的失败空间，迁移到了智能体系统层。

系统层错误最危险的特征不是“失败”，而是没有失败。所有局部信号都是绿色，Agent 宣布任务完成，工作流继续向下游传递，直到回归、上线或真实使用才发现整体目标并未实现。发现错误于是从一次低成本的即时反馈，变成跨产物、跨环节、跨轮次的昂贵排查。

如果智能体系统不能把这种静默错误转化为快速、低成本、可定位的失败信号，所谓自动进化就没有可靠输入。系统只会更快地重复自己没有意识到的错误。

#### 已知规则可以执行，但开放任务不能被规则穷举

[AgentSpec](https://arxiv.org/abs/2503.18666) 给出了一个重要方向：把 Agent 约束表达为触发器、谓词和强制动作，在运行时检查并干预。它说明智能体规则不必只存在于提示词和文档里，也可以成为可执行的系统基础设施。

[Real-Time Detection and Repair of LLM Agent Failures](https://arxiv.org/abs/2608.02464) 则进一步展示了逐步遥测、完成度检查、确定性重算、工具契约、升级和回滚如何在任务完成前发现部分失败。它同样暴露了边界：行为异常监控必须随具体部署重新校准；当一个错误结果在形式上完全合理时，仅凭运行轨迹并不能知道它是错的，系统仍然需要外部参照。

两份材料放在一起，得到的结论不是“我们应该编写更多规则”，而是更严格的一层判断：

> 静态规则能够控制已经认识到的风险，却不能穷举强大 LLM 在开放任务中产生的不确定性。

规则仍然重要，但规则不是系统的核心。核心是承载规则、观测未知失败、限制影响范围，并根据真实结果改变下一轮系统的架构。

#### 不要把 Linux 的核心矛盾硬套给智能体

构建智能体系统时可以借用 Linux 的一个启发：架构先于具体规则。一个长期系统不能依靠不断堆叠零散约束维持秩序。

但类比到这里就应该停止。

Linux 的主要任务是可靠地发挥确定性计算；智能体系统的价值则来自强大 LLM 的不确定性。它能够探索多个方向、补全未明确表达的意图、在陌生环境中生成方案，并根据上下文改变路径。如果控制系统试图把每一步都变成确定行为，它同时也消灭了使用 LLM 的理由。

所以，智能体架构的核心矛盾不是“怎样消除不确定性”，而是“怎样发挥并管理不确定性”。精确控制也不等于精确指定每一步，而是让不确定性具备四个系统性质：

- 可观测：系统知道 Agent 基于什么输入、经过什么轨迹、产生了什么产物和完成声明。
- 后果有边界：不确定的探索可以发生，但资源消耗、外部副作用和错误传播范围受到限制。
- 失败可恢复：发现异常后可以隔离、回退、换路或升级，而不是只能接受整个任务的最终结果。
- 经验可进化：静默失败、误报、漏报和真实成效能够改变下一版提示、技能、评估器、工作流和控制策略。

这四个性质不是四条规则，而是系统架构必须持续提供的能力。

#### 一个围绕 LLM 而不是围绕规则设计的闭环

从这一核心矛盾出发，智能体工作流至少需要三类协同能力。

第一类是生成与探索。LLM 应被允许产生候选方案、分支轨迹和新的解决路径。这个部分负责发挥不确定性的价值，而不是为了可审查性被压缩成固定流水线。

第二类是证据与控制。系统持续记录任务意图、上下文来源、工具调用、输入输出产物、关键决策和真实结果；同时控制预算、副作用、检查点、隔离和恢复。这里要断言的不是“Agent 每一步是否与预定答案相同”，而是它是否仍处于允许探索的边界内，以及它是否有足够证据宣布任务完成。

第三类是进化。系统消费运行轨迹、静默失败、误报、漏报、返工与下游结果，提出对提示、技能、评估器、工作流和控制策略的候选修改。每个环节的输入和输出产物都是观测面；跨环节、跨轮次的变化趋势，则可以帮助系统在误差大规模扩散前提前阻尼。

这里可以有限地借用 PID 的“微分”直觉：系统不能只问当前误差有多大，还要观察误差是在收敛还是加速扩大。但 PID 不是架构本身。没有可信的系统误差信号，再漂亮的控制算法也只是在放大噪声。

#### 最危险的不是 Agent 自主，而是进化不受控制

这套主张最强的反对意见是：如果系统能够持续修改提示、技能、评估器和控制策略，它就变成了一个比静态 Agent 更难审查的自修改系统。

这个反对意见成立，而且不能靠“设置人工审批”轻轻带过。因为进化机制可能优化错误的代理指标，把偶然反馈当作规律，让评估器与 Agent 共同漂移，甚至把原来的审查瓶颈转移成一套更隐蔽的控制系统审查。

但这并不推翻进化模块，反而给出了它必须遵守的架构边界：

> 进化不能位于控制系统之外。进化本身也必须可断言。

一次进化不应是系统直接改写自己，而应先成为一个明确的候选产物：它改变了什么，依据哪些运行证据，预期改善哪个失败模式，又可能损害哪些能力。候选变化需要能够在历史轨迹上回放、在影子环境中比较、以版本方式发布，并在产生有害结果时回滚。

这里的目标仍然不是证明每次进化必然正确。对于开放系统，这种保证并不存在。目标是让错误进化也能快速暴露、影响有限、可以恢复，并为下一次修改留下证据。

换句话说，可进化不等于可以自由自改。真正的自动进化，是把“改变系统”本身纳入与其他工作产物相同的观测、评估和反馈闭环。

#### 技术负责人真正需要先建设什么

对于正在用 Agent 改造遗留代码的中型团队，第一优先级不应是一次性写完全部规则，也不是等待需求意图稳定后再启动自动化。需求只能在测试、反馈和迭代中逐步涌现，等待完全明确意味着永远不会开始。

技术负责人更应该先回答这些架构问题：系统能否知道 Agent 为什么宣布完成；关键输入输出产物能否留下可比较的证据；不确定探索的副作用能否被隔离；发现整体错误后能否回到最近的有效状态；一次失败能否真正改变下一轮工作流；而进化模块自己的改变，能否被观察、验证、版本化和回滚。

具体断言会一点点完善，评估标准也会持续变化。重要的不是第一天就写对全部规则，而是系统从第一天起就具备增加、纠正和淘汰规则的结构。

以前的代码需要工程化，现在的智能体需要精确的系统控制。但这种“精确”不是把 LLM 变成确定程序，而是精确管理它的不确定性：让探索继续发生，让错误尽早显形，让影响停在局部，让每一次真实成败都成为系统进化的输入。

当智能体系统可以像代码一样轻松断言时，我们追求的并不是它永远不犯错。真正的目标是：它即使犯错，也无法悄无声息地完成。
