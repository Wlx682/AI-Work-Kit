# 中文研究包：智能体控制面 MVP

> 这是五份材料的中文翻译式总结，不是全文逐字翻译。正文已经包含形成判断所需的问题、机制、证据和边界；原文链接只放在各节末尾供按需核验。

## 先看结论地图

五份材料其实不在争夺同一个“总架构”，而是在解决五个不同边界：

| 材料 | 真正解决的边界 | 对应系统对象 | 明确不能证明的事 |
|---|---|---|---|
| Ledger | Agent 是否知道当前执行到了哪里 | `ExecutionLedger` | 任务目标是否真的完成 |
| Tax AI | 真实失败如何变成下一轮改进 | `OutcomeRecord`、`EvolutionCandidate` | 一次差异是否就是系统错误 |
| CXI | 一个提议何时有权变成外部副作用 | `ActionManifest`、`ExecutionLease` | 被授权的动作在业务上是否正确 |
| LangGraph Interrupts | 长流程如何暂停并恢复计算状态 | `RecoveryCheckpoint` | 外部世界能否自动回滚 |
| Monitorability | 如何从 Agent 的过程信号中提前发现异常 | `MonitorSignal` | 轨迹或推理是否等于事实真相 |

它们共同留下一个尚未被实现的空位：**谁把任务契约、当前执行状态、行动记录、测试证据、外部结果和未知项汇总起来，决定 Agent 能否宣布完成？** 这正是本期要设计的 `CompletionDecision`。

## 材料一：把交互历史变成执行状态——面向长时编码 Agent 的 Ledger 运行时

- 来源角色：2026 年 8 月论文；软件工程运行时机制。
- 它要解决的问题：长时编码 Agent 的上下文记录了“发生过什么”，却没有持续表达“哪些事实现在仍有效”。

### 中文总结

编码 Agent 会反复读取文件、修改代码、运行测试。普通对话历史只是把这些动作按时间堆在一起：Agent 曾经读过某段代码，但后来文件可能已经被改过；某个测试曾经失败，但代码改变后旧结果已经失效；某条搜索命令可能刚执行过，也可能是在完全不同的代码状态下执行的。

论文认为，缩短或总结上下文只能减少阅读量，不能解决“旧事实是否仍然有效”这个问题。因此它在 Agent 外增加一个确定性的 `Ledger`，只保存可以从工具执行中机械推导的状态，不试图理解模型的隐含思路。

Ledger 包含三类记录：

1. **观察记录**：只有真正成功返回、未截断的文件内容才算已观察；记录完整文件或具体行范围。
2. **修改状态**：为文件和仓库维护变化计数，用来判断旧观察是仍然有效，还是可能已经过期。
3. **命令记录**：把命令规范化并分类为读取、搜索、测试、修改等，从而区分“修改后重新验证”和“状态没变却重复执行”。

这份状态在两个位置生效：

- `inform`：Agent 决策前，把当前关注文件、已观察范围及其新鲜度放到上下文末尾；它只是告知，不限制行动。
- `govern`：命令执行前给出 `Allow / Reuse / Nudge`。确定不会变化的重复读取可以直接复用旧结果；可能陷入循环的操作会被提醒；仍可能有意义的测试或探索继续允许执行。

关键点是：运行时不让模型自己从几百步历史中猜测当前状态，但语义判断仍留给模型。Ledger 明确不判断修复策略是否正确。

### 关键证据

论文在 500 个 SWE-bench Verified 任务上报告：

- GPT-5 mini 的 Pass@1 从 56.2% 提升到 64.2%；
- MiniMax M2.5 从 75.8% 提升到 81.0%；
- 总成本分别下降 28.9% 和 31.8%；
- 接到 Codex 后，Pass@1 从 74.8% 提升到 78.2%，总成本下降 24.4%；
- 消融实验显示，`govern` 对成功率贡献更大，`inform` 对减少调用和输入 token 的贡献更大。

这些结果支持“显式执行状态比单纯压缩历史更有效”，但不能推出“Ledger 能证明业务完成”。

### 局限与反方

- 每个任务只运行一次，没有测量多次运行方差。
- 基准主要是 Python 仓库中的 issue 修复，不能直接外推到大型多语言遗留系统。
- govern 使用人工设定的固定规则和阈值，只能识别已描述的重复模式。
- 不支持的命令、解析失败和内部策略错误默认放行，说明其目标是减少干扰，不是安全上的 fail-closed 门禁。
- 它只维护“已观察、已修改、已尝试”，没有覆盖需求、影响范围、验收证据和真实业务结果。

### 对控制面 MVP 的影响（AI 推断）

原先笼统的 `Evidence` 应拆开：

- `ExecutionLedger` 是持续更新的当前状态，用于下一步决策；
- `EvidencePacket` 是提交完成申请时冻结的证据快照，用于审计和完成判断。

此外，遗留代码任务可能还要补充 `verified / invalidated / affected`：哪些行为已验证、哪些证据因变更失效、哪些下游面受到影响。

### 需要你判断

1. 你遇到的 Agent 静默失败，主要来自“不知道当前状态”，还是“知道状态但理解错目标”？
2. `observed / modified / attempted` 之外，`verified / invalidated / affected` 是否是遗留代码任务的必要状态？
3. 你是否接受：执行状态必须由确定性运行时维护，不能继续只存在于 Agent 上下文里？

原文核验入口：[论文摘要与全文](https://arxiv.org/abs/2608.00808)，重点为第 3 节 Ledger、实验结果和 Limitations。

## 材料二：用 Codex 构建可自我改进的税务 Agent

- 来源角色：OpenAI 与 Thrive Holdings 的生产案例，2026 年 5 月。
- 它要解决的问题：生产中的专家修正很多，但怎样把这些修正变成可靠的改进信号，而不是一堆无法归因的反馈。

### 中文总结

Tax AI 从客户材料中抽取税务字段并生成待审核申报数据。真正困难的不是“让 Agent 输出一个结果”，而是解释结果为何被会计师修改：一次字段差异可能是抽取遗漏，也可能是映射错误、产品暂不支持、会计师偏好、上一年度数据沿用，或者正常流程噪声。

因此系统没有把“人工改了值”直接当成 Agent 犯错，而是建设了三段闭环：

1. **让专家参与定义错误**：实际做税务工作的会计师判断哪些差异真正重要。
2. **让生产主动制造证据**：不仅保存输入和最终输出，还保存源文档、字段引用、抽取值、税务引擎映射、专家修改以及最终提交值。
3. **把经归因的模式变成改进任务**：先记录预测值与最终值的字段级差异，再把相似差异聚类，区分重复故障和正常噪声；只有经过复核、重复出现且能写出成功条件的 finding，才转成定向 eval 和有边界的 Codex 工程任务。

Codex 接到的不是一句“这个字段做错了”，而是一组可调查环境：生产 trace、代表性源材料、预期结果、相关代码、技能说明、定向 eval 和回归 eval。它可以调查根因、提出修改、跑验证并形成候选 PR；模糊或不能安全自动化的情况回到产品和工程团队。

这里的“自我改进”并不是 Agent 在线修改自己，而是：**生产形成结构化证据，证据形成经过治理的改进候选，候选再通过正常工程验证进入系统。**

### 关键证据

案例报告覆盖参与试点的 30 多家会计事务所和 7,000 份税表。文中报告：

- 税务准备时间节省约三分之一；
- 草拟税表最高达到 97% 准确率；
- 吞吐提高约 50%；
- 达到 75% 字段完成正确率的税表比例，从上线时约 25% 提升到六周后的 86%。

这些数字证明该闭环在一个真实、高结构化、专家强参与的领域可运行。但它们来自项目方自己的案例总结，不能当作独立对照实验，也不能直接证明相同方法能在开放式遗留代码任务中取得同等效果。

### 局限与反方

- 税务字段有较清晰的源材料、字段映射、最终申报值和专家裁决，天然比“这次架构改造是否真正满足意图”更容易建立真值。
- 专家修正并不自动等于模型错误，说明反馈必须经过归因；这会引入持续的人力治理成本。
- 文章没有证明全自动自我改进，工程师仍负责架构、产品判断、验证和发布。
- 多次出现才进入 finding 能减少过拟合，但也可能让低频高危问题被延迟处理，因此仍需风险优先级通道。

### 对控制面 MVP 的影响（AI 推断）

`EvolutionCandidate` 至少应包含：失败证据、归因、重复性或风险等级、影响面、候选成功条件、定向 eval、回归集合和责任人。它不能从一次异常自动生成线上规则。

遗留代码场景对应的生产证据可能包括：需求验收失败、人工返工、回归缺陷、线上告警、用户行为变化、回滚和代码进入下游后的兼容性问题。只有代码测试结果是不够的。

### 需要你判断

1. 在你的开发工作流里，哪一种结果最接近 Tax AI 的“最终申报值”，能作为任务真实成败的外部参照？
2. 一次失败什么时候足以进入进化环：重复出现才算，还是高风险单例也应进入？
3. 你是否接受当前边界：Agent 可以调查和提出改进，但架构判断、产品判断与上线仍由人负责？

原文核验入口：[OpenAI 生产案例](https://openai.com/index/building-self-improving-tax-agents-with-codex/)，重点为三段闭环、租赁房产示例和 “How to use Codex to build this loop”。

## 材料三：从上下文到执行的完整性——不要让“证据”洗成“权限”

- 来源角色：2026 年 7 月安全论文，单作者预印本。
- 它要解决的问题：Agent 必须读取 issue、README、日志、网页和工具结果，但这些可被攻击者影响的内容，不应该因为进入模型上下文就获得执行高权限动作的资格。

### 中文总结

论文把核心故障称为“权限洗白”：某段文本本来只是证据，却在同一个模型上下文里悄悄决定了用哪个工具、操作哪个目标、是否已经批准、是否重试，最终变成真实副作用。

例如，CI 日志可以告诉 Agent 哪个文件失败，却不应有权选择生产数据库工具、把审批状态改成已批准，或扩大重试次数。JSON Schema 只能证明字段格式正确，无法证明字段值有权控制这个动作。

CXI 因此把模型输出降级为“动作提议”，在真正执行前通过确定性边界完成六步检查：

1. 把候选动作规范化成唯一 `ActionManifest`；
2. 检查每个受保护字段的来源与字段级权限；
3. 检查执行载荷会产生的精确副作用；
4. 校验一次性的调用能力是否绑定同一 manifest；
5. 消耗该能力并签发 `ExecutionLease`；
6. 只允许通过受控 sink 执行。

它区分几类数据：

- `Trusted state`：用户目标、策略、工具注册表、可信审批；
- `Writable context`：issue、日志、网页等可被影响的输入；
- `Typed release`：经可信验证器提取后，只允许流入某一个特定字段的窄值；
- `Opaque data`：可以被引用和保留，但没有当前执行边界的权限；
- `Protected field`：决定工具、操作、目标、审批、重试或其他副作用的字段。

对 patch、SQL、shell、CI 配置这类“内容本身就是动作”的载荷，仅验证字符串或 JSON 不够。CXI 授权的是解析后会发生的精确效果，例如 patch 必须绑定基础 commit、允许路径、旧新 blob、重命名和权限变化；任何验证后的修改、换仓库、换 principal 或换策略版本都会使摘要变化并拒绝执行。

### 关键证据

论文报告的评估覆盖 720 个 AgentDojo episode、1,739 次 LLM 调用，以及 400 个代码仓库 episode。在代码 Agent 精确副作用测试中，记录到 231 次安全任务完成，未观察到字段、效果或调用权限逃逸。

但论文刻意把“安全通过边界”和“任务质量”分开。在 40 个最终状态审计任务中，只有 29 个无需追加审查就满足任务级断言，另有 11 个仍需处理回归测试缺失、安装钩子、证据歧义、审批范围等普通质量问题。

这恰好证明：**动作被正确授权，并不等于任务正确完成。**

### 局限与反方

- 这是单作者预印本，真实生产复现与外部验证仍有限。
- 策略编写、字段分类、验证器和所有副作用入口都属于可信边界；漏标字段、过宽验证器或绕开统一 gate 都会破坏保证。
- 它只保证被允许执行的动作与获批 manifest 一致，不判断该动作是否值得做、修复是否正确。
- hosted API 无法看到供应商内部注意力、缓存和解码过程，只能使用较弱的宿主侧构造证据。
- 精确效果授权要求针对不同 sink 写 adapter 和验证规则，会带来明显工程成本。

### 对控制面 MVP 的影响（AI 推断）

原来的 `ActionIntent` 只是 Agent 的提议，不应直接交给工具。中间至少需要：

- `ActionManifest`：规范化目标、精确预期效果、基础状态、权限主体、策略版本、有效期和幂等键；
- `ExecutionLease`：由运行时签发的一次性执行资格，执行后即消费。

低风险只读动作可以采用简化策略；写代码、发消息、推送分支、修改数据库或部署等有副作用动作，才进入完整 manifest 路径。

### 需要你判断

1. 在编码场景里，授权 `git push` 这个工具是否太粗，是否应授权“向某分支推送某个已验证 commit”？
2. manifest 由 Agent 生成后，谁负责验证它：确定性规则、另一个模型、人，还是按风险分级组合？
3. 这套精确授权应覆盖所有写操作，还是只覆盖跨系统、难回滚和高风险操作？

原文核验入口：[CXI 论文](https://arxiv.org/abs/2607.06000)，重点为第 2–3 节、5.7 Task Quality 和 Appendix I Residual Risks。

## 材料四：LangGraph Interrupts——暂停并恢复，不等于撤销并回滚

- 来源角色：LangGraph 官方运行时文档。
- 它要解决的问题：长流程如何在任意节点暂停，等待人工审批或补充输入，并在进程重启后继续。

### 中文总结

LangGraph 的 `interrupt()` 不是普通 UI 弹窗，而是一种持久运行状态。触发时，运行时保存图状态并停止执行；调用方通过 `thread_id` 找到同一个检查点，再用 `Command(resume=...)` 把审批或补充信息交回流程。

这提供了三个重要能力：

- 暂停可以无限期等待，不必让原进程一直存活；
- 审批、拒绝、编辑状态等外部决定可以作为正式输入进入后续执行；
- 出错或重启后可以从保存的图状态继续，而不是重跑整条任务。

但它有一个容易被忽略的语义：恢复时，包含 `interrupt()` 的节点会从头重新执行，而不是从源代码的中断行继续。因此中断之前发生的副作用必须幂等，或者被拆到独立节点并放到批准之后，否则恢复可能重复创建记录、重复发送请求或覆盖数据。

### 关键证据

官方文档明确要求生产环境使用持久 checkpointer，并列出人工批准、状态编辑、工具调用复核和输入验证模式。文档同时明确：恢复会重新执行节点，中断前的非幂等副作用可能重复发生。

这里的证据属于框架行为说明，不是“采用 LangGraph 后任务更正确”的实验结果。

### 局限与反方

- Checkpoint 保存的是工作流/图的计算状态，不会自动把邮件撤回、把数据库写入还原或把已经推送的 commit 消失。
- 它没有定义什么动作需要人工审批，也没有判断审批人在恢复时看到的基础状态是否已经变化。
- 一个几小时前批准的动作，恢复执行时可能已经失效；批准后、执行前仍需重新验证前置条件。
- 幂等只能防止重复产生额外效果，不能解决第一次错误副作用的撤销。

### 对控制面 MVP 的影响（AI 推断）

`Checkpoint` 应拆成：

- `RecoveryCheckpoint`：Agent 的运行状态和恢复游标；
- `CompensationPlan`：外部副作用失败或撤销时的反向动作、责任人和不可逆声明。

恢复执行前还需要 `ResumePreconditions`：基础 commit、资源版本、审批有效期、策略版本和预算是否仍与暂停时一致。

### 需要你判断

1. 你是否同意“能恢复 Agent”与“能恢复外部世界”必须是两个独立能力？
2. 哪些开发动作必须在执行前具备补偿计划：文件编辑、commit、push、合并、部署、数据迁移？
3. 人工批准后，哪些前置条件必须在真正执行前重新验证？

原文核验入口：[LangGraph Interrupts 官方文档](https://docs.langchain.com/oss/python/langgraph/interrupts)，重点为暂停/恢复机制与 Rules of interrupts。

## 材料五：评估思维链可监控性——“看见过程”仍不是“知道真相”

- 来源角色：OpenAI 研究，2025 年 12 月；本研究包的反方材料。
- 它要解决的问题：当 Agent 的能力超过人工逐步审查时，较弱监控器能否从 Agent 的推理过程和行动中预测欺骗、奖励黑客、偏见等行为。

### 中文总结

研究把“可监控性”定义为：监控器能否根据 Agent 暴露出的信号，预测某个我们关心的行为属性。它不是 Agent 单方面的属性，而同时取决于 Agent 是否留下可理解信号，以及监控器是否有能力提取这些信号。

研究设计了 13 类评估、24 个环境，分为三种思路：

1. **干预型**：人为改变环境，检查监控器能否发现 Agent 为何改变行为；
2. **过程型**：任务只有有限有效路径，检查监控器能否识别实际采用的步骤；
3. **结果属性型**：结果中某种属性可可靠测量，再检查过程信号能否提前预测它。

总体结果是：只看行动和最终回答，明显弱于同时观察推理过程；更长推理通常更容易监控；更强监控器和更多监控计算也会改善表现。研究甚至提出“可监控性税”：在高风险任务中，可能值得牺牲少量能力或增加计算，换取更容易被监控的系统。

但这项工作对我们的提醒比正面结果更重要：监控器输出的是风险预测，不是真值证明。某些行为在个别评估上仍然很难监控；模型、训练方式、推理长度和环境分布变化都可能改变监控效果。

### 关键证据

- 研究覆盖 13 类评估和 24 个环境；
- 多数设置下，观察推理过程比只观察行动与结果更有效，但并非完美；
- 提高 Agent 和监控器的推理计算通常改善可监控性；
- 事后追加针对性问题，有时能暴露第一次过程里未显式表达的信息。

### 局限与反方

- 每个评估只覆盖一种可监控属性，仍有大量行为没有被测试。
- 基准环境可能不够真实，模型也可能识别出自己处于评估中。
- 结果未必能外推到分布外和真实生产故障。
- 可监控性可能随未来训练和规模变化而变脆弱。
- 推理过程不是稳定、通用、必然可访问的系统接口，因此不能成为唯一承重层。

### 对控制面 MVP 的影响（AI 推断）

模型监控适合作为 `MonitorSignal`：发现风险、选择补证、提高人工复核优先级，但不宜直接等同于 `CompletionDecision`。

完成门禁需要纵深证据：确定性状态、工具结果、可复算测试、权限与副作用记录、独立评估、真实结果和模型监控。证据不足时必须允许返回 `unknown`，而不是逼监控器猜一个 pass/fail。

### 需要你判断

1. 证据账本应不应该保存模型推理，还是只保存外部可观察、可复算的事实？
2. 如果推理监控比行动监控更有效但不稳定，它应参与阻断，还是只负责发出风险信号？
3. `unknown` 出现时，默认动作应是补证、降级、人工接管，还是按风险等级选择？

原文核验入口：[OpenAI 研究](https://openai.com/index/evaluating-chain-of-thought-monitorability/)，重点为评估框架、Agent vs. monitor compute 和 Limitations。

## 第二组：控制论与安全架构的一手材料

> 第一组回答“Agent 工程上有哪些可用机制”，第二组回答“为什么这些机制必须形成控制系统，以及控制能力的理论上限在哪里”。以下仍是翻译式总结，不是原文复刻。

### 材料六：Kalman——可观测不等于可控，输入输出也不等于全部内部状态

- 来源角色：R. E. Kalman，1963 年原始论文，现代状态空间控制理论基础之一。
- 它要解决的问题：一个动态系统应怎样用内部状态或输入—输出关系描述；从外部输入输出究竟能识别系统的哪一部分。

#### 中文总结

Kalman 区分了两件经常被混为一谈的事情：

- **可观测性（observability）**：能否由系统输出和已知输入重建与控制有关的内部状态；
- **可控性（controllability）**：是否存在一组允许的输入，能够把系统从当前状态带到目标状态。

论文在**线性系统**范围内说明，输入—输出关系只决定系统中同时可观测且可控的那一部分，并可由此构造最小实现。换到智能体系统：把日志、trace 和结果采得再完整，也不能自动证明隐藏状态可被可靠重建；即使状态完全可见，如果系统没有网关、限权、隔离、降级或恢复通道，也仍然不可控。

#### 关键证据与边界

这是数学结构结果，不是 Agent 生产实验。它严格支持“可观测性与可控性是两个不同属性”，但不能把线性系统的秩条件原样套在具有非线性、适应性和人类参与的智能体系统上。

#### 对本期架构的影响（AI 推断）

控制面必须维护两张分离的表：

1. `ObservabilityAssessment`：哪些控制相关状态可测、可估、不可知，以及何时过期；
2. `ControlAuthorityMatrix`：对每种偏差，系统拥有何种可执行干预、作用范围、时限和失败后备。

任何高风险 Intent 只有在关键状态可观测、目标状态可达、干预能在截止时间前生效时才可放行。

#### 需要你判断

1. 你是否接受把原主张从“监控决定控制品质”收紧为“监控决定认识上限，控制权决定行动上限”？
2. 对智能体系统来说，最常见的问题是不可观测，还是明明看见却没有有效控制通道？

原文核验入口：[SIAM 论文页与摘要](https://doi.org/10.1137/0301010)，重点为 Abstract 与 controllability / observability 的区分。

### 材料七：Ashby——扰动有多少种，控制器就必须拥有足以应对的响应种类

- 来源角色：W. Ross Ashby，1956 年《控制论导论》第 11、13 章。
- 它要解决的问题：控制器为什么无法用极少数固定响应，稳定压缩一个拥有大量扰动类型的系统输出。

#### 中文总结

Ashby 用“必要多样性定律（Law of Requisite Variety）”给出控制的容量约束。若扰动多样性为 `V_D`，控制器可用响应多样性为 `V_R`，则残余结果多样性不能低于二者之差。直观含义不是“控制器越复杂越好”，而是：如果某类扰动没有对应的识别、决策和有效动作，系统不可能仅靠更聪明地排列现有规则消除它。

他进一步指出，调节超大系统的主要困难通常不是部件数量本身，而是必须抵御的扰动种类。工程上可以通过识别约束、利用重复结构、分解系统、分阶段选择和补充调节能力，减少控制器必须同时处理的有效多样性。

#### 关键证据与边界

这是抽象调节理论，不是“每种异常写一条规则”的论证。多样性是控制选择与通信容量，不等同于监控指标数、Agent 数或流程分支数；它是必要条件，不保证控制动作正确、及时或稳定。

#### 对本期架构的影响（AI 推断）

`Capability Inventory` 不能只盘点 Agent 有什么工具，还要盘点控制面能采取什么动作：拒绝、限权、减速、暂停、隔离、切换模型、只读降级、恢复、补偿、人工接管和急停。MVP 的 18 类故障必须逐一映射到有效控制动作；“检测到了，但只能告警”意味着控制器多样性不足。

#### 需要你判断

1. 你的“精细控制”是否应明确包含一套与扰动分类对应的控制动作词汇表？
2. 对未知扰动，默认隔离和转人工是否足以补充控制器多样性，还是会把复杂性全部转嫁给人？

原文核验入口：[《控制论导论》开放 PDF](https://ashby.info/Ashby-Introduction-to-Cybernetics.pdf)，重点为第 11 章必要多样性、第 13 章超大系统调节。

### 材料八：Conant–Ashby——好的控制器必须包含一个面向目标的系统模型

- 来源角色：Roger C. Conant 与 W. Ross Ashby，1970 年原始论文。
- 它要解决的问题：复杂控制器内部建立被控系统模型，是可选的工程便利，还是高效调节的必要组成。

#### 中文总结

论文在给定假设下证明：一个既成功又足够简洁的调节器，必须在结构上包含被调节系统的模型。这里的“模型”不是保存系统的全部细节，也不是生成漂亮的仪表盘，而是保留完成特定调节目的所必需的关系。

对智能体系统来说，这意味着详尽监控真正要生产的不是数据湖，而是控制器内部的**动态系统镜像**：谁在什么目标、权限、上下文、版本和环境下行动；状态怎样转移；哪些外部结果支持或推翻当前估计；什么动作仍能把系统带回安全域。

#### 关键证据与边界

论文给出的是特定形式化条件下的调节器定理。不能把“模型必须与系统同构”误读成复制系统全部微观状态；模型精度取决于控制目的。更重要的是，错误模型会让控制器稳定地做错事，因此“有模型”不是“模型正确”的保证。

#### 对本期架构的影响（AI 推断）

`Dynamic System Mirror` 必须接受三类独立校准：外部真实结果、故障注入和模型失配事件。控制决策还要保存它使用的 `system_model_version`，否则事故后无法判断是观测缺失、估计错误还是控制律错误。

#### 需要你判断

1. 动态系统镜像应该追求“全量复制”，还是只追求“足以支持当前控制目标的最小模型”？
2. 谁来监控控制器内部模型已经过时：另一个模型、确定性漂移指标、事故回放，还是三者组合？

原文核验入口：[Conant–Ashby 论文收录版](https://ashby.info/Ashby-Mechanisms_of_intelligence.pdf)，论文题为 *Every Good Regulator of a System Must Be a Model of That System*。

### 材料九：Leveson 的 STAMP——复杂事故首先是安全约束失控，不只是部件坏了

- 来源角色：MIT Nancy Leveson 的系统安全理论、开放专著与 STPA 手册。
- 它要解决的问题：软件密集、人机协作、组织参与的复杂系统中，为什么每个组件都“正常”仍可能发生事故。

#### 中文总结

STAMP 把安全视为一种需要持续施加约束的系统涌现属性。事故不仅来自组件失效，也可能来自：

- 必要控制动作没有提供；
- 正确动作在错误时间提供、停止过早或作用对象错误；
- 控制动作已发出，但执行层没有遵循；
- 控制器使用了错误或过期的过程模型；
- 反馈缺失、延迟或无法反映真实状态；
- 组织目标、激励、职责和沟通让安全约束逐渐失效。

因此分析对象不是单一 Agent，而是分层社会技术控制结构：业务与治理层对工程系统施加约束，工程控制面对 Agent 和工具施加约束，Agent 再对任务环境行动；真实世界的反馈逐层返回。

#### 关键证据与边界

STAMP/STPA 已用于航空、汽车、医疗和组织安全等复杂系统分析，但它首先是一套事故因果模型与分析方法，不会自动产生正确监控字段、控制代码或运行阈值。分析质量依赖团队是否正确识别损失、危险、控制动作和因果场景。

#### 对本期架构的影响（AI 推断）

当前 12 类系统内容应继续保留，因为它们覆盖的不只是 Agent 内部状态，还包括目标、组织、人、外部系统、资源和结果。每个控制动作需要同时检查四种不安全方式：不提供、错误提供、时机错误、持续时间错误。MVP 也必须注入“控制命令正确但执行层未执行”的故障，不能只测监控器是否下达了正确决定。

#### 需要你判断

1. 你是否同意把智能体事故的基本单位从“Agent 犯错”改为“安全约束在分层控制结构中失效”？
2. 技术团队是否有权监控组织目标、审批负载和责任链，还是这会越过工具系统的治理边界？

原文核验入口：[MIT Press 开放专著](https://doi.org/10.7551/mitpress/8179.001.0001)、[STPA Handbook](https://psas.scripts.mit.edu/home/get_file.php?name=STPA_handbook.pdf)，重点为 STAMP 基础概念与控制结构。

### 材料十：NASA Runtime Assurance——不能完全信任复杂能力时，监控必须能切换到独立安全通道

- 来源角色：NASA 智能自主系统安全保障报告与自主航空架构研究。
- 它要解决的问题：当复杂、适应性或非确定性功能无法按传统方式完全验证时，怎样允许它提供高性能，同时不让它成为唯一安全承重层。

#### 中文总结

NASA 报告把运行时监控视为智能自主系统安全架构的重要组成，但它不是旁观日志系统。典型 Runtime Assurance / Simplex 结构包含：

1. 高性能但较低可信的主功能；
2. 使用可信输入的高保障监控器；
3. 能真正改变执行路径的切换器；
4. 功能可能较弱、但安全性质更容易保证的替代通道。

安全保证主要建立在监控器和替代通道上，而尽量少依赖不可信主功能。替代通道可以是只读模式、限制范围的确定性流程、冻结写入、回到人工操作或直接急停，不必完整复制 Agent 的全部能力。

#### 关键证据与边界

相关报告来自高安全航空场景，强调架构和保障论证，并非普通软件团队的成本收益实验。Runtime Assurance 也有明确失效边界：监控器若与主功能共享错误传感器、状态摘要、模型或执行通道，就会产生共同模式故障；如果现实中不存在安全替代行为，简单“交给人”也未必有效。

#### 对本期架构的影响（AI 推断）

参考架构 v0.2 的快速确定性安全环得到支持，但还需增加一条硬规则：`safe_fallback` 必须是每个高风险能力的注册属性，包含触发条件、可达时限、独立依赖和保持时间。没有可证明安全替代通道的能力，只能在更小作用域和更低自主等级运行。

#### 需要你判断

1. 智能体生产系统是否应该允许“能力下降但安全”的正式运行模式，而不是把降级视为异常？
2. 如果高风险能力没有真正安全的 fallback，它是否应被禁止自主运行？

原文核验入口：[NASA 2018 安全保障报告](https://ntrs.nasa.gov/api/citations/20180006312/downloads/20180006312.pdf)、[NASA 2023 自主系统安全架构论文](https://ntrs.nasa.gov/api/citations/20220016762/downloads/fnpw-SSS2023-final.pdf?attachment=true)，重点为 pervasive runtime monitoring、Simplex/RTA 和 secondary channel。

## 跨材料综合：当前架构需要怎样修正

以下是 AI 根据五份材料形成的结构化推断，尚未视为用户主张。

### 1. “控制面”不是一个万能监控器，而是多个不同判定边界

```text
TaskContract
    ↓ 约束目标与完成证据
Agent Runtime ──提出──> ActionIntent
    ↓                       ↓
ExecutionLedger       ActionManifest → ExecutionLease → 外部副作用
    ↓                       ↓                    ↓
EvidencePacket ←── 工具结果、测试、权限、恢复与补偿证据
    ↓
CompletionDecision: pass / fail / unknown
    ↓
OutcomeRecord → EvolutionCandidate → 回放 / eval / 审批 / 灰度 / 回滚
```

### 2. 原先六类对象需要拆细

- `Evidence` → `ExecutionLedger + EvidencePacket + OutcomeRecord`
- `ActionIntent` → `ActionIntent + ActionManifest + ExecutionLease`
- `Checkpoint` → `RecoveryCheckpoint + CompensationPlan + ResumePreconditions`
- 保留 `TaskContract + CompletionDecision + EvolutionCandidate`

这些拆分并非为了增加名词，而是防止不同语义混在一个对象里：当前状态不能代替审计证据，批准不能代替执行资格，恢复游标不能代替外部回滚，监控信号不能代替完成结论。

### 3. 完成门禁应判断“证据义务是否闭合”，而不是判断 Agent 是否显得自信

一个暂定的 `CompletionDecision` 至少需要检查：

- 目标：`TaskContract` 中的目标与验收项是否都有对应证据；
- 状态：证据是否仍然新鲜，是否被后续修改失效；
- 影响：声明范围外的下游是否被检查；
- 行动：所有高风险副作用是否经过有效 manifest 和 lease；
- 恢复：失败路径是否有有效恢复点，已发生副作用是否可补偿；
- 结果：关键行为是否经过独立、可复算或外部验证；
- 未知：无法判断的部分是否被显式列出并路由，而不是默认通过。

### 4. 第二组材料把主张改写成“五个相乘项”

```text
生产控制能力
  ≈ 状态可观测性
  × 系统模型充分性
  × 控制动作必要多样性
  × 安全替代通道可信度
  × 结果反馈与模型校准能力
```

这不是可直接计算的数学公式，而是一个架构判据：任何一项接近零，其他部分再强也无法形成生产级控制。

由此得到三个新增对象：

- `ControlAuthorityMatrix`：偏差—动作—权限—时限—验证—后备的映射；
- `SystemModelVersion`：控制决定实际依赖的过程模型版本和适用边界；
- `SafeFallbackContract`：每个高风险能力的独立安全替代通道与可达条件。

不需要阅读原文，也不必逐题回答每份材料。请按你的真实判断回答：

1. **主张边界**：你是否接受“详尽监控是唯一可靠的认识基础，但不是完整控制解法；控制还要求足够的干预手段与安全替代通道”？不同意的部分是什么？
2. **控制对象**：你更认同监控整个“Agent—工具—环境—人—组织”控制结构，还是先把边界限制在 Agent 与工具？为什么？
3. **生产底线**：一个高风险能力如果没有独立且可验证的安全 fallback，是否应该禁止自主运行？请用一个你熟悉的开发任务说明。
