# 研究立项

## 主问题

为什么智能体生产系统不能从功能清单或暂停按钮出发，而应从 Agent—工具—环境—人的完整闭环建立控制母模型？

本期同时回答一个容易混淆的工程问题：DeepSeek Harness（DSH）与该控制系统是什么关系？结论是 DSH 是可替换的下层 Agent Runtime 和插件接缝，不是控制系统本身；完整系统还包括框架无关控制面、高权限 Safety Executor 与 Watchdog。

## 为什么现在值得研究

Agent 正从对话界面进入代码库、浏览器、企业系统和真实业务流程。模型能力越强，团队越容易把“能完成任务”误认为“能稳定进入生产”。现有方案常从日志、权限、编排 UI 或暂停按钮出发，却没有先回答被控对象是什么、哪些状态可观测、控制命令何时真正生效、失败后是否仍可恢复。

## 目标读者与困境

- 目标读者：正在将 Agent 接入研发或业务生产流程的技术负责人、架构师和 Agent 平台建设者；与主题知识距离中等。
- 当前困境：已经有模型、工具调用、日志、权限和工作流，却仍无法判断 Agent 是否理解了当前目标、依据是否过期、控制是否真正接纳、工具成功是否等于现实结果。
- 切身利害：继续堆功能会把不可解释的自主性放大成生产风险；过度收紧又会把 Agent 退化为昂贵脚本。

## 暂定假设

智能体生产系统真正需要控制的不是 LLM 隐藏思维或某次输出，而是 Agent 作为下层控制器，与工具、工作对象、环境和人形成的完整闭环。上层监督控制面不替 Agent 思考，而是动态调整它在什么信息、能力、权限、预算和恢复条件下可以继续改变世界。

## 推翻证据

- 只靠模型级 prompt、日志和一个暂停按钮，能在跨步骤、外部副作用和延迟结果任务中稳定重建状态并验证控制效果；
- 控制命令入队与实际接纳之间没有可观测差异；
- 工具回执可以可靠代表真实世界效果，无需独立对账；
- Agent 版本、上下文、插件、工具集合变化后，历史能力结论仍可无条件继承。

## 本期不研究

- 不证明 LLM 内部状态可被精确估计或输出可数学收敛；
- 不设计完整多 Agent 编排平台、UI、数据库和云选型；
- 不把 DeepSeek Harness 直接定义为生产控制面；
- 不 fork DSH，也不在控制面重写 DSH 已拥有的 Agent Loop / Turn / Step orchestration；
- 不声称本文母模型已经过生产数据验证。

## 时间盒与停止条件

以现有控制母模型、钱学森工程控制论材料和 DeepSeek Harness 固定提交为证据边界。形成一个可反驳主张、一张嵌套闭环图和一篇面向技术负责人的独立文章后停止；工程有效性留给后续单 Agent 对照实验验证。
