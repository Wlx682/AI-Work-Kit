## 已有明确判断

- 用户原始判断：此前控制面 MVP 经多次修改后成为“一次次的临时决定”，没有从 AI Agent 的角度理解目标系统。
- 用户提出的方向：尝试从钱学森《工程控制论》寻找启发，重新设计智能体系统，而非继续修补功能清单。
- 用户对 Harness 的判断：在阅读分析后明确要求“吸收一下”，接受将运行时的事件分域、接纳点、状态投影、继续授权等机制放回母模型，但没有要求把 Harness 原样作为生产架构。
- 本轮发布意图：用户明确要求“根据文档写一篇文章发布到知乎”，即以已形成的控制母模型作为文章主张来源。
- 关系澄清反馈：用户在阅读更新后的母模型和计划后仍明确表示“没看明白，DSH 和我的智能体控制系统是什么关系”，说明原文虽列出 Adapter、插件和安全边界，却没有先给出系统装配关系。
- 用户确认的新表达任务：更新所有相关文档，统一说明“DSH 是下层 Runtime 与插件接缝；控制系统由 DSH 控制插件、框架无关控制面、高权限 Safety Executor/Watchdog 共同构成”。

## 门禁 A 记录

- 惊讶/变化：问题已从“怎样把控制面做完整”转为“控制面究竟在控制哪个系统”。
- 冲突：经典控制论提供有价值的建模次序，但 LLM 隐藏认知不可被当作连续、精确可测状态；Harness 提供灵活运行时，但“无特权核心”不能直接承担生产安全根。
- 跨材料连接：工程控制论要求先区分参考、状态、观测和控制；Harness 恰好暴露出持久事实、实时控制、能力强制以及命令接纳时序的工程切面。
- 结论：门禁 A 已通过，依据是用户对工程控制论方向、临时修补问题和 Harness 吸收边界的连续明确判断。

## 2026-08-14 后置校正

- 不是“fork DSH 改成控制系统”，而是“不 fork DSH，用 out-of-tree 插件把传感器和控制接纳点装进 DSH”。
- 不是“在 DSH 外重写 orchestration”，而是让 DSH 继续拥有 Agent Loop，控制面只监督运行条件。
- 不是“安全能力不能是插件”，而是无论实现形式如何，Agent 都不能拥有安全配置、卸载、凭证或旁路权。
