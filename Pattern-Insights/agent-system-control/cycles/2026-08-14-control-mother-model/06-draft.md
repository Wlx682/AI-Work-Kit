# 研究稿

## 读者入口卡

- 文章类型：技术观点型。当前只有架构推导和公开工程案例，没有本系统自己的生产实验，不能写成案例复盘型或研究结果型。
- 具体目标读者：正在把 Agent 接入代码库、浏览器或业务系统的技术负责人、架构师和平台建设者。
- 与主题的知识距离：中。读者理解 LLM、工具调用、日志和权限，但未必熟悉控制论或 Agent Runtime 的接纳时序。
- 读者当前处境：已经搭出 Agent demo，正在讨论生产化；平台功能越列越多，却仍无法回答什么时候可以放心放权。
- 读者已经知道什么：模型会幻觉、工具需要权限、长任务需要日志和人工接管。
- 读者尚未意识到什么：这些能力没有共享同一个被控系统模型；Agent Runtime 与控制系统不是同一层；“指令已发”“API 成功”“目标 active”也都不等于控制已经发生。
- 这件事与读者的切身利害：控制对象定义错误，会同时造成风险失控与过度治理，既无法安全放权，也无法保留 Agent 的自主价值。
- 读者当前默认判断：再补日志、规则、评估、编排 UI 和暂停按钮，系统就会逐步可控。
- 读后应改变的判断或行动：先建立 Agent—工具—环境—人的完整闭环，按事实、估计、偏差、命令、生效和结果分账；将 DSH 之类的框架放在下层 Runtime，把插件接缝、上层监督决策和高权限执行边界装配成完整控制系统。
- 本文不解决什么：不提供完整平台 API/ER，不证明 LLM 内部可观测，不给生产收益百分比。
- 开场策略：熟悉处境。先从“Agent demo 很快、生产控制面越做越大”进入，再指出功能累积无法回答控制对象。
- 同心入口：Agent 进入真实系统 → 日志权限仍无法放心放权 → 旧解释把控制等同于功能 → 真正要控制的是 Agent 改变世界的条件。
- 案例能否前置：不能。Harness GUI 事故需要解释项目和运行环境，放在主张建立后作为验证。

## 论证骨架

1. 功能清单不能累积成可控性，因为每项功能使用了不同的隐含系统边界。
2. Agent 自己是下层控制器；人类系统应成为上层监督控制器。
3. 上层不读取隐藏思维，而重建可证伪的功能状态并控制运行条件。
4. 工程上必须把事实投影、认识估计、偏差余量、命令、生效和现实结果分账。
5. DSH 是下层 Runtime；控制插件把传感器和接纳点装进 DSH；框架无关控制面负责估计与决策；高权限执行器/Watchdog 负责不可旁路执行和降级。
6. Harness 通过事件分域、纯投影、接纳点和 Goal 激活暴露这些工程切面；事故复盘说明外部状态不可省略，但 `ControlApplicationReceipt` 与 `ContinuationLease` 是本系统派生契约。
7. 安全边界取决于 Agent 是否掌握配置、卸载、凭证和旁路权，不取决于能力是否以插件实现。
8. MVP 应先用同一契约比较 DSH 插件与现有 LangGraph Adapter，再验证单 Agent 闭环，而非先做平台大全。

## 反向提纲

1. 为什么功能越加越多仍不放心 → 功能没有共享被控系统边界 → 需要先定义谁控制谁。
2. Agent 是什么角色 → Agent 自己是下层控制器 → 上层只能监督运行条件。
3. 为什么引用工程控制论 → 借建模次序而非精确预测 → 转向可证伪功能状态。
4. 怎样形成系统镜像 → 六类事实与推断分账 → 才能定位失败来源。
5. DSH 与控制系统是什么关系 → DSH 负责下层 Agent 运行，插件负责传感与接纳，控制面负责监督判断，安全执行域负责不可旁路动作 → 不 fork、不重写第二套 orchestration。
6. Harness 提供什么证据 → 事件、投影、Goal 和接纳点真实存在 → 但 Receipt/Lease/现实恢复属于控制系统派生契约，安全按权限域证明。
7. 真实失败怎样发生 → 局部成功没有共同现实对象 → 结果验证必须独立。
8. 如何定义稳定 → 目标、资源、影响与恢复有界 → 不能压成输出一致或总分。
9. 怎样验证 → 先做双 Runtime 接缝 Spike，再做单 Agent A/B/C 对照 → 先证明接缝与闭环，再扩平台。
