# 研究立项

## 主问题

推进智能体控制系统实践时，为什么第一步应是评估，以及如何用最小评估基线识别 Agent—工具—环境闭环是否具备进入控制改造的条件？

## 为什么现在值得研究

上一篇已经把 DSH 定位为可替换的下层 Agent Runtime，把控制系统定位为框架无关的上层监督控制面。下一步若直接实现状态机、控制策略、看板或编排层，会同时引入太多假设：团队甚至不知道当前 Agent 的失败主要来自模型、Harness、工具、环境、任务定义，还是验收方式。

因此实践的第一步不是“先加控制”，而是建立一份可复现的控制就绪度基线：先证明我们测的是哪一个系统、能看到哪些关键事实、外部结果能否独立验收、干预命令能否到达，以及受扰动后是否还能安全恢复。

## 目标读者与困境

- 目标读者：已经拥有可运行 Agent 或准备基于 DSH/LangGraph 等 Runtime 改造的技术负责人、架构师和平台工程师。
- 知识距离：理解 Agent Loop、工具调用和常规测试，但容易把模型 Benchmark、Demo 成功率或日志完整度当成生产可控性的证据。
- 当前处境：模型和工具都在快速变化，团队想推进控制面实践，却不知道第一批数据、故障样本和验收条件该怎么选。
- 切身利害：若没有基线，后续任何“提升”都无法归因；若只做能力分数，又可能把高能力但不可观测、不可干预、不可恢复的配置放进生产。

## 暂定假设

用户的起始判断是“推进实践的第一步应该是评估”。本期把它收敛为一个可反驳假设：

> 智能体控制系统的第一项工程产物不应是控制策略或平台 UI，而应是一套控制就绪度评估基线。它把模型、Harness、工具、权限、任务环境和资源预算视为同一个被测配置，并通过真实任务、外部结果验收、轨迹证据、干预测试和故障注入，判断这套配置是否具备进入控制改造的条件。

评估的产物不是一个“Agent 健康总分”，而是一张带硬缺口的证据矩阵：任务价值、结果真实性、可观测性、控制可达性、扰动恢复、可靠性与成本分别保留，任何关键维度缺失都不能由平均分抵消。

## 推翻证据

- 仅靠公开模型 Benchmark 或一次端到端成功率，就能稳定预测具体 Harness、工具、权限和真实环境下的生产行为；
- 改变 Harness、上下文管理、工具集合、重试预算或环境后，原评估结论仍可无条件继承；
- Agent 的自述、工具 HTTP 200 或内部测试通过可以可靠替代外部世界状态验收；
- 不注入权限拒绝、陈旧证据、工具假成功、目标变更和恢复失败等扰动，也能证明暂停、降权、回滚和接管链路有效；
- 一个统一总分比保留多维硬缺口更能指导是否扩大 Agent 自主权。

## 本期不研究

- 不建设完整 Eval 平台、排行榜或跨行业通用题库；
- 不以模型排名代替具体生产配置评估；
- 不证明隐藏思维可被完整观测，也不把 Chain-of-Thought 作为唯一证据；
- 不在本期实现全部控制面，只定义最小评估对象、任务集、故障集、记录格式和准入判断；
- 不把 20–50 个初始任务产生的结果外推为长期生产安全证明。

## 时间盒与停止条件

研究包以 6 类材料为边界：近期 Agent Eval 实践、Harness 有效性、DSH 真实失败、NIST 评估探针、SRE/混沌工程和 Benchmark 反例。形成以下内容后停止：

1. 一个可反驳核心主张；
2. 一张“被测配置—观测—干预—外部结果”评估闭环图；
3. 一套 12–20 个真实任务、5 类扰动、3 组对照和多维准入门槛的最小实践方案；
4. 一篇承接上一篇、面向技术负责人的知乎独立文章。
