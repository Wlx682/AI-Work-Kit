# 模式图

## 模式 1：评估不是测量入口，评估有效性才是入口

- **可反驳表述：** 在用 Eval 结论改造或控制 Agent 之前，必须先证明 Eval 的任务、参照、评分器、Harness 和预算足以支持目标主张；否则“评估优先”只是在更早阶段引入假证据。
- **来源事实：** OpenAI 要求先声明能力、比较或安全主张，并检查 Reward Hacking、坏题、污染和 Harness 失真；Anthropic 要求参考解、人工校准与轨迹复核。
- **用户连接：** 用户明确判断，评估若虚假或没有参考价值，之前假设全部不成立。
- **最强反例：** 实践中无法先证明评估绝对正确；若把“评估评估器”无限递归，会阻塞任何工程进展。
- **成立边界：** 不要求绝对正确，只要求证据足以支持当前风险等级的决策，并明确不能支持什么。低风险、可逆任务可用较轻校准；高风险、不可逆任务要求外部真值和人工裁决。
- **缺失证据：** 尚未为目标 Agent 任务计算人工一致性、评分器错误率和任务可解性。
- **置信度：** 高。
- **质量评分：** 9/10；跨供应商方法、反方论文、真实事故和用户判断一致。

## 模式 2：允许拒绝出分，是靠谱评估的组成部分

- **可反驳表述：** 一个必须对每次试验给出通过/失败或总分的评估系统，会在参照不足、环境异常和专家分歧时制造伪精度；可靠体系必须允许 abstain、不可评和升级人工。
- **来源事实：** Anthropic 指出模型评分器需要人工校准，坏题往往表现为极端低通过率；OpenAI 把 broken problems 和 validity hazards 作为标准风险；NIST Probe 返回带理由和证据的结构化 verdict，而非只有分数。
- **用户连接：** 用户明确要求哪怕人工辅助，也不能为了完成评估而强行完成。
- **最强反例：** 大量不可评会使团队无法比较版本，也可能被滥用为回避困难案例。
- **成立边界：** abstain 必须附原因码、缺失证据、责任人和重新评估条件；持续高 abstain 率本身是 Evaluation Readiness 失败，而不是无责任出口。
- **缺失证据：** 尚未定义原因码和人工响应时限。
- **置信度：** 高。
- **质量评分：** 9/10；直接来自用户价值判断，并有方法论支撑。

## 模式 3：先验证参照物，再验证 Agent

- **可反驳表述：** 每个评估任务必须有可执行参考解或可观测外部真值，并通过人工/程序验证评分器能让正确方案通过、错误机制失败；否则不能进入基线。
- **来源事实：** Anthropic 建议每个任务设置可通过的参考方案；DSH 回归测试曾因超时退出而产生假阳性，真实复现才暴露问题；Google SRE 强调测试必须覆盖实际配置并可因报告机制失败。
- **用户连接：** 用户把“有没有参考价值”提升为所有后续假设成立的前提。
- **最强反例：** 开放式研究、设计和决策任务没有唯一参考答案。
- **成立边界：** “参照”不等于标准答案；可以是外部事实、业务约束、专家共识区间、禁止行为、不变量或多方案可接受集合。没有可接受判据的任务暂不自动评分。
- **缺失证据：** 目标领域的专家共识与可接受解集合尚未采集。
- **置信度：** 高。
- **质量评分：** 9/10；DSH 案例提供了清晰反事实。

## 模式 4：评估可靠性与 Agent 表现必须分开报告

- **可反驳表述：** 每个结果至少包含两个轴：Agent 表现和 Evaluation Confidence。低置信的高分不能用于扩大自主权，高置信的失败才可驱动确定性改造。
- **来源事实：** OpenAI 要求把有效性危害、Harness 和预算与结果同时报告；Benchmark Lottery 说明聚合分数受任务选择支配；NIST 把 verdict、理由和证据映射放入审计轨迹。
- **用户连接：** 若评估不可靠，之前控制假设全部失效，因此“Agent 得分”不能脱离“这次评估有多可信”。
- **最强反例：** 双轴和证据矩阵比一个总分难传播、难设 KPI。
- **成立边界：** 决策界面可以简化，但底层不得丢失证据质量、覆盖率、人工一致性、不可评比例和配置版本。
- **缺失证据：** Evaluation Confidence 的计算方式仍需 Spike，不能先虚构公式。
- **置信度：** 中高。
- **质量评分：** 8/10；方向清晰，量化方法待实验。

## 模式 5：自主权应随证据成熟度递增，而不是等评估“全部完成”

- **可反驳表述：** 不急于完成整个系统并不等于停滞。可以按证据成熟度从影子运行、只读、受限写入到高权限执行逐级开放；每一级只使用已验证的评估维度。
- **来源事实：** Anthropic 建议从 20–50 个真实任务起步并持续维护；Chaos Engineering 要求最小爆炸半径；Google SRE 将测试覆盖与可接受风险、发布节奏关联。
- **用户连接：** 用户明确不要急于完成整个系统，把靠谱评估置于进度之前。
- **最强反例：** 过细的成熟度分级可能演变成治理流程，拖慢价值验证。
- **成立边界：** 第一阶段只做一个 Agent、一类任务和少量可逆工具；不建设全量平台，不承诺通用评分。
- **缺失证据：** 尚未确定首个真实任务域和风险分级。
- **置信度：** 中高。
- **质量评分：** 8/10；需要真实 Spike 验证成本。

## 暂定因果链

1. 若评估任务、参照或评分器失真；
2. 则 Agent 状态估计与能力判断使用错误证据；
3. 上层控制策略会基于错误状态分配权限、预算和继续授权；
4. 控制系统虽然流程完整，却会稳定地做出错误决定；
5. 因此第一项实践不是“评估 Agent”，而是“建立并验证一套有资格产生控制证据的评估闭环”。
