# 研究稿：智能体控制实践的第一步，是先证明评估可信

> 本文件保存读者模型、论证结构、证据边界与编辑检查，不直接发布。

## 文章类型

技术观点型，带最小实践方案。没有生产对照实验数据，不写成案例复盘或已验证方法。

## 读者入口卡

- **具体是谁：** 已经拥有一个可运行 Agent，或准备基于 DSH、LangGraph 等 Runtime 推进生产改造的技术负责人、架构师、平台工程师；与评估主题知识距离中等。
- **此刻在哪里：** 已经能跑任务、调用工具、看日志，正在决定先做 Eval 平台、控制面、权限系统还是编排能力。
- **已经知道什么：** 模型有随机性，需要测试；真实 Agent 不只是一次模型调用；工具成功不一定等于业务成功。
- **尚未意识到什么：** Eval 不是中立仪表。任务、参照、Harness、预算和评分器一旦失真，控制面会稳定地消费假证据。
- **为什么现在读：** 没有可信基线，后续所有优化不可归因；错误评估还会给扩大权限制造“数据依据”。
- **默认判断：** 先找 Benchmark、搭评估平台、把成功率跑出来，再据此改 Agent。
- **读后改变：** 先建设 Evaluation Qualification，允许不可评和人工裁决；只在评估本身合格后建立 Agent 基线。
- **不讲什么：** 不建设完整控制面，不比较所有 Runtime，不设计通用排行榜，不给出未经实验验证的统一分数公式。
- **开场策略：** 从读者熟悉的“跑成功率、选模型、搭 Eval”处境进入，先说明错误评估对权限决策的直接风险，再给出“先评估评估本身”的判断；DSH 案例后置为证据。

## 单一核心主张

智能体控制系统实践的第一步，不是给 Agent 打分，而是先证明评估本身有资格产生控制证据。宁可人工介入或宣布不可评，也不能为了跑完流程强行给出通过结论。

## 论证骨架

### 一、评估可以比没有评估更危险

没有评估时，团队知道自己在凭经验；错误评估会把未知包装成 82 分、90% 通过率和一条绿色曲线，进而为加权限、扩任务和减少人工提供伪证据。

### 二、DSH 事故证明：选错参照，所有内部成功都可同时成立

引用固定提交的 GUI Post-mortem。构建成功、HTTP 200、Boot Manifest、替代服务正常都成立，但没有一个证明用户当前页面已变化。这里的核心不是 Agent 能力差，而是验收对象、环境身份和失败机制没有被正确限定。

### 三、靠谱不是完美，而是知道证据能支持什么

评估结果采用四态：PASS、FAIL、ABSTAIN、INVALID。后两者分别表示证据不足和评估装置失效。Agent 表现与 Evaluation Confidence 分开。

### 四、Evaluation Qualification 六道资格检查

1. Decision Claim：本轮结果准备用于什么决策；
2. Config Identity：固定模型、Harness、工具、权限、环境和预算；
3. Reference Validity：有外部真值、业务不变量或专家共识区间；
4. Failure Sensitivity：已知错误必须能失败，负对照不能被误判通过；
5. Grader Calibration：程序、模型和人工评分器相互校准；
6. Uncertainty Exit：证据不足时可 abstain 并升级人工。

### 五、最小实践不做平台，只做一个合格评估闭环

限定一个 Agent、一类高价值任务、少量可逆工具；先从 4 个高信息密度 Case 起步，其中同时有正常任务、边界/拒绝任务、已知故障 Seed 和恢复/接管任务。先用参考解和错误解验证评估，再跑 Agent。

实现落点增加 `evaluation/models.py`、`fingerprint.py`、`oracles.py`、`qualification.py`、`runner.py`、`store.py` 及对应 Red 测试。首个验收必须证明：`RunResult.succeeded=True` 时，外部文件状态未变化仍判 FAIL；未知工具效果且无外部证据时判 ABSTAIN；Oracle 或环境无效时判 INVALID。

### 六、人工不是自动化失败，而是测量基准

人工负责建立 Gold Set、处理分歧、校准 LLM Judge、判定开放式任务是否可接受。自动化只能覆盖已经被证明可自动判断的部分。

### 七、进入下一步的不是一个总分，而是一组可审计产物

EvaluationConfig、Qualified Eval Registry、Evidence Matrix、Failure Corpus、人工裁决记录与重评触发条件。只有证据支持相应风险等级，才进入影子运行或受限写入实验。

### 八、回应“可靠评估会拖慢实践”

不要求完美评估或全场景覆盖，而要求权限不超过证据。最小基线用于减少不可归因性，不是先造平台。

## 证据与边界

- Anthropic 支持 task/trial/grader/transcript/outcome、参考解、重复试验和人工校准；不能证明本文控制准入方案已经有效。
- OpenAI 支持 Harness、预算、工具和有效性风险是评估结果的一部分；其主题偏第三方前沿模型评估。
- DSH Post-mortem 是强机制案例，但只是单一事故。
- NIST 支持嵌入式 Probe 和机器可读证据链，目前重点是事实落地性。
- Google SRE/Chaos 支持受控扰动、实际配置核验和可失败测试；不能把稳态指标原样套到开放任务。
- Benchmark Lottery 支持反对统一聚合分数；不能推出拒绝一切量化。
