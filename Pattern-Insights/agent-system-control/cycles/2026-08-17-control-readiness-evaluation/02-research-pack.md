# 中文研究包

> AI 交付翻译式总结，不是全文逐字翻译；原文链接与定位只作为核验入口。

## 先读结论地图

六类材料共同指向一个暂定判断：推进控制系统实践时，“评估”不能只是给模型做题，而是对一份明确版本的 Agent 运行配置做系统辨识。至少要回答五个问题：

1. **测的是谁**：模型、Harness、提示词/上下文、工具、权限、环境、资源预算和安全措施的哪一个组合？
2. **结果是真的吗**：Agent 自述、工具回执和外部世界状态是否被区分并独立验收？
3. **过程看得见吗**：轨迹、工具参数、证据、目标版本和环境身份是否足以重放关键判断？
4. **干预到得了吗**：暂停、撤权、降级、恢复、接管是否被 Runtime 接纳并产生可验证效果？
5. **受扰动后怎样**：目标变化、陈旧证据、工具假成功、权限拒绝、延迟反馈和恢复失败出现时，损失、恢复时间和人工负担是多少？

下面不是把六份材料的结论拼成答案，而是把它们各自能证明什么、不能证明什么和需要你决定什么列出来。

## 材料 1：把 Agent Eval 从“回答评分”改成“任务—轨迹—外部结果”

- **来源角色：** Anthropic 工程团队，2026 年 Agent Eval 实践总结。
- **要解决的问题：** 多轮 Agent 会调用工具、修改环境并适应中间结果，传统单轮输入—输出评分无法覆盖错误传播、环境变化和非确定性。
- **核心主张：** 评估 Agent 时，评估的是 Harness 与模型共同构成的系统。一个 Eval 至少要明确任务、重复试验、评分器、完整轨迹和最终环境结果；结果不是 Agent 说“完成了”，而是外部状态真的发生了预期变化。
- **机制/方法：**
  - 用 task 定义输入和成功条件，用 trial 表示同一任务的一次随机尝试；
  - 同时采用代码评分器、模型评分器和人工评分器，并把主观评分器与专家判断校准；
  - 区分 capability eval 与 regression eval：前者寻找能力边界，后者保护已经稳定的行为；
  - 对非确定性重复运行，用 pass@k 衡量“多次里至少成功一次”，用 pass^k 衡量“连续多次都成功”；
  - 从 20–50 个真实失败或人工检查任务开始，不等待完美大题库。
- **关键证据：** Anthropic 给出的编码、对话、研究和 Computer Use 例子都把环境状态检查放在最终结果层；其 Claude Code 实践也从窄行为评估逐步扩展到复杂行为。材料特别强调读取轨迹，不能只接受头部总分。
- **局限与反方：** 这是供应商经验总结，不是独立对照研究；其重点仍是产品质量与回归，不直接给出控制可达性、恢复性和安全准入门槛。LLM 评分器可扩展但非确定，需要人工校准。
- **与本期问题的关系：** 它给出“先评估”的最小工程骨架，但本期需要再加上控制系统特有的干预回执、外部对账、故障注入和恢复评估。
- **需要你判断：**
  1. 第一版是否从 12–20 个高价值真实任务开始，而不是追求 50 个？
  2. 对生产 Agent，你更关心 pass@k 的上限能力，还是 pass^k 的连续可靠性？
  3. “任务完成、没有越权、可以恢复”是否必须是三个独立硬门槛？
- **原文核验入口：** [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，重点看 The structure of an evaluation、How to think about non-determinism、Going from zero to one。

## 材料 2：Harness 不是评测容器，而是被测系统的一部分

- **来源角色：** OpenAI，2026 年关于可信第三方评估的测量有效性总结。
- **要解决的问题：** 同一个模型在不同上下文管理、工具、重试、预算和 Harness 下会表现出不同能力；如果报告只写模型名和分数，结论可能错配。
- **核心主张：** 评估必须先声明想支持哪一种主张：能力上限、同条件比较，还是安全措施抗攻击性。Harness、工具、预算、Elicitation 方法和有效性检查都是评估结果的一部分。
- **机制/方法：**
  - 若要估计能力上限，要使用可信的强 Harness 和足够预算；
  - 若要比较系统，要固定任务、评分、预算和 Harness，或预先固定一组 Harness；
  - 记录模型、推理设置、工具、上下文管理、重试、Token、时间、成本和安全措施；
  - 每轮检查 reward hacking、拒答、数据污染、坏题和评估意识；
  - Harness 变化后重新评估，不把旧分数直接迁移到新配置。
- **关键证据：** 材料列举长轨迹中压缩策略、测试预算和定制 Harness 会显著改变结果；同一 Benchmark 换 Harness，性能和成本结构都可能变化。它还指出评估得分应表述为“在此 Harness 和预算下的结果”，不是模型的固定属性。
- **局限与反方：** 文章主要讨论前沿模型第三方安全与能力评估，目标比普通企业 Agent 更宏观；其 maximum elicitation 思路不应直接作为生产准入，因为生产更关心受限权限下的可靠性和损失。
- **与本期问题的关系：** 直接支持把 DSH/LangGraph Adapter、工具集合、权限策略、上下文压缩和预算统一纳入 EvaluationConfig。DSH 不是中立跑分器，它本身会改变被测行为。
- **需要你判断：**
  1. 控制面是否应该把 EvaluationConfig 做成不可变版本，并要求任何关键变化触发重新基线？
  2. 第一版要比较 DSH 与现有 LangGraph Runtime，还是只为当前 Runtime 建基线？
  3. 资源预算应作为硬条件，还是只做成本指标？
- **原文核验入口：** [OpenAI：A shared playbook for trustworthy third party evaluations](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)，重点看 Selecting the right harness、Assess validity 和报告字段清单。

## 材料 3：DSH 事故说明“内部成功”与“用户世界改变”是不同事实

- **来源角色：** DeepSeek Harness 官方 Post-mortem，固定提交 47f9438，真实失败案例。
- **要解决的问题：** Web Agent 修改 GUI 后，没有识别当前页面、URL、进程和运行模式；它把构建成功、HTTP 200、Boot Manifest 和用户当前页面变化当成了同一种成功。
- **核心主张：** 每个内部动作都合理，并不代表它们指向同一个验收对象。评估必须绑定确切的运行时身份和外部结果，替代服务成功不能证明当前服务发生了变化。
- **机制/方法：**
  - 把当前 URL、Runtime 模式和进程身份变成模型可见、Shell 可查询、日志可重建的事实；
  - 针对原始端口和未变化页面做外部验收，不以新起服务替代；
  - 回归测试必须能因报告中的真实机制而失败，不能让超时或错误退出制造假阳性；
  - 保存原始 Session 事件、浏览器截图、HTTP、进程和外部状态证据。
- **关键证据：** Agent 在 5173 端口看到 HTTP 200 后声明成功，但页面因缺少 window.__DSH_BOOT__ 白屏；随后又验证 3334 的替代服务，却从未检查用户使用的 3081。最终由用户指出原页面已变化，才检查真实进程。
- **局限与反方：** 这是单一 Web GUI 事故，不能量化所有 Agent 的失败率；修复措施针对 DSH Web 组合，不等于通用控制协议。
- **与本期问题的关系：** 它适合作为最小基线的第一颗 Failure Seed：工具成功但外部结果未确认、运行时身份错误、替代目标验收、非托管后台进程、错误回归测试。若评估体系抓不住这个已知故障，就没有资格评价控制就绪度。
- **需要你判断：**
  1. 这篇续文是否以该事故作为中段证据，而不是开场案例？
  2. “外部结果验证”是否应当是所有有副作用任务的硬门槛？
  3. DSH Spike 是否必须复用这一事故作为跨 Runtime 一致性测试？
- **原文核验入口：** [DeepSeek Harness Post-mortem 0003](https://github.com/deepseek-ai/deepseek-harness/blob/47f943859bef60e4160492346772ded9b24f765a/docs/postmortem/0003-web-agent-gui-feedback-loop.md)，重点看 Executive summary、Root cause、Guardrails added、Lessons。

## 材料 4：评估可以嵌入运行过程，形成机器可读证据链

- **来源角色：** 美国 NIST ITL 的 Agentic AI 评估探针项目，2026 年公开进展。
- **要解决的问题：** Agent 表面接口很简单，内部却是多步工作流；用户缺少对证据、工具使用和决策链的可见性，难以判断输出是否可信。
- **核心主张：** 可把独立 Evaluation Probe 嵌入 Agent 工作流，作为对抗性验证器；探针既可在线执行，也可事后执行，并把 verdict、理由和证据映射积累为机器可读审计轨迹。
- **机制/方法：**
  - 当前从事实落地性这一基础任务切入，以人工整理的可信语料为参照；
  - 每个引用分别检查 faithful、complete、sufficient；
  - 探针由独立 rubric 定义，新增维度无需重写主流程；
  - 输出结构化 verdict、理由和证据位置。
- **关键证据：** NIST 已构建开源 Deep Research Testbed，把相关性判断、带引用报告和逐引用 Evaluation Probe 串联，并保存结构化审计轨迹。
- **局限与反方：** 项目仍处于方法建设阶段，当前重点是事实与引用，不覆盖工具副作用、权限控制、恢复能力或生产损失；LM Judge 自身也需要校准。
- **与本期问题的关系：** 它支持把 Eval 从一次性离线报告升级为 Runtime Seam：离线用于基线与回归，在线用于关键证据、工具结果和继续授权的探针。但第一版不应直接把所有在线探针变成阻断策略。
- **需要你判断：**
  1. 第一阶段是只读 Observation Mode，还是允许部分硬门禁阻断？
  2. Probe Verdict 应写回 DSH Session Log，还是先进入框架无关的 Causal Ledger？
  3. 哪些证据维度必须用确定性程序判断，哪些可暂用 LLM Judge？
- **原文核验入口：** [NIST：Building Evaluation Probes into Agentic AI](https://www.nist.gov/programs-projects/building-evaluation-probes-agentic-ai)，重点看 Overview、Objectives、Approach。

## 材料 5：要理解系统，就必须在受控条件下让它遭遇真实扰动

- **来源角色：** Google SRE 的可靠性测试经验与 Chaos Engineering 的系统实验原则，作为邻近领域迁移。
- **要解决的问题：** 单元测试或正常路径成功无法证明复杂系统在真实配置、依赖组合和故障下仍可靠；系统变化会增加未来行为的不确定性。
- **核心主张：** 测试的价值是减少变化带来的不确定性。先定义可测的正常系统输出，再引入真实世界扰动，比较控制组与实验组，主动尝试推翻“系统仍能保持可接受状态”的假设。
- **机制/方法：**
  - 核验生产实际配置，而不只核验仓库里的期望配置；
  - 重放随机动作并保存 Seed，通过重复运行估计非失败率；
  - 从可测外部结果定义稳态，注入依赖失败、错误响应、流量变化等扰动；
  - 优先高影响或高频扰动，控制爆炸半径，自动化重复执行；
  - 高风险系统需要更高覆盖，不用平均测试数量掩盖关键路径缺口。
- **关键证据：** Google SRE 指出测试环境依赖缺口会导致测试持续通过而被测系统仍有错；配置测试需要查询实际生产配置。Chaos Engineering 明确把可测输出、控制组、真实扰动和证伪作为四步实验。
- **局限与反方：** Agent 任务常是非平稳、开放式和语义型的，“稳态”不能简单照搬吞吐、延迟；生产直接故障注入不适合早期 Agent 控制实验，应先从沙箱/影子运行和最小爆炸半径开始。
- **与本期问题的关系：** 支持将评估从“静态题库”推进为最小系统辨识实验。候选扰动包括陈旧证据、工具假成功、权限拒绝、目标版本切换、上下文压缩、延迟回执和恢复点损坏。
- **需要你判断：**
  1. 第一版最值得注入的 3–5 类扰动是什么？
  2. 评估指标应该优先看任务成功，还是损失上界、恢复时间和接管负担？
  3. 是否采用基线组、只观测组、闭环控制组三组对照？
- **原文核验入口：** [Google SRE：Testing for Reliability](https://sre.google/sre-book/testing-reliability/)；[Principles of Chaos Engineering](https://principlesofchaos.org/)。

## 材料 6：先评估不等于先造一个漂亮的统一分数

- **来源角色：** Dehghani 等研究者对 Benchmark 范式的反方批判，2021 年。
- **要解决的问题：** 社区常把 Benchmark 排名当成算法优越性的客观证明，但任务选择、子集、指标和历史状态都可能改变排名。
- **核心主张：** 每个 Benchmark 都隐含“什么重要”的价值选择。只改变任务子集，就可能让不同算法轮流成为最优；聚合分数会掩盖上下文与任务选择偏差。
- **机制/方法：**
  - 分析 task selection bias、community bias 和 Benchmark 的 statefulness；
  - 比较同一批模型在不同任务子集下的排名变化；
  - 要求先清晰定义问题、目标和适用上下文，再选择数据与指标。
- **关键证据：** 论文在多个 ML 领域展示相对排名会随任务选择显著变化；以 SuperGLUE 为例，不同子任务上的优胜者并不一致，平均分用于具体应用选型可能是次优的。
- **局限与反方：** 论文早于当前 Agent 浪潮，主要分析模型 Benchmark，不直接研究多步工具轨迹、环境状态和控制；它不能推出“不要量化”，只能推出“量化必须与主张和上下文绑定”。
- **与本期问题的关系：** 这是本期最强反方：评估第一很容易演变为“指标第一”。控制就绪度评估应保留多维硬门槛、失败样本和配置版本，而不是把一切压成 82 分。
- **需要你判断：**
  1. 是否明确拒绝统一健康分，只输出证据矩阵与硬缺口？
  2. 哪些维度允许加权优化，哪些维度必须零容忍？
  3. 文章是否需要正面批评当前 Agent Leaderboard 文化，还是保持在工程实践范围？
- **原文核验入口：** [The Benchmark Lottery](https://arxiv.org/abs/2107.07002)，重点看摘要、Task selection bias、Benchmark building blocks 和结论。

## 跨材料冲突与暂定综合

### 冲突一：能力上限还是生产可靠性

OpenAI 强调强 Harness 与足够预算，避免低估能力；生产控制则需要在明确权限、预算和干预约束下测可靠性。两者并不矛盾，但必须分成两套问题：

- **能力探测：** 这套系统在可信强配置下最多能做到什么？
- **准入评估：** 这套生产配置在限制条件下能否连续、可恢复地做到？

不能拿能力上限分数直接批准生产自主权。

### 冲突二：只看外部结果还是同时看轨迹

外部结果是任务价值的最终证据，但相同结果可能由越权、碰运气或不可恢复路径得到。只看轨迹又可能惩罚合法的创造性方案。因此最小方案应把二者分层：

- 结果层判断现实是否改变、是否满足业务和安全约束；
- 轨迹层判断证据、工具、权限、预算和干预链路是否可审计；
- 只有结果正确且关键过程约束满足，才算准入成功。

### 冲突三：评估先行还是评估拖慢实践

Anthropic 的经验是 20–50 个真实任务即可起步；本期更激进地提出先用 12–20 个高价值任务和已知故障 Seed 建最小基线。目的不是先造平台，而是减少后续控制改造的不可归因性。
