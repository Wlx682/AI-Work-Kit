# 核心主张

## 待用户确认的主张

> 智能体控制系统实践的第一步，不是给 Agent 打分，而是先证明评估本身有资格产生控制证据。任何评估在没有明确被测配置、有效参照、可失败任务、评分器校准、外部结果验证和不确定性出口之前，都不能用于扩大 Agent 自主权。宁可人工介入，或者明确宣布“不可评、证据不足”，也不能为了完成评估而强行得出通过结论。

## 大多数人可能认为

先选一个主流 Benchmark 或搭建 Eval 平台，得到成功率、质量分、安全分，就可以比较模型、确定 Runtime 并开始控制面改造。

## 用户观察到

条件评估是所有后续控制假设的上游。如果评估虚假、失去参照价值或为了完成流程强行出分，那么状态估计、风险判断、继续授权和控制策略都会在错误证据上运行。

## 真正机制

Eval 不是中立仪表。任务选择、Harness、工具、预算、评分器、参考事实和环境身份共同决定它测到了什么。只有先通过 Evaluation Qualification：

1. 明确此次结果想支持哪一种决策；
2. 固定并版本化被测配置；
3. 证明任务可解、参照可用、评分器可区分正确与错误机制；
4. 用外部结果和真实故障 Seed 验证评估能够失败；
5. 校准自动评分器与人工判断；
6. 为证据不足、专家分歧和环境异常提供 abstain/人工升级路径；

评估结果才有资格进入控制面的状态估计和自主权决策。

## 成立边界

- 不追求绝对正确或完整通用 Eval，而追求与当前风险和决策相称的证据；
- 第一阶段限定一个 Agent、一类真实任务、少量可逆工具和明确版本配置；
- 低风险可逆任务允许较轻参照，高风险或不可逆动作必须有外部真值、人工校准和恢复验证；
- “不可评”必须可追踪、可重试、有责任归属，不能成为回避评估的借口。

## 最强证据

1. DSH GUI 事故显示：验收对象错误时，构建、HTTP 200 和替代服务全部可以“通过”，但都不能证明用户页面发生了预期变化。
2. OpenAI 的评估有效性总结显示：Harness、工具、预算、坏题和 Reward Hacking 会实质改变结果及其可支持的主张。
3. Anthropic 要求参考解、重复试验、轨迹复核和人工校准；Benchmark Lottery 进一步说明统一聚合分数会随任务选择改变排名。

## 最强反方

不存在完全可靠的评估；如果先验证任务、参照、评分器和评估器本身，可能无限递归、错过业务窗口。模型与 Harness 变化又很快，刚校准完就可能过期。

## 回应

本主张不要求“评估完美后再行动”，而要求**决策权限不超过证据成熟度**。用影子运行、只读、可逆写入和高权限动作分级；自动评估不确定时升级人工；关键配置变化后只重评受影响证据。这样既避免伪确定性，也不把实践冻结在评估平台建设中。
